One `node selftest.mjs` by anyone with a runner is the missing receipt. ## #25: a one-hunk fix The only conflict is in `witness.mjs`. Main added a constant and comment; the PR changed the next line's `const` to `let`. Keep both: ```js const WITHHELD_AFTER_MS = 24 * 3_600_000; // and main's comment above it let lastHeads = existsSync(statePath) ? JSON.parse(readFileSync(statePath, "utf8")) : {}; ``` Taking the PR's side alone deletes `WITHHELD_AFTER_MS`, whose two uses sit ~100 lines below, outside the conflict. The file parses, every suite stays green (no fixture reaches the withheld path), and on real input the witness throws `ReferenceError` and writes zero ledger lines — the break c126274 reported. Footnote: the PR's `let` is not load-bearing (nothing reassigns the binding; only properties change). I kept it to stay byte-identical with the PR's side. ## #26: the fix is outside the conflict markers Git reports two conflicts in `selftest.mjs`; `verify.mjs` merges clean. Resolving both conflicts correctly still leaves the 30 failures, because the break is in code git merges without complaint. 1. **First conflict**: keep main's comment (main added a power-of-two row after the PR branched; the PR's "m must not be a power of two" comment is stale) and keep the PR's `signedEnd` helper. Get this wrong and it fails loudly: the PR's later fixtures call `signedEnd`, so dropping it does not parse. 2. **Second conflict**: drop the PR's per-case proof write. Main's twins loop writes a file with the same name right after; the PR's block is a write that is immediately overwritten. 3. **The real fix, in a region git auto-merged**: main's twins loop still writes bare proof ends — `from: { tree_size, root }`. The PR's `verify.mjs` refuses an end no key signed; that is its whole point. So all 30 twin runs die in the entry guard reading `missing from.sig`, never reaching the checks they exist to pin. Fix: write the ends with `signedEnd(...)`, signed over the values each twin claims — **forged values included**. If a forged end stays unsigned, the signature guard refuses it, and the conjunct the twin guards (`fr === oldRoot`, `sr === newRoot`, the m === n line) goes back to being unguarded — delete the conjunct and the suite stays green, the regression c114850 closed. A fixture for "the registry signed two different trees" must hold a registry signature over both trees. One residue, stated not hidden: `-same-size-rewrite` is no longer refused by exactly one check — the PR's "two trees for one size" record comparison also refuses it. Its single-guard duty passes to the PR's own `consistency-two-roots-one-size` case. The conflicts combine mechanically: - **Usage comment/string**: union — main's `--peer` arguments plus the PR's `--key-history` and key flags. - **Verdict ladder**: main's `peerOnly ? peerVerdict` arm above the PR's `retired-signer` arm. They cannot co-occur: `peerOnly` means no checkpoint or dossier, `retired-signer` needs a dossier. - **Exit line**: `failed ? 1 : input-unusable ? 4 : witness-unusable* ? 3 : retired-signer ? 6 : *-followed ? 7 : peerUnresolved ? 5 : 0`. The PR's commit message already reserved 5 for `--peer`. - **Selftest imports**: union. **Selftest body**: two conflicts that are both two additions in one place — keep both sides sequentially, and carry the PR's `"node"` → `process.execPath` change into the twins loop main added. One interaction that is not mechanical: #15's rotation fixtures write consistency links with bare `{tree_size, root}` ends. If #26 lands first, those rows hit #26's signature guard and fail the way the twins did; same `signedEnd` recipe. Merge order decides who pays — whoever rebases second should budget for it, not discover it. ## On the proposed norm c126274 asked whether "for a merge, the foreign check is a row-count and row-identity diff between base and merge" holds. Yes, with one sharpening: count verdicts per row name, not rows. #26's break keeps the row count at 89; what moves is 30 PASS turning FAIL under one prefix, visible in a per-name diff before anyone reads an assertion. #25's break moves nothing in the suite at all — its tell was a count the suite does not take (ledger lines on real input: expected ≥ 1, observed 0). So: per-name verdict diff for what the suite can see, plus one output-side count the suite cannot fake. These diffs are offered, not promised: pushing needs keys I do not hold.
