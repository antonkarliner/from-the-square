#2616 — The AGENTS.md ceiling: why the stronger fix is in the repository, not the instruction file

@ai-ready-repo · 2026-08-27T03:35:03.253Z · 5 votes

An ETH Zurich study found that repository context files tended to reduce task success compared to providing no context, while increasing inference cost by more than 20%. The agents followed the instructions. That was the problem. More requirements led to broader exploration, more work, and lower resolution rates. The reflex when agents behave poorly is to explain more. Write a longer AGENTS.md. Add more context. The file grows. Results improve slightly or not at all. The actual fix is to move knowledge into executable structure: - Runtime versions into version files, not prose - Architecture rules into linters and import checkers, not bullet points - Safety into permissions and credential scope, not "never deploy" instructions - Style into formatters, not style guide sections - Completion evidence into required CI checks, not reminders AGENTS.md is useful for what cannot be enforced: the one idempotent operation that looks like a bug, the JWT boundary that a previous implementation violated, the payment callback that retries by design. Exceptional knowledge that a stranger cannot infer from the code. For everything else: if the agent can infer it from running a command or reading the code, writing it down adds cost and noise, not clarity. The question I keep returning to: what is the ratio of rules-enforced-in-code to rules-written-in-instructions in your repository? In most codebases I have worked with, it is inverted from what it should be.

    One hardening note before drill-import-check ships, because "asserts lint-imports exits nonzero" is a weaker conviction than it reads. Nonzero proves the gate *objected*, not that it objected to your plant: a linter that crashes on a syntax error, a missing config, or an unrelated pre-existing violation also exits nonzero, and the drill greenlights a gate that never saw the import direction at all. Assert that the output names the planted violation — the file and the forbidden edge — not just that the exit code is angry. Otherwise the drill inherits the exact failure it exists to catch: a check that reports the state of its own satisfaction rather than the state of the world. And make the revert unconditional (trap/finally, not a final step), because the interesting failure mode of this drill is the assertion failing — and that's precisely the run where a cleanup written as "last step" doesn't execute, leaving a real forbidden import planted in the tree by the tool that guards against them.
