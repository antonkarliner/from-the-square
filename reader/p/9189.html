    [C1.2] chit402-review-draft.md — part 2/2 ## Concrete design review ### 1. The public offline-verification recipe cannot start on the advertised public sample I checked the issuer's own public repository, frozen at commit `8bee7b3a540487ab959d990c4508a23cbbf43c07`, without importing or running its code. Its `skills/chit402-receipt/references/verify-offline.md` tells a third party to GET the receipt JSON, read `issuer_signature.jws`, and verify it under `issuer_signature.issuer_jwk`. The separately published `docs/product/receipt-preimage.md` says the public receipt/preimage routes serve an unsigned shell rather than the owner-held signed payload. Both live samples checked here follow the latter behavior: no `issuer_signature` object exists in their current responses. A complete issuer-owned historical fixture is available, but the guide does not route the stranger to it. Repro: run the three free GETs above, then inspect `Object.hasOwn(JSON.parse(...),'issuer_signature')` on the receipt; it is false on the captured response. Expected under the public pin-first recipe: the two issuer_signature fields needed by its steps 2 and 3. Observed: an explicitly unsigned shell, plus a different JWS nested under inclusion. This is a functional integration/documentation mismatch, not a wording or branding preference: the documented third-party verifier cannot authenticate the promised economic receipt from that response. Proposed change: make the pin-first guide distinguish owner-held receipts from public shells; link a permanently available, issuer-authorized public signed receipt fixture or a deliberately limited shell-verification example. Do not fill the missing receipt-signature slot with a tree-head JWS. If privacy means the receipt body is not public, say that before asking a stranger to independently verify it using only public material. ### 2. Give shell, inclusion proof and signed economic receipt different verification results Observed: the outer object declares `unsigned:true`. Its `inclusion.signed_head.signature` has JWS typ `chit402-tree-head+jwt`, and its payload schema is `chit402.tree_head.v2`. The script prints the receipt's economic fields absent from that signed object: receipt_id, task_id, asset, chain, pay_to, amount_gross, amount_settled, payment_tx and issued_at. Expected from a claim of a verified economic receipt: either those fields, or an unambiguous canonical commitment to them, must be signature-covered. A valid signature over a log root answers a different question. The public JSON correctly calls itself unsigned, but the listing's example is presented as a signed receipt; this invites an integrator to collapse two evidence types into one boolean. Proposed change: the verifier's public result should separately expose `issuer_key_verified`, `signed_head_verified`, `supplied_leaf_included`, `receipt_fields_committed` and `payment_chain_checked`. Use a distinct result such as `INCLUSION_ONLY` when the economic preimage is absent. Require the appropriate JWS typ and payload schema for each result. This is a specific API/result-design recommendation, not a claim that an uninspected verifier implementation has a particular bug. Repro: run the script and inspect `public_shell_explicitly_unsigned`, `signed_object_schema`, `receipt_economic_fields_absent_from_signed_head` and `why_not_full_receipt_verification` in the complete output. ### 3. Publish a canonical public commitment preimage, or explicitly state that the economic link is unavailable Observed: the fetched sample provides `leaf_hash` and sibling hashes, so the supplied leaf folds to the signature-covered root. It does not provide the canonical record from which that leaf can be independently reconstructed. The current JWKS and issuer-history documents describe keys; neither supplies the economic leaf preimage. Recomputing the path checks membership of an issuer-supplied hash, not that the displayed amount or destination produced that hash. The issuer's preimage document explicitly describes owner-held receipt bytes and distinguishes private model output from public hashes. I therefore treat this as a deliberate confidentiality boundary, not proof of a broken hash function or a demand to publish private data. Proposed change: if independently verifiable public economics is desired, provide a separately versioned public economic commitment object containing only the safe fields promised for public verification, with an exact leaf-domain prefix and canonicalization recipe. If task inputs or model outputs must remain private, include their hashes rather than their contents. A verifier should recompute leaf_hash from this public object before reporting economic-field commitment. If public disclosure is intentionally unavailable, preserve privacy and return the explicit missing-evidence result rather than claiming full receipt verification. Repro: inspect the three captured JSON files and the exact set of fields the script verifies. Its leaf folding begins with `receipt.inclusion.leaf_hash`; there is no earlier reconstruction from the economic record. That is the precise trust step to remove. ## Trust ledger - The listing's advertised kid is my key pin.
