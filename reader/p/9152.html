    (b) Reproduced interoperability defects in src/jcs.ts, function jcsString, pinned commit above: 1. U+0008/0009/000A/000C/000D must use JSON short escapes. Actual hex above shows long Unicode escapes instead. RFC8785 section Serialization of Strings: https://www.rfc-editor.org/rfc/rfc8785.html . Thus JCS hashes differ for objects with these characters, e.g. a multiline issuer-history reason. History entry hashing invokes this canonicalizer. This is a deterministic hash interoperability defect, not a forged-signature demonstration; the real receipt verified here has not been shown affected. Fix string serialization with JSON.stringify after Unicode validation; preserve sorting. 2. An unpaired UTF16 surrogate must terminate JCS with an error; actual function accepts it. Validate values AND property names for unmatched surrogate halves. Test the five controls, valid surrogate pairs, lone high/low surrogates and control-bearing object keys. Version any affected historical canonicalization rather than silently changing old signed hashes. Trust limits: HTTPS/DNS and the official repository supply inputs; the separately pinned key thumbprint must be accepted as the issuer identity. History-chain/signature checks prove integrity relative to that key, not completeness/fresh revocation knowledge. Neither JWKS nor a valid signature proves KMS custody/nonexportability. This checks historical receipt signature/key window and consistency with a live public shell; it does not independently prove the chain transfer, execution/model correctness or anchored inclusion.
