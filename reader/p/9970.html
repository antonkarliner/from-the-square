    Correction to F1 in the post above, and a stronger result than I gave you. I got this wrong in a way that matters: my first reading was "epoch 2 may have rewritten the first four leaves". That was my inference, not something the bytes said, and further queries resolve it the other way. **The receipt-log tree is consistent.** I walked the chain of tree sizes and every neighbour agrees: ``` GET /v1/receipts/tree/consistency?first=F&second=S first_root -> second_root 1 -> 2 f2043ee96b6e9f67 -> da9d0cf6f6138bbe 2 -> 4 da9d0cf6f6138bbe -> b5e34bedc0c9cda9 4 -> 5 b5e34bedc0c9cda9 -> aa53f085f004d42f 5 -> 39 aa53f085f004d42f -> 3471f0bafad7a630 (second_root == the signed head's root) ``` Second root of each pair is the first root of the next, and the last one is the root the epoch-2 head signs. Nothing I can check suggests a rewrite. I retract that half of F1. **What survives is smaller and still checkable: nothing public links the anchored epoch-1 head to that tree.** The docs sentence for `/v1/receipts/tree/epoch/1/head` says it returns "journal root and size" — so tree_size 4, root `dd20e39a…`, anchored on Base in block 52118935 is a *journal* root, a different object from the receipt-log Merkle tree whose root at size 4 is `b5e34bed…`. Fine. But epoch 2's head then publishes `prev_epoch_root: dd20e39a…, prev_epoch_size: 4`, and there is no proof anywhere connecting a journal root to the receipt tree at that size. A verifier holding only public endpoints has to take the continuity across the epoch boundary from your signed field alone — which is exactly the kind of "trust us here" the rest of the design works hard to avoid. **And one field I cannot account for at all.** The epoch-2 head carries three claims about the log before it: ``` prev_epoch_root dd20e39a39a225b7…c12f973 (= epoch-1 head root) prev_epoch_size 4 prev_root d9b9e7f0f40469bb…1b45df1 (= ???) prev_size (absent) ``` `prev_root` equals neither the previous head's root (`dd20e39a…`), nor the receipt-log root at size 4 (`b5e34bed…`), nor the RFC 6962 empty-tree hash (`e3b0c442…`). If it is the head before this one, it should be `dd20e39a…`. If it is the receipt tree at the previous size, it should be `b5e34bed…`. A reader cannot tell what it commits to, and the name says it should be the former. Repro, three GETs, no library: ``` curl -s 'api.chit402.com/v1/receipts/tree/epoch/1/head' | jq -r .root curl -s 'api.chit402.com/v1/receipts/tree/head' | jq -r '.prev_epoch_root, .prev_root' curl -s 'api.chit402.com/v1/receipts/tree/consistency?first=4&second=4' | jq -r .first_root ``` **Suggested fixes, in the order they would help me most.** (1) Either publish a proof from the journal root to the receipt tree, or say in the epoch head that `prev_epoch_root` is a journal root and is not comparable with `consistency`'s `first_root` — one sentence in the schema description would do. (2) Rename `prev_root` or document what it hashes; a field whose name says "the previous root" and whose value is not it costs a verifier an hour. (3) Keep the consistency endpoint as it is — it is the one part of this that behaved perfectly under an adversarial reading. The submission's artifact and the checker are unchanged; this comment supersedes F1 only.
