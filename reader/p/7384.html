The automatic gap extractor still labels the four three-byte clusters as `changed`, because it currently recognizes only isolated two-byte differences.     [DRVSPACE.EXE supplemental research update — part 3/3] ## 8. The compression UI "Press C" gate Providing `DRVSPACE.INI` switches the executable from its installation wizard into the management UI and reaches both: ```text compress existing drive create new compressed drive ``` Both flows reach the final `Press C` confirmation screen, but the program does not proceed. This was initially suspected to be a keyboard-delivery problem. VM instrumentation disproved that. The active BIOS call was recovered from the real guest stack: ```text 1E98:CEEA CD 16 INT 16h return 1E98:CEEC ``` At the gate, `[DI+1Dh] = 10h`, making this BIOS function `INT 16h/AH=12h`: an enhanced-keyboard status query, not a blocking key read. The recovered runtime state also independently confirms the DGROUP relation: ```text DS - load segment = 0x3E49 ``` DriveSpace installs no INT 09h or INT 16h hook, so there is no hidden product keyboard filter. The following inputs were tested: - no input; - unrelated key `Z`; - documented key `C`; - Enter; - repeated key bursts; - all 42 common keyboard scancodes; - Shift+C with explicit make/break codes; - modifier-release sequences; - explicit BIOS keyboard-state cleanup. The BIOS keyboard buffer proves that the key is delivered and read. Nevertheless, the screen and execution profile remain unchanged. Measured execution: ```text condition guest-code share disk changed no key 31% no Z 32% no C 33% no Enter 33% no ``` The entire 64 MiB disk remained byte-identical for 60 consecutive seconds. Therefore the program is not blocked waiting for the confirmation key. It is already cycling in an input-independent busy loop. This path is parked as a limitation of the tested v86 0.5.462 + SeaBIOS environment, not as evidence that the compression engine is unreachable in general. ## 9. Mouse path recovered in the VM A functional INT 33h mouse driver was built and verified from DOS: ```text TEST33.COM -> INT 33h AX=0000 returned AX=FFFF ``` With the driver installed, DriveSpace makes six INT 33h calls and registers a user-event callback through `AX=000Ch`: ```text registered callback = 1E98:BF70 ``` The callback maps mouse events into synthetic UI key codes: ```text movement 0x200 left-button press 0x201 left-button release 0x202 right-button press 0x204 right-button release 0x205 ``` They are passed into the console/input layer through: ```text call 1E98:C005 ``` An INT 1Ch injector was constructed to invoke the registered callback. Its far-call and return discipline were independently validated by redirecting the callback to a bare `RETF`. Calling the real DriveSpace callback from an arbitrary timer-interrupt context crashes into segment `0000`. The console layer is not reentrant. A second injector was gated to fire only outside the BIOS and console segments. At the `Press C` screen, the gate never found a safe context because the console layer remained continuously active on the stack. This establishes the mechanism: ```text the keyboard is delivered but the UI does not consume it the mouse callback is registered but cannot be safely entered the normal UI event loop is not running the program is livelocked inside its console/keyboard layer ``` This explains the frozen screen, the fixed count of six INT 33h calls, the absence of disk activity and the large BIOS residency. It also establishes previously unknown application structure: ```text mouse callback 1E98:BF70 console injection 1E98:C005 synthetic key family 0200h..0205h ``` These findings are semantic/runtime evidence only and admit no image bytes. ## 10. Separate stage2 runtime checkpoint A separate earlier VM campaign compared the stock path with a controlled B/SHELL fixture. Both paths used the same packed `DRVSPACE.EXE` and footer, but the stage2 input had already diverged before the copy loop: ```text normalized source +0x287C6: stock 0x13 B/SHELL 0x01 stage2:00F8 LODSB stock BX=0013 B/SHELL BX=0001 stage2:0103 REP MOVSB copy length therefore diverges ``` The recorded causal chain for the B/SHELL case is: ```text pre-stage2 write at child alias +0x07ED6 -> stage2:002B -> normalized source +0x287C6 -> stage2:00F8 -> BX divergence -> stage2:0103 output divergence ``` This proves that the later stage2 output difference is caused by an earlier input-byte difference, not by different packed EXE/footer bytes. It does not yet establish the upstream semantic cause of the byte change and contributes no ownership admission. ## 11. Final forensic boundary The new results change our understanding of the residual, but not the forensic coverage contract: ```text TARGET1 = PROVEN EXACT_UNIQUE_MATCH TARGET2 = SUPPORTED RELOCATED_OR_REBASED_MATCH both are inherited application code both remain CROSS_VERSION_HOMOLOGY neither has contribution ownership OWNERSHIP_DELTA = 0 B ADMISSIBLE_BYTES = 0 B COVERAGE_DELTA = 0 B ``` The unresolved ownership front remains: ```text 409 B singleton-zero linker candidates 593 B encoded resource containers 726 B other DGROUP objects 216 B principal code with provenance but incomplete ownership ``` TARGET1 and TARGET2 no longer need to be treated as unidentified code.
