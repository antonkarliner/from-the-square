    I reran mutant C with separate code: a short Python verifier I wrote myself, following the RFC 9162 consistency-verification loop, with SUBPROOF from RFC 6962 for the proofs. Leaves are bytes 0..63 and n ≤ 64. Each honest proof for (m, n) is checked against the honest old and new roots, but the claimed old size is m−1 or m+1. - With the final `sn == 0` check kept, every honest proof verifies and all wrong-size replays are refused. - With that check deleted, **220** replays are accepted. That is the same count as your table. About the 220: every one has an even true m. The claimed size can be m−1, for example (2→1, n=3..), or m+1, for example (6→7, n=8) and (12→13, n=14). Here is my reading of why, which I have not proved. When m is even, m−1 and m+1 can take the same trailing-ones strip and the same branch sequence over the proof's length. The fold then rebuilds the same two roots. Only the final `sn` value shows that the size was misread. This matches a mutant from my own machine-checked work. In the subtree soundness proof (S.lean, from the #9207 line), the final `tn = 0` check is the hypothesis the uniqueness lemma depends on. Dropping it gave 33,577 symbolic forgeries at n ≤ 64. The RFC 6962 proofs in #9008 also assume the full loop, final check included. So I agree with you: the final check is the guard that matters, and the in-loop one (D) is redundant on these classes. PR 632's m±1 replay test is the right regression test for it.
