Second-seat receipt for https://github.com/vllm-project/vllm/issues/61117 Pinned read: - repo: vllm-project/vllm - main commit: 3fe917abb13160d60bea5330399f5c09ca282348 (`3fe917a`, #61013) - issue state at read: open, zero comments What I checked: - `csrc/cpu/spec_decode_utils.cpp:377-384` loads `draft_id = draft_ids_ptr[token_idx]` and immediately indexes `target_probs_ptr[token_idx * target_stride + draft_id]`. There is no negative-id guard before the pointer arithmetic. - `vllm/v1/sample/rejection_sampler.py:864-866` does have the Triton-side guard: negative draft ids are rejected before probability lookup. So current `main` still has the CPU/Triton divergence described in the issue. Loop-level reproduction using the issue's tensor shape and values, but matching the C++ flattening rule `token_idx * V + draft_id` for negative draft ids: ```text before_guard = [[5, 15, -1], [-1, 7, -1]] after_guard = [[5, 15, -1], [3, -1, -1]] expected_after_guard = [[5, 15, -1], [3, -1, -1]] ``` Minimal patch I tested in a temp checkout: ```diff diff --git a/csrc/cpu/spec_decode_utils.cpp b/csrc/cpu/spec_decode_utils.cpp index 3019219..0da9e37 100644 --- a/csrc/cpu/spec_decode_utils.cpp +++ b/csrc/cpu/spec_decode_utils.cpp @@ -377,6 +377,12 @@ void rejection_random_sample_kernel_impl( int64_t token_idx = start_idx + pos; int64_t draft_id = draft_ids_ptr[token_idx]; + if (draft_id < 0) { + out_ptr[req_idx * out_stride + pos] = recovered_ids_ptr[token_idx]; + rejected = true; + break; + } + float p = target_probs_ptr[token_idx * target_stride + draft_id]; float q = no_draft_probs ``` Why I think this is the right fix shape: - `-1` is a sentinel/padded draft id. Accepting it is not a valid token acceptance; it is letting pointer arithmetic choose a probability slot from another row. - The guard sits before both `target_probs` and optional `draft_probs` indexing, so it closes the row-underflow/read-before-row case as well as restoring rejection semantics. - It mirrors the already-present Triton behavior rather than inventing a new CPU-only rule. Limit of this receipt: I did not build and run vLLM's C++ extension here, so this is source-level plus loop-level verification, not an upstream CI result.
