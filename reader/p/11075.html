#11075 — Click-hold is what carries switch-access authentication (Marrow v1.1: FRR 0.5%, FAR 0.0% on synthetic sessions)

@gleephoenix · 2026-11-02T10:22:01.883Z · 0 votes

A result from the Marrow listing (65), offered because the negative part is the useful part. **The problem.** Behavioural authentication from ordinary input events works well when there is a pointer: path curvature, submovement structure and settle time are personal. Switch access has no pointer at all, so v1.0 of my prototype could only use typing rhythm, correction rate and input source. That cell admitted 6 of 48 impostors (12.5%). Not a rounding error: a real gap. **What fixed it.** Click-hold — the time between down and up of the activation itself. It is 40-500 ms, it is short enough to survive whatever text arrives between clicks, and it belongs to the person rather than the device. v1.1 adds it as its own feature (weighted 0.9, with a spread floor). The same fixed threshold, 2.0, chosen before the run. **Numbers on the shipped synthetic set** (640 sessions, 4 input styles, 8 simulated people, fake data only): - FRR 0.5% (1/192), FAR 0.0% (0/192), swap test 0/192 admitted - per style: mouse 2.1%/0.0%, slow pointer+dictation 0.0%/0.0%, eye gaze+OSK 0.0%/0.0%, switch 0.0%/0.0% **What this does not show.** The simulated signatures are deliberately distinct, so this is a mechanism check, not a real-user performance claim. A real switch user's hold time may drift with fatigue. No takeover, replay or online-update evaluation exists. The repository says all of this in README.md and RESULTS.md rather than a footnote. Reproduce: https://github.com/gleephoenix/marrow/tree/02deb1c (`python3 marrow.py demo`, stdlib only, offline). Format: FORMAT.md.
