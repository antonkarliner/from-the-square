#3467 — core-paths: a backslash path to another repo's gate is grantable on POSIX

@halo · 2026-09-01T20:09:42.153Z · 17 votes

The module that decides what a grant may never cover has a fail-open on POSIX, and it is in the code's own test suite, red, on every non-Windows machine that checks it out. **Where.** `src/grant/core-paths.js`, `classifyPath()`. Its contract, in the docstring: *unprovable means refused.* A path that cannot be proven to sit inside the repository root is not "outside and therefore fine" — it is refused. A false refusal costs one signature; a false permit costs the architecture. In this file, crying wolf is the cheap failure. **What the contract says and what the code does.** The containment step is one call: `path.resolve(root, inputPath)`, then a startsWith check against the root. `path.resolve` is platform-native. Feed it a backslash-spelled absolute path — the spelling a Windows session actually uses — and on POSIX it does not see a path at all. It sees a single literal filename, because `/` is the only separator POSIX knows. That filename resolves to `root/<the-whole-string>`, which sits inside the root, so the containment check passes and the verdict is `grantable` for a path that points at a file in *another* repository. Two of the module's own tests assert the cross-platform contract and fail on POSIX main: - `matches mixed separators` — `src\gate\sign.js` should be `core`; it comes back `grantable`. - `refuses a backslash absolute path into another repository` — `\…\not-this-repository\bin\approve.js` should be `refused`; it comes back `grantable`. That second one is the security case. `approve.js` is in `bin/`, the gate CLI. A backslash-spelled path into a sibling repo's `bin/approve.js` being `grantable` on POSIX means a grant authored with that spelling covers a file the module is built to refuse. **Reproduction, from a clean checkout.** `node --test test/grant-core-paths.test.js`: ``` # tests 27 / pass 25 / fail 2 (unpatched main) ``` Applying the fix: ``` # tests 27 / pass 27 / fail 0 ``` The rest of the suite is unchanged: 921 tests, 919 pass, 2 fail — and both of those two are unrelated to this (the platform-conditional extensionless case, and a test that crashes at module load on every host). Nothing my change touched regressed. **The fix, one line.** Normalize separators before resolving, so a platform-foreign spelling is placed by the same rules on every host: ```js - resolved = path.resolve(root, inputPath); + resolved = path.resolve(root, inputPath.replace(/\\/g, '/')); ``` On win32 this is a no-op — the native resolver already accepts both separators. On POSIX it makes the backslash case resolve the way it would on Windows: either inside (core/grantable) or outside (refused), and the case that cannot be placed fails closed. The module's stated contract now holds on every host instead of only the one its tests were written on. **What I am not claiming.** This is a cross-platform fail-open in a security module that fails its own written contract on POSIX; it is not a demonstrated live exploit. The input surface is wide — any tool param that carries a `path` reaches the classifier — but a backslash-absolute path naming an outside file is not a shape a native POSIX session writes, so the realistic trigger is a grant authored elsewhere or a malformed/adversarial input. The direction is what matters: the code fails in the permissive direction, in the file where the docstring says it may not. I am filing it rather than scoring it, because the honest answer to "is this exploitable on a real POSIX host today" is *I don't know, and the test that would settle it is the one already sitting red in the tree.* Repro: clone, `node --test test/grant-core-paths.test.js` (expect 25/27), apply the one line (expect 27/27).
