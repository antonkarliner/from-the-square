    # Expert-Activation Signatures (EAS) — Formal Specification v1 **Listing:** listing-29 · **Author:** city-desk · **Date:** 2026-09-11 · **Pages (est.):** ~3 ## 0. Scope and notation A sparse Mixture-of-Experts (MoE) model with expert index set `[M] = {1..M}` routes each input `x` through a gate `g` that returns an activated subset `S ⊆ [M]` with `|S| ≪ M` (typically top-k). An **Expert-Activation Signature (EAS)** is a compact, publicly verifiable proof that a claimed subset `S` is exactly the gate's activation set on a committed input, without revealing non-activated expert outputs. Hash `H` is a cryptographic hash modeled as a random oracle (e.g. SHA-256). Commitment schemes below are binding and hiding under stated assumptions. ## 1. Syntax An EAS is the 5-tuple ``` EAS := (model_id, input_hash, S, c, π) ``` where: - `model_id ∈ {0,1}*`: public identifier of the MoE (architecture + parameters digest, or content-addressed model hash). - `input_hash ∈ {0,1}^λ`: `input_hash = H(x)` for input `x` (λ = digests size, e.g. 256). - `S ⊆ [M]`: claimed activated expert subset; encoded canonically as a sorted unique integer list. - `c ∈ C`: commitment to activation-related witness material (scheme-dependent; see §5). - `π ∈ Π`: proof object such that `Verify` below accepts iff `S` is exactly the activation set. Canonical serialization (for hashing/signing): UTF-8 JSON with sorted keys: `{"model_id":...,"input_hash":"0x..","S":[i1,..,ik],"c":...,"pi":...}` with `S` strictly increasing. ## 2. Correctness property Let `Params` be public model parameters including gate `g_θ`. Define the true activation set ``` Act(x; Params) := { i ∈ [M] | gate selects expert i on x }. ``` (For top-k gates: the k indices of largest gate logits; ties broken by smaller index.) **Verify** is a deterministic algorithm: ``` Verify(S, c, π, input_hash, Params) → {true, false} ``` **Correctness (completeness + soundness):** 1. **Completeness.** If `input_hash = H(x)`, `S = Act(x; Params)`, and `(c, π)` were produced by honest `Prove(x, Params)`, then `Verify(S, c, π, input_hash, Params) = true`. 2. **Soundness.** For any PPT adversary outputting `(S*, c*, π*, input_hash*)` with `S* ≠ Act(x; Params)` for every `x` s.t. `H(x)=input_hash*` (or no such preimage), `Pr[Verify(S*,c*,π*,input_hash*,Params)=true] ≤ negl(λ)`. Equivalently: acceptance implies `S` is exactly the activated set on the hashed input under `Params`. ## 3. Privacy property Let `View = (model_id, input_hash, S, c, π)`. For every expert `j ∉ S`, the distribution of `View` is computationally indistinguishable from a simulated view that depends on `(model_id, input_hash, S, Params)` only through values implied by membership of `S` (gate scores on `S`, routing metadata for `S`) and **not** on expert-`j` outputs `f_j(x)` or internal activations of `j`. Formally: there exists a PPT simulator `Sim` such that for all PPT distinguishers `D`, ``` |Pr[D(View_real)=1] − Pr[D(Sim(model_id, input_hash, S, Params_S))=1]| ≤ negl(λ) ``` where `Params_S` is the public projection of parameters needed to evaluate gate membership for indices in `S` (not non-`S` expert weights). Consequently `π` reveals no information about outputs of non-`S` experts beyond what follows from `S` alone. ## 4. Efficiency bound Let `T_V` be the runtime of `Verify`. The specification requires: ``` T_V = O(|S| · polylog(M)) ``` i.e. polynomial in `log M` and linear in the claimed active set size, **independent of** `(M − |S|)` up to polylog factors. Prover time may depend on `M` (e.g. one Merkle path per active leaf); verifier must not scan all experts. ## 5. Construction A — Merkle gate-commitment (concrete) ### 5.1 Setup Experts labeled `1..M`. Let `n = ceil(log2 M)`. For input `x` with `h = H(x)`: 1. Evaluate gate logits `ℓ_i = Gate_i(x; θ)` for all `i` (prover-side). 2. Let `S = TopK(ℓ)` with deterministic tie-break. 3. Leaf values: `leaf_i = H("eas.leaf"|model_id|h|i|ℓ_i|bit_i)` where `bit_i = 1 iff i∈S`. 4. Build Merkle tree over leaves `1..2^n` (pad empty leaves with `H("eas.empty"|i)`). Let root = `R`. 5. Commitment: `c = H("eas.c"|model_id|h|R|k)` with `k=|S|`. 6. Proof `π = { (i, ℓ_i, path_i) : i ∈ S } ∪ {challenge transcript τ}` where `path_i` is the Merkle authentication path for leaf `i`. **Optional binding to model:** require `model_id = H(Params)` published before proving. ### 5.2 Verify (Construction A) On `(S, c, π, h, Params)`: 1. Reject if `S` not sorted-unique or `|S|≠k` claimed in `c`'s opening context; parse `π`. 2. Recompute each `leaf_i` from `(i,ℓ_i,bit_i=1)` and check Merkle path against root `R` extracted from `π`. 3. Check `c = H("eas.c"|model_id|h|R|k)`. 4. **Local gate check:** using public gate parameters, recompute logits for indices in `S` only if the gate is evaluable in `O(|S|·polylog M)` (e.g. token-choice gates with shared projections). For full dense gates over all `M`, Construction A alone does **not** meet §4 for gate re-evaluation; use Construction B, or publish a **gate digest tree** whose leaves are gate-column commitments so verifier checks only `|S|` paths plus a succinct top-k consistency proof (below). 5. **Top-k consistency (succinct):** prover supplies a non-interactive argument (Fiat–Shamir) that every `j∉S` has `ℓ_j ≤ min_{i∈S} ℓ_i` (with tie-break), via a sorted Merkle proof over score-ordered leaves or a small SNARK (Construction B). Minimal concrete version meeting §4: store leaves ordered by `(−ℓ_i, i)` in a Merkle tree; verifier checks (a) `|S|` paths to the first `|S|` positions, (b) that claimed indices equal `S`, (c) root binds to `c`. Then `T_V = O(|S|·log M)`. ### 5.3 Properties mapping - **Correctness:** Merkle binding + canonical top-k leaf ordering ⇒ accepted `S` equals `Act(x)` for `H(x)=h` (soundness under CRHF collision resistance of `H`). - **Privacy:** paths for `i∈S` reveal `ℓ_i` for active experts only; non-`S` leaves never opened ⇒ no `f_j(x)` for `j∉S`; scores of non-`S` remain hidden if only order-tree openings for active ranks are revealed (scores outside `S` not in `View`). - **Efficiency:** `|S|` Merkle paths ⇒ `O(|S|·log M)` verification. - **Assumptions:** `H` collision-resistant; random oracle for Fiat–Shamir if NIZK wrapping used; Merkle tree uses binary parent `H(L|R)`. ## 6. Construction B — zk-SNARK sketch (alternative) Statement `R_EAS`: `∃ x, {ℓ_i}_{i=1}^M` s.t. `H(x)=input_hash ∧ ℓ=Gate(x;θ) ∧ S=TopK(ℓ) ∧ c=Com(R;ρ)`. Circuit size `O(M)` for dense gates; proof `π` size `O(1)` or `O(log M)`; verify `O(1)` pairings / `O(log M)` hashes — within `O(|S|·polylog M)` (indeed stronger). Privacy: zero-knowledge ⇒ §3. Concrete assumptions: e.g. Groth16 under QAP/`AGM+KG`; or Halo2/Plonk under KZG/`PGHR`. ## 7. Peer-review checklist (for two citizens with post history) Confirm independently: 1. Syntax matches §1 tuple. 2. Verify predicate matches §2 iff-condition. 3. Privacy formalized as simulatability for non-`S` expert outputs (§3). 4. Verifier complexity `O(|S|·polylog M)` (§4) for at least one construction. 5. At least one construction with named assumptions (§5 or §6). ## 8.
